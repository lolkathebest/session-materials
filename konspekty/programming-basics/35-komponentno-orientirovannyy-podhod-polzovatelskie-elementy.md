## 1. Теоретические основы компонентно-ориентированного подхода в C#

### Определение компонентно-ориентированного подхода и его отличие от объектно-ориентированного

В процессе разработки программного обеспечения разработчики постоянно сталкиваются с необходимостью управлять сложностью больших систем. На предшествующих занятиях вы изучили объектно-ориентированное программирование (ООП), где базовыми строительными блоками выступают классы и объекты. ООП позволяет моделировать предметную область через сокрытие данных (инкапсуляцию), наследование и полиморфизм. Однако на уровне проектирования крупных графических интерфейсов чистого ООП иногда оказывается недостаточно для эффективной организации кода.

> **Определение.** Компонентно-ориентированный подход (Component-Based Development, CBD) — это методология проектирования и разработки программного обеспечения, которая фокусируется на создании систем из независимых, заменяемых и готовых к повторному использованию модулей, называемых компонентами.

Чтобы четко понимать разницу между ООП и CBD, рассмотрим их ключевые отличия:

| Критерий | Объектно-ориентированный подход (ООП) | Компонентно-ориентированный подход (CBD) |
|---|---|---|
| **Базовая единица** | Класс и объект | Компонент (модуль с четким контрактом) |
| **Уровень абстракции** | Низкий / Средний (работа с конкретными типами, полями, методами) | Высокий (работа с автономными функциональными блоками) |
| **Связанность (Coupling)** | Объекты могут иметь тесные связи через прямые ссылки и вызовы методов | Компоненты слабо связаны; взаимодействие строго через интерфейсы и события |
| **Повторное использование** | На уровне исходного кода (наследование классов, подключение библиотек) | На уровне двоичного кода и визуальных элементов (белая коробка против черной коробки) |
| **Интеграция** | Требуется перекомпиляция или изменение исходного кода при замене реализации | Возможна «горячая» замена компонентов без изменения остальной системы |

В объектно-ориентированном программировании вы создаете класс `Button`, описывающий его поля, методы рисования и клика. В компонентно-ориентированном подходе готовая кнопка рассматривается как черный ящик (компонент), который можно перетащить из панели элементов на форму, изменить его свойства через окно свойств (Properties) в Visual Studio и задействовать в проекте, не вдаваясь в детали того, как именно реализован код ее отрисовки.

### Понятие компонента в .NET: интерфейс IComponent и пространство имен System.ComponentModel

Платформа .NET предоставляет мощную инфраструктуру для поддержки компонентов. В основе этой инфраструктуры лежит пространство имен `System.ComponentModel`.

> **Определение.** Интерфейс `IComponent` — это базовый контракт, которому должен удовлетворять любой объект, претендующий на звание компонента в среде .NET. Он определяет минимальный набор свойств и методов для управления жизненным циклом объекта и его интеграции в среду разработки.

Интерфейс `IComponent` выглядит следующим образом:

```csharp
namespace System.ComponentModel
{
    public interface IComponent : IDisposable
    {
        ISite? Site { get; set; }
        event EventHandler? Disposed;
    }
}
```

Разберем составляющие этого интерфейса:
1. `IDisposable`: поскольку компоненты часто управляют неуправляемыми ресурсами (например, дескрипторами операционной системы, графическими кистями, файловыми потоками), они обязаны реализовывать метод `Dispose()` для корректного освобождения памяти.
2. `Site`: свойство, связывающее компонент с контейнером, в котором он находится. Контейнер управляет именем компонента, его лицензированием и взаимодействием со средой разработки (дизайнером Visual Studio).
3. `Disposed`: событие, которое генерируется сразу после вызова метода `Dispose()`, позволяя другим объектам узнать об уничтожении компонента.

На практике классы редко реализуют интерфейс `IComponent` «с нуля». Вместо этого они наследуются от базового класса `Component`, который уже реализует `IComponent` и предоставляет базовую функциональность (поддержку работы с лицензиями, контейнерами и событиями):

```csharp
using System.ComponentModel;

public class MyCustomComponent : Component
{
    // Пользовательская логика компонента
}
```

### Свойства компонентов: инкапсуляция внутреннего устройства, независимость, возможность повторного использования

Компоненты обладают тремя фундаментальными свойствами, которые делают их незаменимыми при разработке интерфейсов на Windows Forms:

1. **Инкапсуляция внутреннего устройства («Черный ящик»):** Пользователь компонента видит только его внешний интерфейс — публичные свойства, методы и события. Внутренняя структура (например, какие именно дочерние элементы управления используются внутри) полностью скрыта. Если разработчик решит изменить внутреннюю реализацию компонента, внешний код, использующий этот компонент, останется работоспособным при сохранении контракта.
2. **Независимость (Автономность):** Компонент спроектирован так, чтобы функционировать самодостаточно. Он содержит всю необходимую логику обработки данных и отрисовки, не завися от конкретного приложения, в которое он встроен.
3. **Возможность повторного использования (Reusability):** Написав и отладив компонент один раз, вы можете применять его в десятках различных проектов без дублирования кода.

### Архитектура клиент-компонент: контракты взаимодействия, свойства, методы и события

Взаимодействие между главной формой приложения (клиентом) и пользовательским компонентом строится на основе архитектуры «клиент-компонент». Эта архитектура регламентирует три канала связи:

- **Свойства (Properties):** Служат для настройки внешнего вида и состояния компонента. Свойства обеспечивают безопасный доступ к внутренним данным через методы доступа `get` и `set`. Например, свойство `TitleText` позволяет внешней форме задать заголовок, отображаемый внутри компонента.
- **Методы (Methods):** Представляют собой действия, которые компонент может выполнить по команде клиента. Например, метод `ClearData()` очищает введенные внутри компонента значения.
- **События (Events):** Механизм обратной связи. Если внутри компонента происходит что-то важное (например, пользователь нажал внутреннюю кнопку или изменил данные), компонент генерирует событие. Клиент (форма) подписывается на это событие и реагирует на него.

```
+-------------------------------------------------------+
|                     Главная форма                     |
|                                                       |
|  [ Установка свойств ] ----> (Свойства)                |
|  [ Вызов методов    ] ----> (Методы)                  |
|  [ Обработка        ] <---- (События)                 |
+-------------------------------------------------------+
                                 |
                                 v
+-------------------------------------------------------+
|                 Пользовательский компонент            |
|                                                       |
|   [Внутренний TextBox]   [Внутренняя Кнопка]          |
+-------------------------------------------------------+
```

### Преимущества повторного использования кода в графических интерфейсах Windows Forms

Без использования компонентно-ориентированного подхода разработка сложных оконных приложений превращается в дублирование кода. Представьте, что в приложении на каждой из пяти разных форм должен присутствовать одинаковый блок авторизации (поля «Логин», «Пароль» и кнопка «Войти»). 

При процедурном или наивном объектном подходе разработчик будет копировать эти элементы управления и обработчики кликов на каждую форму. Это приводит к трем критическим проблемам:
1. **Дублирование кода:** Изменение логики авторизации потребует ручного исправления кода на всех формах.
2. **Высокий риск ошибок:** Легко пропустить одну из форм или нарушить единый стиль интерфейса.
3. **Раздувание кодовой базы:** Объем исходного кода возрастает в несколько раз.

Компонентно-ориентированный подход решает эти проблемы радикально: блок авторизации создается один раз как единый компонент, после чего визуально «вставляется» на нужные формы. Любое изменение в логике компонента мгновенно отражается во всех местах его использования.

### Иерархия визуальных элементов управления: от класса Object до Control и UserControl

В платформе .NET и Windows Forms все визуальные элементы выстроены в строгую иерархическую цепочку наследования. Понимание этой иерархии критически важно, так как каждый вышестоящий класс передает по наследству определенный функционал.

1. `System.Object`: Абсолютный корень всей иерархии типов в C#. Каждый класс неявно наследует от него.
2. `System.MarshalByRefObject`: Базовый класс для объектов, позволяющих осуществлять маршалинг по ссылкам через границы доменов приложений.
3. `System.ComponentModel.Component`: Базовый класс для всех компонентов (как визуальных, так и не визуальных, например, `Timer`). Реализует интерфейс `IComponent`.
4. `System.Windows.Forms.Control`: Ключевой базовый класс для **всех визуальных элементов управления** в Windows Forms. Именно уровень `Control` отвечает за:
   - Позиционирование на экране (`Location`, `Size`).
   - Отображение (`Visible`, `Enabled`, `ForeColor`, `BackColor`).
   - Обработку ввода с клавиатуры и мыши (`Click`, `KeyDown`, `MouseDown`).
   - Отрисовку на поверхности экрана.
5. `System.Windows.Forms.ScrollableControl`: Промежуточный класс, добавляющий поддержку полос прокрутки для контейнеров.
6. `System.Windows.Forms.ContainerControl`: Класс, управляющий фокусом ввода среди дочерних элементов управления (базовый для форм).
7. `System.Windows.Forms.UserControl`: Специализированный класс-контейнер, предназначенный для создания составных пользовательских элементов управления путем объединения нескольких готовых контролов (`Button`, `TextBox` и т.д.).

Схема иерархии в виде текстового дерева:

```
object
 └── MarshalByRefObject
      └── Component
           └── Control (базовый класс для всех визуальных элементов)
                └── ScrollableControl
                     └── ContainerControl
                          ├── Form (окно приложения)
                          └── UserControl (основа для пользовательских компонентов)
```

### Понятие контейнера компонентов и жизненный цикл компонента в памяти

Когда вы размещаете визуальные элементы на форме в Visual Studio, форма выступает не просто как графическое окно, но и как **контейнер компонентов** (`IContainer`). Контейнер отвечает за две важнейшие задачи:
1. Хранение ссылок на все дочерние компоненты в коллекции `Controls` или `Components`.
2. Управление жизненным циклом компонентов.

Жизненный цикл компонента состоит из следующих этапов:
1. **Создание (Instantiation):** Вызывается конструктор компонента (например, `new MyControl()`). На этом этапе выделяется память в куче (Heap), инициализируются внутренние поля.
2. **Инициализация (Initialization):** Вызывается метод `InitializeComponent()`, устанавливаются свойства, переданные из дизайнера.
3. **Активное использование:** Компонент отображается на экране, принимает фокус, генерирует события и обрабатывает действия пользователя.
4. **Уничтожение (Disposal):** Когда форма закрывается, контейнер обходит все вложенные компоненты и вызывает для каждого из них метод `Dispose()`. На этом этапе освобождаются системные ресурсы (например, графические контексты), а сборщик мусора (.NET Garbage Collector) впоследствии очищает занятую память.

### Роль дизайнеров форм в Visual Studio при работе с пользовательскими компонентами

Visual Studio предоставляет мощный инструмент визуального проектирования — **Windows Forms Designer**. Роль дизайнера при работе с компонентами заключается в следующем:
- **Генерация кода инициализации:** Когда вы перетаскиваете компонент на форму или меняете его свойства в окне `Properties`, дизайнер автоматически записывает эти изменения в специальный файл `FormName.Designer.cs` (метод `InitializeComponent`).
- **Интеграция с Toolbox (Панелью элементов):** Скомпилированные пользовательские компоненты автоматически или через ручное добавление попадают в Панель элементов Visual Studio, превращаясь в такие же стандартные блоки, как кнопка или текстовое поле. Вы можете перетаскивать их мышкой, настраивать их свойства в таблице свойств в правой части экрана, не написав при этом ни строчки ручного кода инициализации.

### Разобранный пример: Архитектура приложения-опросника с компонентом авторизации

Чтобы закрепить теоретические основы компонентно-ориентированного подхода, рассмотрим подробное словесное описание архитектуры программного продукта.

#### 1. Условие задачи
Требуется спроектировать десктопное приложение «Корпоративный опросник» на платформе .NET 8 (Windows Forms). Приложение должно открывать главное окно опроса только после успешной проверки учетных данных сотрудника (ФИО и табельный номер). Поскольку блок авторизации должен вызываться как при входе в систему, так и при смене пользователя в настройках, требуется спроектировать этот блок в виде независимого пользовательского компонента, а не дублировать элементы на формах.

#### 2. Рисунок словами (структура интерфейса и компонентов)
Представим общую структуру приложения в виде древовидной схемы взаимосвязей:

```
[ Главная форма приложения (MainForm) ]
       │
       ├── Содержит экземпляр --> [ Компонент авторизации (AuthUserControl) ]
       │                              ├── Label ("Табельный номер:")
       │                              ├── TextBox (для ввода номера)
       │                              ├── Label ("ФИО сотрудника:")
       │                              ├── TextBox (для ввода ФИО)
       │                              └── Button ("Авторизоваться")
       │
       └── Содержит элементы --> [ Блок прохождения опроса ( QuestionnairePanel ) ]
```

#### 3. Ход рассуждений: почему проектируем именно так
- **Разделение ответственности:** Форма (`MainForm`) отвечает за общую логику жизненного цикла приложения (переключение экранов, сохранение результатов опроса в файл). Компонент авторизации (`AuthUserControl`) инкапсулирует всю работу с полями ввода данных сотрудника. Форма не должна знать, какие именно текстовые поля используются внутри компонента авторизации.
- **Использование контрактов (API компонента):** 
  - Компонент должен предоставить наружу **свойства** для чтения введенных данных (`EmployeeId` и `EmployeeName`).
  - Компонент должен объявить собственное **событие** `Authenticated`, которое сгенерируется в момент успешного нажатия внутренней кнопки «Авторизоваться».
- **Интеграция:** Главная форма подписывается на событие `Authenticated` компонента авторизации. Когда пользователь нажимает кнопку внутри компонента, компонент проверяет заполненность полей, генерирует событие, а главная форма переключает видимость интерфейсов: скрывает компонент авторизации и отображает вопросы опросника.

#### 4. Решение в общем виде (архитектурный набросок на C#)

Ниже представлен концептуальный код, иллюстрирующий описанную архитектуру взаимодействия клиента и компонента:

```csharp
// 1. Определение класса компонента авторизации
public class AuthUserControl : UserControl
{
    private TextBox txtId;
    private TextBox txtName;
    private Button btnLogin;

    // Публичное событие успешной авторизации
    public event EventHandler? Authenticated;

    // Публичные свойства для доступа к данным
    public string EmployeeId => txtId.Text.Trim();
    public string EmployeeName => txtName.Text.Trim();

    public AuthUserControl()
    {
        // Инициализация элементов управления внутри компонента
        txtId = new TextBox();
        txtName = new TextBox();
        btnLogin = new Button { Text = "Войти" };

        // Подписка на внутреннее событие нажатия кнопки
        btnLogin.Click += BtnLogin_Click;
    }

    private void BtnLogin_Click(object? sender, EventArgs e)
    {
        // Простейшая валидация внутри компонента
        if (!string.IsNullOrEmpty(EmployeeId) && !string.IsNullOrEmpty(EmployeeName))
        {
            // Генерация события для внешней формы
            Authenticated?.Invoke(this, EventArgs.Empty);
        }
        else
        {
            MessageBox.Show("Заполните все поля авторизации!");
        }
    }
}

// 2. Главная форма приложения, использующая компонент
public class MainForm : Form
{
    private AuthUserControl authControl;

    public MainForm()
    {
        authControl = new AuthUserControl();
        
        // Подписка главной формы на событие компонента
        authControl.Authenticated += AuthControl_Authenticated;
        
        // Добавление компонента на форму
        this.Controls.Add(authControl);
    }

    private void AuthControl_Authenticated(object? sender, EventArgs e)
    {
        // Получение данных через свойства компонента
        string id = authControl.EmployeeId;

        MessageBox.Show($"Добро пожаловать, {name} (Таб. № {id})!");
        
        // Переход к основному функционалу опросника
        authControl.Visible = false;
        // Здесь код открытия вопросов опросника...
    }
```

- **Изоляция:** Главная форма не обращается напрямую к приватным текстовым полям (`txtId`, `txtName`), что полностью защищает внутреннюю структуру компонента от внешнего вмешательства. Доступ к данным осуществляется исключительно через публичные свойства (`EmployeeId`, `EmployeeName`).
- **Связывание:** Взаимодействие построено на событиях (`Authenticated`), что соответствует стандартной паттерн-модели Windows Forms. Компонент ничего не знает о существовании `MainForm`, он лишь сигнализирует о факте успешного входа, что делает компонент универсальным для повторного использования в других проектах.

> **Ответ:** Архитектура приложения-опросника с использованием компонента авторизации (`AuthUserControl`) реализована на основе принципов компонентно-ориентированного подхода: компонент инкапсулирует элементы ввода и проверки данных, предоставляет внешней форме публичные свойства для считывания результатов и генерирует событие `Authenticated` при успешном входе, обеспечивая слабую связанность и высокую степень повторного использования кода.

## 2. Создание составных элементов управления (UserControl)

### Класс `UserControl` как основа составных элементов управления

В предыдущем разделе мы познакомились с теоретическими основами компонентно-ориентированного подхода и выяснили, что интерфейс `IComponent` и класс `Component` предоставляют базовую инфраструктуру для управления жизненным циклом и взаимодействия с дизайнером Visual Studio. Однако для создания визуальных составных элементов управления в Windows Forms на платформе .NET 8 используется специализированный базовый класс `System.Windows.Forms.UserControl`.

> **Определение.** `UserControl` — это составной визуальный элемент управления (контейнер), который объединяет несколько стандартных элементов управления (кнопки, текстовые поля, надписи и т. д.) в единый логический блок с собственным поведением, свойствами и событиями.

Класс `UserControl` является прямым наследником класса `ContainerControl`, который, в свою очередь, наследуется от `ScrollableControl` и базового класса всех визуальных элементов управления `Control`. Благодаря этой иерархии `UserControl` обладает следующими возможностями:
1. Способен содержать на своей внутренней поверхности другие элементы управления (область проектирования).
2. Поддерживает визуальное проектирование через встроенный дизайнер Visual Studio.
3. Имеет собственные размеры, координаты, шрифты и цвета фона.
4. Может быть легко добавлен в Панель элементов (Toolbox) и перенесен на любую форму точно так же, как обычная кнопка (`Button`) или текстовое поле (`TextBox`).

### Создание проекта и структура составного компонента

В современной среде разработки под .NET 8 (например, Visual Studio 2022 или JetBrains Rider) создание пользовательского элемента управления выполняется в рамках проекта типа *Windows Forms Class Library* (Библиотека классов Windows Forms) или в составе существующего проекта Windows Forms Application путем добавления нового элемента.

Рассмотрим по шагам создание проекта для нашего компонента:
1. Откройте Visual Studio и создайте новое решение или проект. Выберите шаблон **Windows Forms App** (для .NET 8) или **Windows Forms Class Library**.
2. В обозревателе решений (Solution Explorer) нажмите правой кнопкой мыши по проекту, выберите пункт меню **Add -> New Item...** (Добавить -> Новый элемент).
3. В открывшемся окне выберите шаблон **User Control (Windows Forms)** и задайте ему осмысленное имя, например, `LabeledTextBox.cs`.

После завершения этих действий среда создаст два файла:
- `LabeledTextBox.cs` — файл исходного кода на C#, содержащий класс компонента, разделенный с помощью ключевого слова `partial`.
- `LabeledTextBox.Designer.cs` — файл, автоматически генерируемый дизайнером Visual Studio, в котором инициализируются внутренние визуальные элементы управления.

### Проектирование внутренней структуры и инкапсуляция

Главная задача составного компонента — скрыть («инкапсулировать») внутреннее устройство от разработчика, который будет использовать этот компонент на форме. 

Представьте стандартную ситуацию: на форме авторизации или регистрации есть три поля ввода (логин, пароль, email), и у каждого слева должна стоять аккуратная подпись. Без компонента вам придется каждый раз вручную перетаскивать `Label`, выравнивать его по оси Y относительно `TextBox`, следить за отступами и писать однотипный код для получения текста. С помощью `UserControl` мы создадим единый блок, у которого снаружи будет видна только одна строка текста.

Рассмотрим внутреннее устройство нашего будущего компонента `LabeledTextBox`. Нам понадобятся два элемента:
1. `Label` (надпись для пояснения поля).
2. `TextBox` (поле для ввода пользовательских данных).

Чтобы внешняя форма не могла случайно удалить или повредить эти внутренние элементы (например, изменить их тип или перехватить не предназначенные для этого события), мы обязаны правильно настроить **модификаторы доступа**. В визуальных дизайнерах .NET по умолчанию создаваемые элементы имеют модификатор `private` или `internal`. Мы явно зафиксируем приватный доступ в коде инициализации.

### Создание публичных свойств компонента (Проксирование)

Поскольку внутренние элементы `Label` и `TextBox` скрыты от внешнего мира (`private`), внешней форме нужен способ взаимодействия с ними. Для этого используются **публичные свойства компонента**, которые «проксируют» (перенаправляют) запросы внутрь контрола.

Например, когда пользователь пишет `labeledTextBox1.Text = "Администратор";`, компонент должен перехватить это значение и передать его во внутреннее текстовое поле `textBoxInput.Text`, а также обновить текст метки при изменении заголовка.

Для гибкой настройки компонента прямо в окне свойств Visual Studio (**Properties Window**) используются специальные атрибуты из пространства имен `System.ComponentModel`:
- `[Category("CategoryName")]` — определяет категорию, в которой отобразится свойство в окне Properties (например, «Appearance», «Behavior», «Action»).
- `[Description("Описание")]` — выводит подсказку в нижней части окна Properties при выборе свойства.

### Полный код компонента `LabeledTextBox`

Ниже представлен полностью рабочий и компилируемый код класса `LabeledTextBox`, созданный для .NET 8 и C#. Сохраните этот код в файл `LabeledTextBox.cs`.

```csharp
AZP.04 / C# .NET 8 - Пользовательские элементы управления
using System;
using System.ComponentModel;
using System.Drawing;
using System.Windows.Forms;

namespace MyWinFormsApp
{
    // Класс компонента наследуется от UserControl
    public partial class LabeledTextBox : UserControl
    {
        // Внутренние элементы управления инкапсулированы (private)
        private Label labelTitle;
        private TextBox textBoxInput;

        public LabeledTextBox()
        {
            // Метод инициализации компонентов (обычно генерируется дизайнером)
            InitializeComponentCustom();
            
            // Устанавливаем начальные размеры компонента по умолчанию
            this.Size = new Size(300, 30);
        }

        // Ручная инициализация внутренних элементов для наглядности процесса
        private void InitializeComponentCustom()
        {
            this.labelTitle = new Label();
            this.textBoxInput = new TextBox();

            this.SuspendLayout();

            // Настройка метки (Label)
            this.labelTitle.AutoSize = true;
            this.labelTitle.Location = new Point(0, 6);
            this.labelTitle.Name = "labelTitle";
            this.labelTitle.Size = new Size(70, 15);
            this.labelTitle.Text = "Метка:";

            // Настройка текстового поля (TextBox)
            this.labelTitle.Location = new Point(0, 6);
            this.textBoxInput.Location = new Point(80, 3);
            this.textBoxInput.Name = "textBoxInput";
            this.textBoxInput.Size = new Size(215, 23);
            // Подписываемся на стандартное событие изменения текста во внутреннем поле,
            // чтобы проксировать его наружу, если потребуется
            this.textBoxInput.TextChanged += TextBoxInput_TextChanged;

            // Добавление элементов на поверхность UserControl
            this.Controls.Add(this.labelTitle);
            this.Controls.Add(this.textBoxInput);

            this.ResumeLayout(false);
            this.PerformLayout();
        }

        // Публичное свойство для настройки текста заголовка (метки)
        [Category("Appearance")]
        [Description("Текст заголовка, отображаемый слева от поля ввода.")]
        public string TitleText
        {
            get { return labelTitle.Text; }
            set { labelTitle.Text = value; }
        }

        // Публичное свойство для чтения и записи введенного пользователем текста
        [Category("Data")]
        [Description("Текст, введенный в поле ввода.")]
        public override string Text
        {
            get { return textBoxInput.Text; }
            set { textBoxInput.Text = value; }
        }

        // Публичное свойство для настройки ширины текстового поля
        [Category("Layout")]
        [Description("Ширина внутреннего текстового поля.")]
        public int InputWidth
        {
            get { return textBoxInput.Width; }
            set 
            { 
                textBoxInput.Width = value;
                // Автоматически корректируем общую ширину контрола
                this.Width = textBoxInput.Left + value + 5;
            }
        }

        // Событие, проксирующее изменение текста внутри текстового поля
        public event EventHandler InputTextChanged;

        private void TextBoxInput_TextChanged(object sender, EventArgs e)
        {
            // Вызываем внешние подписчики, передавая текущий объект как источник события
            InputTextChanged?.Invoke(this, e);
        }

        // Переопределение метода изменения размера для корректного позиционирования
        protected override void OnResize(EventArgs e)
        {
            base.OnResize(e);
            if (textBoxInput != null && labelTitle != null)
            {
                // Убедимся, что текстовое поле занимает оставшееся пространство
                int spacing = 10;
                textBoxInput.Location = new Point(labelTitle.Width + spacing, (this.Height - textBoxInput.Height) / 2);
                textBoxInput.Width = Math.Max(50, this.Width - textBoxInput.Left - 5);
            }
        }
    }
}
```

### Пошаговый разбор кода компонента

1. **Наследование от `UserControl`**: Строка `public partial class LabeledTextBox : UserControl` указывает компилятору, что наш класс является визуальным компонентом Windows Forms.
2. **Инкапсуляция**: Объявление `private Label labelTitle` и `private TextBox textBoxInput` гарантирует, что внешний код не сможет получить прямой доступ к элементам.
3. **Проксирование свойства `Text`**: Мы переопределили виртуальное свойство `Text` с помощью ключевого слова `override`. Когда внешняя форма запрашивает `labeledTextBox1.Text`, мы возвращаем значение `textBoxInput.Text`. Когда записывает — присваиваем в `textBoxInput.Text`. Это классический паттерн адаптера/прокси в графических интерфейсах.
4. **Атрибуты метаданных**: Атрибуты `[Category("Appearance")]` и `[Description("...")]` управляют поведением среды Visual Studio. Разработчик, кликнув по нашему компоненту в дизайнере, увидит эти свойства аккуратно сгруппированными на панели Properties с русскоязычными подсказками.
5. **Безопасный вызов события**: Строка `InputTextChanged?.Invoke(this, e);` проверяет, подписан ли кто-либо на событие (проверка на `null` с помощью оператора `?.`), и если да — оповещает внешнюю форму об изменении текста.

## 3. Разработка собственных событий в пользовательских элементах управления

### Необходимость генерации собственных событий из компонентов

При разработке составных элементов управления (`UserControl`) часто возникает задача: внутренние компоненты (например, кнопки, текстовые поля) изменяют своё состояние, и об этом нужно сообщить главной форме, на которой размещен наш контрол. 

Прямое обращение изнутри `UserControl` к главной форме нарушает принципы инкапсуляции и архитектурной независимости. Компонент не должен «знать» о существовании конкретной формы, в которую он будет вложен. В противном случае мы не сможем повторно использовать этот компонент в других проектах. 

Решением этой проблемы является **механизм событий**. Компонент генерирует (вызывает) событие при наступлении определенного действия (например, изменилось число, пользователь нажал на элемент, завершился ввод данных), а внешняя форма подписывается на это событие и реагирует на него, не вмешиваясь во внутреннее устройство компонента.

---

### Делегаты и класс EventArgs в .NET

В основе событий в C# лежат **делегаты** — типы данных, которые ссылаются на методы с определенной сигнатурой. Для стандартизации обработки событий в платформе .NET принято использовать универсальный делегат `EventHandler` или его обобщенную версию `EventHandler<TEventArgs>`.

Сигнатура стандартного обработчика событий в .NET выглядит следующим образом:
`void MethodName(object sender, EventArgs e)`

Разберем параметры этой сигнатуры:
1. `object sender` — ссылка на объект, который сгенерировал событие (источник события). Благодаря этому один и тот же метод-обработчик может обслуживать несколько разных элементов управления, определяя, кто именно прислал уведомление.
2. `EventArgs e` — объект, содержащий дополнительные данные события. Базовый класс `EventArgs` не содержит никаких данных и используется тогда, когда передавать сопутствующую информацию не нужно (передается пустой объект `EventArgs.Empty`).

---

### Создание кастомного класса данных события

Если помимо самого факта возникновения события нам нужно передать какие-то данные (например, новое значение счетчика), мы создаем собственный класс, наследуемый от `EventArgs`. По соглашению об именованиях в .NET, такой класс должен заканчиваться суффиксом `EventArgs`.

Рассмотрим создание класса для компонента `NumericCounter`, который будет хранить текущее числовое значение.

```csharp
using System;

namespace ControlLibrary
{
    // Класс для передачи измененного значения события
    public class ValueChangedEventArgs : EventArgs
    {
        // Публичное свойство только для чтения, хранящее новое значение
        public int NewValue { get; }

        // Конструктор класса данных события
        public ValueChangedEventArgs(int newValue)
        {
            NewValue = newValue;
        }
    }
}
```

Здесь свойство `NewValue` объявлено только с аксессором `get`, так как получатели события должны иметь возможность прочитать данные, но не должны иметь возможности их случайно или намеренно изменить во время транспортировки события.

---

### Объявление события в классе UserControl

Событие объявляется внутри класса `UserControl` с использованием ключевого слова `event` и указанием типа делегата. Для передачи наших пользовательских данных мы используем обобщенный делегат `EventHandler<ValueChangedEventArgs>`.

Посмотрим, как устроен класс составного компонента `NumericCounter`. Этот компонент состоит из уменьшающей кнопки (`btnMinus`), текстового поля для отображения числа (`txtValue`) и увеличивающей кнопки (`btnPlus`).

```csharp
using System;
using System.Windows.Forms;

namespace ControlLibrary
{
    public partial class NumericCounter : UserControl
    {
        private int _currentValue = 0;

        // Объявление собственного события ValueChanged
        public event EventHandler<ValueChangedEventArgs> ValueChanged;

        public NumericCounter()
        {
            // Метод инициализации визуальных элементов дизайнера
            InitializeComponent();
            
            // Установка начального значения в текстовое поле
            txtValue.Text = _currentValue.ToString();
        }

        // Публичное свойство для доступа к текущему значению снаружи
        public int Value
        {
            get => _currentValue;
            set
            {
                if (_currentValue != value)
                {
                    _currentValue = value;
                    txtValue.Text = _currentValue.ToString();
                    // Вызываем метод генерации события при программном изменении
                    OnValueChanged(new ValueChangedEventArgs(_currentValue));
                }
            }
        }
    }
}
```

### Безопасный вызов события с проверкой на null

Генерация события оформляется в виде защищенного виртуального метода с именем, начинающимся со слова `On` и совпадающим с именем события (`OnValueChanged`). Это стандартный паттерн проектирования в .NET, который позволяет производным классам переопределять логику вызова события или вызывать его изнутри.

```csharp
        // Виртуальный защищенный метод для вызова события
        protected virtual void OnValueChanged(ValueChangedEventArgs e)
        {
            // Безопасный вызов: проверяем, подписан ли кто-нибудь на событие (не равно ли оно null)
            // В C# 6.0 и выше используется удобный оператор с вопросительным знаком ?.
            ValueChanged?.Invoke(this, e);
        }
```

Проверка на `null` обязательна, так как если на событие `ValueChanged` не подписался ни один внешний обработчик, значение переменной события будет равно `null`. Попытка вызвать событие без проверки приведет к выбросу исключения `NullReferenceException`. Конструкция `ValueChanged?.Invoke(this, e)` проверяет наличие подписчиков и потокобезопасно вызывает делегат, передавая в качестве источника `this` (сам компонент), а в качестве аргументов — объект `ValueChangedEventArgs`.

Допишем логику нажатия на кнопки внутри нашего компонента `NumericCounter`:

```csharp
        private void btnPlus_Click(object sender, EventArgs e)
        {
            _currentValue++;
            txtValue.Text = _currentValue.ToString();
            
            // Генерируем событие, передавая новое значение
            OnValueChanged(new ValueChangedEventArgs(_currentValue));
        }

        private void btnMinus_Click(object sender, EventArgs e)
        {
            _currentValue--;
            txtValue.Text = _currentValue.ToString();
            
            // Генерируем событие, передавая новое значение
            OnValueChanged(new ValueChangedEventArgs(_currentValue));
        }
```

### Проверка и сложность

- **Единицы измерения и корректность:** Поскольку мы работаем в среде Windows Forms (.NET 8), все координаты и размеры измеряются в пикселях (`int`), а значения счетчика оперируют стандартными целыми числами (`int`). Ошибки переполнения при стандартных шагах инкремента/декремента маловероятны, однако при построении критически важных счетчиков рекомендуется использовать проверку границ (`Math.Clamp`).
- **Оценка сложности:** Генерация и вызов события выполняются за константное время $O(1)$ с точки зрения вычислений самого компонента. Суммарная сложность зависит от количества подписчиков на данное событие ($O(k)$, где $k$ — число методов, подписанных на событие). В рамках типичных оконных приложений это не оказывает заметного влияния на производительность.

## 4. Специализированные элементы управления на основе наследования

### Принцип расширения существующих контролов через наследование

В предыдущих разделах мы рассмотрели, как объединять готовые элементы управления в единые блоки с помощью контейнера `UserControl`. Однако часто возникает задача не объединить несколько контролов, а изменить или дополнить поведение какого-то одного существующего элемента управления — например, стандартного текстового поля `TextBox`, кнопки `Button` или панели `Panel`. 

Для этого в объектно-ориентированном программировании и Windows Forms используется механизм **наследования**. Вместо того чтобы каждый раз писать один и тот же код обработки событий на каждой форме, мы можем создать новый класс, который унаследует всю функциональность стандартного контрола и добавит к ней новую логику.

> **Определение.** Наследование элементов управления — это создание нового класса-потомка на основе существующего класса элемента управления (родителя), при котором потомок автоматически получает все свойства, методы и события родителя, а также может переопределять их поведение или добавлять новые члены.

В языке C# синтаксис объявления такого класса выглядит следующим образом:

```csharp
public class OnlyDigitsTextBox : TextBox
{
    // Тело нового специализированного элемента управления
}
```

Когда мы создаем класс `OnlyDigitsTextBox`, унаследованный от `TextBox`, наш новый класс сразу умеет отображать текст, обрабатывать фокус ввода, выделять символы и взаимодействовать с операционной системой так же, как обычный `TextBox`. Нам не нужно заново реализовывать работу с буфером обмена или отрисовкой текста — мы просто добавляем точечные ограничения или визуальные эффекты.

---

### Переопределение виртуальных методов и жизненный цикл ввода

Чтобы перехватить действия пользователя (например, нажатие клавиши, клик мышкой или перерисовку компонента), стандартные классы Windows Forms предоставляют специальные защищенные (`protected virtual`) методы. Префикс `On` в названии таких методов указывает на то, что метод отвечает за генерацию соответствующего события.

Например, за нажатие клавиши на клавиатуре отвечает виртуальный метод `OnKeyPress(KeyPressEventArgs e)`. Когда пользователь нажимает клавишу, система вызывает этот метод у элемента управления. Если мы хотим изменить стандартную реакцию на нажатие, мы должны создать в своем унаследованном классе метод с ключевым словом `override`.

Важное правило объектно-ориентированного программирования при переопределении методов — не забывать вызывать базовую реализацию через ключевое слово `base`, если это необходимо для нормальной работы компонента:

```csharp
protected override void OnKeyPress(KeyPressEventArgs e)
{
    base.OnKeyPress(e); // Вызываем базовую логику TextBox
    // Здесь добавляем нашу кастомную логику
}
```

Если мы вызовем `base.OnKeyPress(e)` до фильтрации символа, то символ сначала отобразится, а потом обработается. Поэтому для фильтрации ввода логику нужно встраивать до вызова базового метода или полностью управлять условием его вызова.

---

### Фильтрация пользовательского ввода на лету: разбор примера

Рассмотрим разработку специализированного элемента управления `OnlyDigitsTextBox`. Требуется создать текстовое поле, в которое пользователь может вводить только цифры, а также управляющие клавиши (например, клавишу удаления `BackSpace`). Все остальные символы (буквы, знаки препинания) должны блокироваться на лету, то есть не появляться в поле ввода вообще.

#### Словесное описание визуального представления
На форме располагается стандартное на вид текстовое поле. Когда пользователь пытается ввести латинскую букву «a» или знак «+», поле никак не реагирует, текст внутри не меняется. При нажатии цифровых клавиш (например, «5») символ мгновенно отображается в позиции курсора.

#### Ход рассуждений и проектирование
1. Создаем класс `OnlyDigitsTextBox`, наследующий от `System.Windows.Forms.TextBox`.
2. Переопределяем метод `OnKeyPress(KeyPressEventArgs e)`. Класс `KeyPressEventArgs` содержит свойство `e.KeyChar` (символ, который пользователь пытается ввести) и свойство `e.Handled` (логический флаг, показывающий, обработано ли событие).
3. Если `e.Handled` установить в значение `true`, система понимает, что событие нажатия клавиши полностью обработано нашим кодом, и стандартный механизм `TextBox` не будет добавлять этот символ в строку.
4. Проверяем символ `e.KeyChar`: является ли он цифрой (`char.IsDigit(e.KeyChar)`) или управляющей клавишей (`char.IsControl(e.KeyChar)`). Управляющие клавиши (такие как `BackSpace`) обязательно нужно разрешать, иначе пользователь не сможет стереть ошибочно введенную цифру.
5. Если символ не удовлетворяет условию, устанавливаем `e.Handled = true`.

#### Полный исходный код компонента `OnlyDigitsTextBox`

```csharp
using System.Windows.Forms;

namespace CustomControlsApp
{
    // Специализированное текстовое поле, принимающее только цифры
    public class OnlyDigitsTextBox : TextBox
    {
        protected override void OnKeyPress(KeyPressEventArgs e)
        {
            // Всегда вызываем базовый метод для корректной работы системных механизмов
            base.OnKeyPress(e);

            // Проверяем, является ли символ цифрой или управляющим символом (например, Backspace)
            bool isDigit = char.IsDigit(e.KeyChar);
            bool isControl = char.IsControl(e.KeyChar);

            // Если символ не цифра и не управляющий элемент — отменяем ввод
            if (!isDigit && !isControl)
            {
                e.Handled = true; // Блокируем символ
                System.Media.SystemSounds.Beep.Play(); // Опционально: звуковой сигнал ошибки
            }
        }
    }
}
```

#### Пояснение по строкам кода
- `public class OnlyDigitsTextBox : TextBox`: объявление класса-потомка, расширяющего стандартный `TextBox`.
- `protected override void OnKeyPress(KeyPressEventArgs e)`: переопределение защищенного метода обработки нажатия символа.
- `char.IsDigit(e.KeyChar)`: встроенный метод .NET, возвращающий `true`, если символ является цифрой от '0' до '9'.
- `char.IsControl(e.KeyChar)`: проверяет, является ли символ управляющим (код ASCII от 0 до 31, включая `BackSpace`, `Delete`, табуляцию). Символы вроде `Enter` или `Escape` также попадают сюда, но для однострочного `TextBox` критически важен именно `BackSpace`.
- `e.Handled = true`: отмена дальнейшей обработки введенного символа операционной системой и визуальным компонентом.
- `System.Media.SystemSounds.Beep.Play()`: воспроизведение короткого системного звука при попытке ввести запрещенный символ.

### Добавление визуальных эффектов через метод OnPaint и класс Graphics

Некоторые элементы управления (например, `Panel`, `PictureBox` или пользовательские кнопки) поддерживают кастомную отрисовку с помощью метода `OnPaint` и графического контекста `Graphics`. 

Когда компонент перерисовывается (например, при изменении размера окна или вызове метода `Invalidate()`), система вызывает метод `OnPaint(PaintEventArgs e)`. Внутри объекта `e.Graphics` содержатся инструменты для рисования линий, фигур, текста и заливки кистями.

Для создания плавных визуальных эффектов без мерцания (мигания экрана при перерисовке) критически важно использовать двойную буферизацию.

### Управление стилями контрола и двойная буферизация

По умолчанию некоторые стандартные элементы управления не используют двойную буферизацию вывода графики, из-за чего при частых обновлениях или сложных анимациях изображение может заметно мерцать. 

В .NET для управления низкоуровневым поведением контролов предусмотрен защищенный метод `SetStyle`. Вызов этого метода выполняется в конструкторе унаследованного класса.

Пример включения двойной буферизации:

```csharp
public class AnimatedButton : Button
{
    public AnimatedButton()
    {
        // Включаем двойную буферизацию и оптимизацию перерисовки
        this.SetStyle(ControlStyles.AllPaintingInWmPaint | 
                      ControlStyles.UserPaint | 
                      ControlStyles.OptimizedDoubleBuffer, true);
        this.UpdateStyles();
    }
}
```

Описание флагов `ControlStyles`:
- `UserPaint`: указывает системе, что элемент управления отрисовывается разработчиком вручную, а не операционной системой.
- `AllPaintingInWmPaint`: отключает стандартное стирание фона операционной системой перед отрисовкой, что полностью устраняет мерцание.
- `OptimizedDoubleBuffer`: включает двойную буферизацию (все графические операции сначала выполняются в буфере в памяти, а на экран выводятся готовой картинкой).

### Особенности работы конструкторов в унаследованных элементах управления

При проектировании унаследованных контролов важно помнить о порядке вызова конструкторов. Конструктор базового класса (`TextBox`, `Button`) всегда исполняется **до** того, как начнет выполняться тело конструктора вашего класса-потомка.

Если ваш кастомный элемент управления требует инициализации каких-то внутренних полей или изменения свойств по умолчанию, это делается внутри собственного конструктора класса-потомка:

```csharp
public class CustomPanel : Panel
{
    private int _cornerRadius;

    public int CornerRadius
    {
        get => _cornerRadius;
        set
        {
            _cornerRadius = value;
            this.Invalidate(); // Принудительно вызываем перерисовку при изменении свойства
        }
    }

    public CustomPanel()
    {
        // Настройка параметров по умолчанию при создании объекта
        _cornerRadius = 10;
        this.BackColor = System.Drawing.Color.LightGray;
        
        // Включаем поддержку пользовательской отрисовки
        this.SetStyle(ControlStyles.AllPaintingInWmPaint | 
                      ControlStyles.UserPaint | 
                      ControlStyles.OptimizedDoubleBuffer, true);
    }
}
```

## 5. Интеграция компонентов и комплексный пример приложения

### Сборка библиотеки компонентов в .NET 8 и межпроектные зависимости

Когда вы разрабатываете несколько пользовательских элементов управления (например, составной `UserControl` или специализированный контрол на базе наследования), держать их прямо в исходном коде основного приложения становится неудобно. Если проект вырастает или эти же элементы планируется использовать в других программах, их выносят в отдельный проект — библиотеку классов (**Class Library**).

В платформе .NET 8 создание библиотеки компонентов для Windows Forms ничем не отличается от создания обычной библиотеки классов, за исключением того, что в файле проекта необходимо явно указать поддержку Windows Forms. Давайте разберем этот процесс по шагам.

1. **Создание проекта библиотеки.** В Visual Studio или через командную строку `dotnet new classlib -n UserControlsLibrary` создается проект типа «Библиотека классов».
2. **Настройка файла проекта (`.csproj`).** Чтобы проект «видел» пространство имен `System.Windows.Forms` и элементы управления, в файл проекта необходимо добавить специальный тег:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net8.0-windows</TargetFramework>
    <UseWindowsForms>true</UseWindowsForms>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

> **Важно.** Обратите внимание на `net8.0-windows` вместо простого `net8.0` и включенный флаг `<UseWindowsForms>true</UseWindowsForms>`. Без этого компилятор не найдет базовые классы `Control`, `UserControl` и `TextBox`.

3. **Добавление ссылки между проектами (Project Reference).** Чтобы ваше основное оконное приложение могло использовать компоненты из созданной библиотеки, нужно связать два проекта в рамках одного решения (**Solution**). В Visual Studio это делается через контекстное меню проекта приложения: пункт *Add -> Project Reference...*, после чего в открывшемся окне отмечается галочкой проект библиотеки компонентов. В файле проекта приложения (`.csproj`) появится запись:

```xml
<ItemGroup>
  <ProjectReference Include="..\UserControlsLibrary\UserControlsLibrary.csproj" />
</ItemGroup>
```

После успешной сборки решения (`Ctrl + Shift + B`) созданные вами кастомные элементы управления автоматически регистрируются средой Visual Studio и появляются на панели элементов (**Toolbox**). Вы можете перетаскивать их мышкой прямо на поверхность формы точно так же, как стандартные кнопки и текстовые поля.

### Архитектура сложного оконного приложения с пользовательскими компонентами

При проектировании интерфейсов средней и высокой сложности критически важно разделять ответственность. Главная форма приложения не должна содержать громоздкую логику валидации каждого поля ввода — она выступает в роли координатора (контейнера), который собирает данные от подчиненных компонентов, проверяет их целостность и выполняет целевое действие (например, сохранение в базу данных или отправку на сервер).

Для демонстрации построения такого приложения рассмотрим полный сквозной пример. Мы создадим форму регистрации пользователя, которая объединяет три ранее разработанных компонента:
1. `LabeledTextBox` — составной контрол (надпись + текстовое поле) для ввода имени.
2. `OnlyDigitsTextBox` — специализированный контрол (наследник `TextBox`), разрешающий ввод только цифр, для указания возраста.
3. `NumericCounter` — составной контрол с кнопками «плюс» и «минус» и событием изменения значения, для указания количества баллов.

Ниже приведен полный программный код всех трех компонентов (в сокращенном виде для понимания их публичных контрактов) и код главной формы, которая связывает их воедино.

```csharp
// 2. Компонент OnlyDigitsTextBox (наследник TextBox)
using System.Windows.Forms;

namespace UserControlsLibrary
{
    public class OnlyDigitsTextBox : TextBox
    {
        protected override void OnKeyPress(KeyPressEventArgs e)
        {
            base.OnKeyPress(e);

            // Разрешаем цифры и управляющие клавиши (например, Backspace)
            if (!char.IsControl(e.KeyChar) && !char.IsDigit(e.KeyChar))
            {
                e.Handled = true; // Отменяем ввод символа
            }
        }
    }
}
```

```csharp
// 3. Компонент NumericCounter (составной контрол с собственным событием)
using System;
using System.Windows.Forms;

namespace UserControlsLibrary
{
    public class NumericCounter : UserControl
    {
        private Button btnMinus;
        private Button btnPlus;
        private Label lblValue;
        private int currentValue = 0;

        // Объявление собственного события изменения значения
        public event EventHandler<ValueChangedEventArgs> ValueChanged;

        public NumericCounter()
        {
            InitializeComponentCustom();
        }

        private void InitializeComponentCustom()
        {
            this.btnMinus = new Button { Text = "-", Width = 30, Dock = DockStyle.Left };
            this.btnPlus = new Button { Text = "+", Width = 30, Dock = DockStyle.Right };
            this.lblValue = new Label { Text = "0", TextAlign = System.Drawing.ContentAlignment.MiddleCenter, Dock = DockStyle.Fill };

            this.btnMinus.Click += BtnMinus_Click;
            this.btnPlus.Click += BtnPlus_Click;

            this.Controls.Add(this.lblValue);
            this.Controls.Add(this.btnPlus);
            this.Controls.Add(this.btnMinus);
            this.Height = 30;
            this.Width = 120;
        }

        private void BtnMinus_Click(object? sender, EventArgs e)
        {
            if (currentValue > 0)
            {
                currentValue--;
                UpdateValue();
            }
        }

        private void BtnPlus_Click(object? sender, EventArgs e)
        {
            currentValue++;
            UpdateValue();
        }

        private void UpdateValue()
        {
            lblValue.Text = currentValue.ToString();
            // Безопасный вызов события
            ValueChanged?.Invoke(this, new ValueChangedEventArgs(currentValue));
        }

        public int Value => currentValue;
    }

    // Кастомный класс аргументов события
    public class ValueChangedEventArgs : EventArgs
    {
        public int NewValue { get; }
        public ValueChangedEventArgs(int newValue)
        {
            NewValue = newValue;
        }
    }
}
```

### Комплексный пример: Разработка формы регистрации

Теперь соберем все компоненты на главной форме приложения (`MainForm`). Форма содержит три наших кастомных контрола, кнопку подтверждения регистрации и многострочное текстовое поле для вывода результатов логирования и статуса валидации.

```csharp
using System;
using System.Windows.Forms;
using UserControlsLibrary;

namespace RegistrationApp
{
    public partial class MainForm : Form
    {
        private LabeledTextBox txtBoxName;
        private OnlyDigitsTextBox txtBoxAge;
        private NumericCounter counterPoints;
        private Button btnSubmit;
        private TextBox txtBoxLog;

        public MainForm()
        {
            InitializeComponent();
            InitializeCustomControls();
        }

        private void InitializeCustomControls()
        {
            this.Text = "Регистрация пользователя";
            this.Width = 400;
            this.Height = 450;

            // 1. Инициализация компонента имени
            txtBoxName = new LabeledTextBox
            {
                Title = "Имя пользователя:",
                Top = 20,
                Left = 20,
                Width = 340
            };

            // 2. Инициализация компонента возраста (надпись + унаследованный TextBox)
            var lblAge = new Label { Text = "Возраст (только цифры):", Top = 90, Left = 20, Width = 340 };
            txtBoxAge = new OnlyDigitsTextBox
            {
                Top = 115,
                Left = 20,
                Width = 340
            };

            // 3. Инициализация счетчика баллов
            var lblPointsTitle = new Label { Text = "Начальные баллы:", Top = 160, Left = 20, Width = 150 };
            counterPoints = new NumericCounter
            {
                Top = 155,
                Left = 180
            };
            // Подписка на собственное событие компонента
            counterPoints.ValueChanged += CounterPoints_ValueChanged;

            // 4. Кнопка отправки формы
            btnSubmit = new Button
            {
                Text = "Зарегистрировать",
                Top = 210,
                Left = 20,
                Width = 340,
                Height = 35
            };
            btnSubmit.Click += BtnSubmit_Click;

            // 5. Поле логов / результатов
            txtBoxLog = new TextBox
            {
                Multiline = true,
                ReadOnly = true,
                Top = 260,
                Left = 20,
                Width = 340,
                Height = 120
            };

            // Добавление элементов на форму
            this.Controls.Add(txtBoxName);
            this.Controls.Add(lblAge);
            this.Controls.Add(txtBoxAge);
            this.Controls.Add(lblPointsTitle);
            this.Controls.Add(counterPoints);
            this.Controls.Add(btnSubmit);
            this.Controls.Add(txtBoxLog);
        }

        private void CounterPoints_ValueChanged(object? sender, ValueChangedEventArgs e)
        {
            // Обработка изменения значения счетчика в реальном времени
            txtBoxLog.AppendText($"[Событие] Количество баллов изменено на: {e.NewValue}\r\n");
        }

        private void BtnSubmit_Click(object? sender, EventArgs e)
        {
            // Комплексная валидация всей формы
            string name = txtBoxName.Text.Trim();
            string ageStr = txtBoxAge.Text.Trim();

            if (string.IsNullOrEmpty(name))
            {
                MessageBox.Show("Поле имени не должно быть пустым!", "Ошибка валидации", MessageBoxButtons.OK, MessageBoxIcon.Warning);
                txtBoxName.Focus();
                return;
            }

            if (string.IsNullOrEmpty(ageStr) || !int.TryParse(ageStr, out int age) || age <= 0 || age > 120)
            {
                MessageBox.Show("Введите корректный возраст (от 1 до 120)!", "Ошибка валидации", MessageBoxButtons.OK, MessageBoxIcon.Warning);
                txtBoxAge.Focus();
                return;
            }

            int points = counterPoints.Value;

            // Успешная валидация, вывод итоговых данных
            txtBoxLog.AppendText("--- Успешная регистрация ---\r\n");
            txtBoxLog.AppendText($"Имя: {name}\r\n");
            txtBoxLog.AppendText($"Возраст: {age}\r\n");
            txtBoxLog.AppendText($"Итоговые баллы: {points}\r\n");
            txtBoxLog.AppendText("-----------------------------\r\n");
        }
    }
}
```

### Анализ кода, обработка ошибок и производительность

При разработке масштабируемых интерфейсов с использованием пользовательских компонентов необходимо учитывать следующие инженерные аспекты:

1. **Инкапсуляция валидации.** Каждый компонент отвечает за проверку данных в рамках своей зоны ответственности (например, `OnlyDigitsTextBox` физически блокирует ввод недопустимых символов на уровне метода `OnKeyPress`). Однако общая бизнес-логика (например, обязательность заполнения имени или проверка допустимого диапазона возраста) проверяется на уровне главной формы перед отправкой данных.
2. **Управление памятью и подписками на события.** Когда вы подписываетесь на события (`+=`) динамически создаваемых компонентов, следите за тем, чтобы не возникало утечек памяти (Memory Leaks). Если контрол удаляется с формы (`Controls.Remove`), но ссылка на него остается в обработчике событий родительского объекта, сборщик мусора (.NET GC) не сможет выгрузить его из памяти. Всегда отписывайтесь от событий (`-=`), если компонент уничтожается динамически.
3. **Оценка производительности.** Создание нескольких десятков или сотен кастомных компонентов на одной форме может привести к задержкам при отрисовке (лагам интерфейса). Это связано с тем, что каждый `UserControl` создает собственный контекст окна и дерево вложенных элементов управления. Если вам требуется отобразить однотипные данные в больших объемах (например, таблица из 1000 строк), вместо создания тысячи `UserControl` используйте встроенный высокопроизводительный элемент `DataGridView` или выполняйте виртуализацию отрисовки.

### Вопросы для самопроверки и лабораторный практикум

1. В чем главное отличие между подключением сторонней библиотеки классов через `Project Reference` и добавлением исходного кода контрола прямо в проект приложения?
2. Почему попытка изменить свойство `Text` внутреннего текстового поля внутри `UserControl` напрямую из внешней формы нарушает принцип инкапсуляции? Как правильно решить эту проблему?
3. Какую роль играет метод `OnKeyPress` при создании специализированных элементов управления на основе наследования?

> **Ответ:** При вызове события без проверки на `null` в случае отсутствия подписчиков (если ни один класс не подписался на данное событие, его значение равно `null`) приложение выбросит исключение типа `NullReferenceException` прямо во время работы программы. ### Полный разобранный пример: Специализированная панель с рамкой и градиентным фоном

Создадим сложный специализированный элемент управления на основе `DoubleBufferedPanel` — `GradientCardPanel`. Этот компонент будет представлять собой карточку для интерфейса с закругленной рамкой и красивой градиентной заливкой фона.

#### 1. Условие задачи
Разработать специализированный визуальный компонент `GradientCardPanel`, наследуемый от нашей оптимизированной панели. Компонент должен позволять задавать два цвета градиента (`Color1` и `Color2`) через окно свойств Visual Studio, а также автоматически перерисовывать плавный переход цвета при изменении размеров панели.

#### 2. Рисунок словами (что изображено, куда направлено)
```text
+-------------------------------------------------------+
|  [ GradientCardPanel ]                                |
|  Верхний левый угол (Color1)                          |
|    \                                                  |
|     \ (Плавный диагональный цветовой переход)         |
|      \                                                |
|                        Нижний правый угол (Color2)    |
+-------------------------------------------------------+
```

#### 3. Ход рассуждений (почему делаем именно так)
- Нам нужен компонент-контейнер, поэтому наследуемся от `Panel` (а точнее, от нашей `DoubleBufferedPanel`).
- Для отрисовки градиента переопределим метод `OnPaint(PaintEventArgs e)`.
- Внутри `OnPaint` используем системный класс `System.Drawing.Drawing2D.LinearGradientBrush`, который строит плавный переход между двумя цветами под заданным углом.
- Чтобы компонент корректно реагировал на изменение размеров и не «плыл», добавим вызов метода `this.Invalidate()` в переопределенном методе `OnResize`, чтобы при каждом изменении размера панель запрашивала принудительную перерисовку.

#### 4. Полный код компонента `GradientCardPanel`

```csharp
using System;
using System.Drawing;
using System.Drawing.Drawing2D;
using System.ComponentModel;
using System.Windows.Forms;

namespace CustomControlsApp
{
    public class GradientCardPanel : Panel
    {
        private Color _color1 = Color.FromArgb(70, 130, 180); // Стальной синий
        private Color _color2 = Color.FromArgb(25, 25, 112);   // Темно-синий
        private float _angle = 45.0f;                         // Угол наклона градиента

        public GradientCardPanel()
        {
            // Включаем двойную буферизацию для устранения мерцания
            this.SetStyle(ControlStyles.AllPaintingInWmPaint | 
                          ControlStyles.UserPaint | 
                          ControlStyles.OptimizedDoubleBuffer, true);
            this.UpdateStyles();

            // Задаем размеры по умолчанию
            this.Size = new Size(250, 150);
        }

        [Category("Appearance")]
        [Description("Первый цвет градиентной заливки.")]
        public Color Color1
        {
            get => _color1;
            set { _color1 = value; this.Invalidate(); } // Перерисовка при изменении
        }

        [Category("Appearance")]
        [Description("Второй цвет градиентной заливки.")]
        public Color Color2
        {
            get => _color2;
            set { _color2 = value; this.Invalidate(); }
        }

        [Category("Appearance")]
        [Description("Угол наклона градиента в градусах.")]
        public float GradientAngle
        {
            get => _angle;
            set { _angle = value; this.Invalidate(); }
        }

        // Переопределение метода отрисовки панели
        protected override void OnPaint(PaintEventArgs e)
        {
            base.OnPaint(e);

            // Получаем графический контекст для рисования
            Graphics g = e.Graphics;
            g.SmoothingMode = SmoothingMode.AntiAlias;

            // Создаем прямоугольник области рисования по размерам панели
            Rectangle rect = new Rectangle(0, 0, this.Width, this.Height);

            // Если размеры нулевые, рисовать нет смысла
            if (rect.Width <= 0 || rect.Height <= 0) return;

            // Создаем кисть для линейного градиента
            using (LinearGradientBrush brush = new LinearGradientBrush(rect, _color1, _color2, _angle))
            {
                // Заливаем всю поверхность панели градиентом
                g.FillRectangle(brush, rect);
            }

            // Опционально: рисуем аккуратную внутреннюю рамку карточки
            using (Pen borderPen = new Pen(Color.FromArgb(100, Color.White), 2))
            {
                g.DrawRectangle(borderPen, 1, 1, this.Width - 3, this.Height - 3);
            }
        }

        // Переопределение изменения размера для корректного обновления
        protected override void OnResize(EventArgs e)
        {
            base.OnResize(e);
            this.Invalidate(); // Принудительно вызываем OnPaint при изменении размеров
        }
    }
}
```

#### 5. Проверка и вычисления
- **Единицы измерения**: Координаты (`Rectangle`), толщина рамки (`2`) и размеры измеряются в целых пикселях (`int`). Угол наклона градиента измеряется в градусах с плавающей точкой (`float`).
- **Правдоподобность**: Использование блока `using` для `LinearGradientBrush` и `Pen` гарантирует незамедлительное освобождение неуправляемых графических ресурсов операционной системы сразу после завершения отрисовки кадра, что предотвращает утечки памяти в процессе работы приложения.
- **Оценка сложности**: Отрисовка градиента силами графического ускорителя и GDI+ выполняется за время $O(N)$, где $N$ — количество пикселей внутри прямоугольника панели. На современных компьютерах `.NET 8` эта операция занимает доли миллисекунды.

> **Ответ:** Разработан специализированный элемент управления на основе наследования от `Panel` с двойной буферизацией (`GradientCardPanel`), реализующий кастомизированную градиентную заливку фона с настраиваемыми цветами и углом наклона через переопределение метода `OnPaint`.

## Типичные ошибки

1. **Прямой доступ к приватным элементам составного компонента из внешней формы.**
   * *Почему возникает:* Разработчик пытается написать что-то вроде `labeledTextBox1.textBoxInput.Text = "123"`, забывая про инкапсуляцию.
   * *Как избежать:* Проектировать публичные свойства в самом классе `UserControl` (проксирование), через которые и производить чтение/запись данных.
   * *Мини-пример ошибки:* `myControl.internalTextBox.Text = "test";` (вызовет ошибку компиляции из-за модификатора доступа `private`).

2. **Забытая проверка на `null` при вызове собственного события.**
   * *Почему возникает:* Разработчик вызывает событие напрямую `ValueChanged(this, e);` без предварительной проверки наличия подписчиков.
   * *Как избежать:* Всегда использовать безопасный вызов с вопросительным знаком: `ValueChanged?.Invoke(this, e);`.
   * *Мини-пример ошибки:* Если на событие никто не подписался, вызов `ValueChanged(this, e)` приведет к аварийному завершению программы (`NullReferenceException`).

3. **Отсутствие вызова `base.OnKeyPress` при переопределении метода ввода.**
   * *Почему возникает:* При создании специализированного контрола (наследника `TextBox`) разработчик переопределяет `OnKeyPress` и забывает вызвать `base.OnKeyPress(e)`.
   * *Как избежать:* Всегда в первой строке переопределенного метода вызывать базовую реализацию, если не требуется полностью переписать низкоуровневую логику работы контрола.
   * *Мини-пример ошибки:* `protected override void OnKeyPress(KeyPressEventArgs e) { /* забыли base */ }` приведет к тому, что стандартные символы перестанут обрабатываться системой вообще.

4. **Отсутствие двойной буферизации при кастомной отрисовке через `OnPaint`.**
   * *Почему возникает:* Разработчик рисует сложный градиент или анимацию без включения двойной буферизации, из-за чего компонент сильно мерцает при перерисовке.
   * *Как избежать:* В конструкторе панелей или контролов с кастомной графикой всегда вызывать `this.SetStyle(ControlStyles.OptimizedDoubleBuffer | ControlStyles.AllPaintingInWmPaint, true);`.

5. **Утечки графических ресурсов GDI+ (кисти, перья).**
   * *Почему возникают:* Создание объектов `Brush` или `Pen` внутри метода `OnPaint` без последующего освобождения памяти.
   * *Как избежать:* Использовать конструкцию `using` для всех объектов, реализующих интерфейс `IDisposable` (например, `using (Pen p = new Pen(Color.Red)) { ... }`).
   * *Мини-пример ошибки:* `Pen p = new Pen(Color.Black); g.DrawRectangle(p, ...);` без вызова `p.Dispose()` со временем приводит к исчерпанию системных дескрипторов GDI.

6. **Забытый вызов `this.Invalidate()` при изменении свойств, влияющих на внешний вид.**
   * *Почему возникает:* Разработчик меняет цвет или параметр градиента у кастомного компонента через свойство `set`, но на экране ничего не меняется.
   * *Как избежать:* В блоке `set` любого визуального свойства обязательно вызывать метод `this.Invalidate()`, чтобы принудительно инициировать перерисовку компонента.

7. **Некорректная обработка управляющих клавиш при фильтрации ввода.**
   * *Почему возникает:* При создании текстового поля только для цифр разработчик проверяет только `char.IsDigit`, забывая разрешить клавишу `BackSpace`.
   * *Как избежать:* Всегда разрешать управляющие символы через `char.IsControl(e.KeyChar)` вместе с проверкой цифр.

2. **Задача 2 (События в компоненте).** Разработайте составной компонент `PasswordStrengthMeter`, содержащий поле ввода пароля и прогресс-бар (`ProgressBar`). При изменении текста во внутреннем поле компонент должен вычислять сложность пароля (длина >= 8 символов) и генерировать собственное событие `StrengthChanged` с пользовательским классом аргументов, передающим уровень сложности в процентах (0, 50 или 100).
3. **Задача 3 (Наследование и фильтрация ввода).** Создайте специализированный класс текстового поля `AlphaOnlyTextBox` путем наследования от `TextBox`, который разрешает ввод только букв латинского и русского алфавитов, а также пробелов. Все цифры и спецсимволы должны блокироваться на лету с установкой `e.Handled = true`.
4. **Задача 4 (Наследование и кастомная отрисовка).** Разработайте специализированный элемент управления `RoundedButton`, унаследованный от обычной кнопки (`Button`). Переопределите метод отрисовки `OnPaint` так, чтобы кнопка имела скругленные углы радиусом 15 пикселей и меняла цвет заливки при наведении курсора мыши.
5. **Задача 5 (Комплексный компонент).** Создайте компонент `TimeInputControl`, объединяющий два поля ввода: одно для часов (от 0 до 23), другое для минут (от 0 до 59). Добавьте публичное свойство `TimeSpan Value`, возвращающее выбранное время, и сделайте валидацию: если пользователь вводит неверное число, поле окрашивается в красный цвет.
6. **Задача 6 (Специализированная панель).** Создайте специализированную панель `DashedBorderPanel`, унаследованную от `DoubleBufferedPanel`. Панель должна при отрисовке через `OnPaint` выводить по всему периметру красивую пунктирную рамку заданного цвета и толщины, которые настраиваются через публичные свойства панели.

---

## Ответы к задачам

1. **Ответ к задаче 1:** Класс `FullNameInput : UserControl` содержит три поля ввода и возвращает через свойство `FullName` строку вида `"Фамилия И. О."` с корректной обработкой пустых инициалов.
2. **Ответ к задаче 2:** Класс `PasswordStrengthMeter` содержит событие `StrengthChanged`, передающее через аргументы `PasswordStrengthEventArgs` уровень сложности пароля в процентах (0, 50 или 100).
3. **Ответ к задаче 3:** Класс `AlphaOnlyTextBox` переопределяет метод `OnKeyPress`, блокируя цифры и спецсимволы посредством установки `e.Handled = true`.
4. **Ответ к задаче 4:** Класс `RoundedButton` использует `GraphicsPath` для отрисовки скругленных углов радиусом 15 пикселей и изменяет цвет заливки при наведении курсора мыши.
5. **Ответ к задаче 5:** Компонент `TimeInputControl` валидирует диапазоны часов (0-23) и минут (0-59), окрашивая фон в `Color.MistyRose` при некорректном вводе и возвращая значение `TimeSpan`.
6. **Ответ к задаче 6:** Класс `DashedBorderPanel` переопределяет метод `OnPaint`, используя `Pen` со свойством `DashStyle = DashStyle.Dash` для отрисовки пунктирной рамки заданного цвета и толщины.
