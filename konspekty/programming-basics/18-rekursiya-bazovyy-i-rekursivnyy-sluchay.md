## Понятие рекурсии и два обязательных условия её работы

### Сущность рекурсии и её место в программировании

В программировании и алгоритмизации под **рекурсией** (от латинского *recursio* — возвращение) понимают такой способ организации вычислительного процесса, при котором метод (функция) в ходе своего выполнения обращается сам к себе. 

> **Определение.** Рекурсия — это метод решения вычислительной задачи, при котором исходная задача разбивается на одну или несколько более мелких подзадач того же типа, для решения которых вызывается тот же самый метод.

Чтобы понять эту концепцию не с технической, а с концептуальной стороны, обратимся к аналогии из реального мира. Представьте, что вы стоите в огромном зрительном зале кинотеатра и хотите узнать, в каком ряду вы сидите. Вы не можете видеть номер своего ряда напрямую. Вы спрашиваете человека, сидещего ровно перед вами: «В каком ряду ты сидишь?». Тот человек тоже не знает и задает тот же вопрос своему соседу спереди. Этот процесс продолжается до тех пор, пока вопрос не доходит до зрителя на первом ряду. Зритель на первом ряду точно знает свой номер — $1$. Он поворачивается назад и говорит второму рядю: «Я на первом, значит, ты на втором». Второй ряд передает третьему: «Я на втором, значит, ты на третьем». Цепочка ответов идет обратно, пока нужная информация не доходит до вас. 

В программировании этот процесс устроен точно так же. Вместо того чтобы вычислять результат сложной задачи в один большой прием с помощью циклов (`for`, `while`), мы сводим задачу к точно такой же задаче, но с меньшим объемом входных данных, пока не дойдем до простейшего состояния, ответ для которого очевиден.

Математической основой рекурсивного мышления является **метод математической индукции**. В индукции мы сначала доказываем утверждение для базового случая (например, для $n = 1$), а затем доказываем, что если утверждение верно для $n$, оно верно и для $n + 1$. В рекурсии мы поступаем наоборот: предполагая, что мы умеем решать задачу для $n - 1$, мы показываем, как выразить решение для $n$.

### Два обязательных условия корректной рекурсии

Любой рабочий рекурсивный алгоритм обязан опираться на два фундаментальных кита:
1. **Базовый случай (условие выхода)** — состояние системы, при котором задача настолько проста, что ее решение известно сразу и не требует повторного вызова метода. Без базового случая рекурсия будет продолжаться бесконечно.
2. **Рекурсивный шаг (уменьшение задачи)** — правило, по которому исходная задача с параметром $n$ сводится к аналогичной задаче с измененным параметром (например, $n - 1$, $n / 10$ и т. д.), причем этот новый параметр неуклонно приближается к базовому случаю при каждом новом вызове.

Если нарушить хотя бы одно из этих условий, программа не сможет корректно завершить работу.

Рассмотрим классический пример задачи на нахождение суммы первых $n$ натуральных чисел: $S(n) = 1 + 2 + \dots + n$. 

Математически ее можно определить рекурсивно:
- Если $n = 0$, то сумма равна $0$ (это базовый случай).
- Если $n > 0$, то сумма равна $n + S(n - 1)$ (это рекурсивный случай, так как задача о сумме $n$ чисел свелась к задаче о сумме $n - 1$ чисел).

Запишем соответствующий метод на языке C#:

```csharp
static int SumTo(int n)
{
    // Базовый случай
    if (n == 0)
    {
        return 0;
    }
    
    // Рекурсивный случай
    return n + SumTo(n - 1);
}
```

Рассмотрим, как выполнится вызов `SumTo(3)`:
1. Вызывается `SumTo(3)`. Поскольку $3 \neq 0$, управление переходит в ветку рекурсивного случая: возвращается значение $3 + \text{SumTo}(2)$. Чтобы сложить числа, компилятору сначала нужно вычислить значение `SumTo(2)`.
2. Вызывается `SumTo(2)`. Возвращается $2 + \text{SumTo}(1)$.
3. Вызывается `SumTo(1)`. Возвращается $1 + \text{SumTo}(0)$.
4. Вызывается `SumTo(0)`. Выполняется проверка `n == 0`. Условие истинно, метод возвращает число `0` без новых вызовов. Это точка останова.
5. Теперь запускается процесс возврата результатов снизу вверх:
   - `SumTo(0)` возвращает `0`, подставляясь в `SumTo(1)`: $1 + 0 = 1$.
   - `SumTo(1)` возвращает `1`, подставляясь в `SumTo(2)`: $2 + 1 = 3$.
   - `SumTo(2)` возвращает `3`, подставляясь в `SumTo(3)`: $3 + 3 = 6$.
6. Итоговый результат выполнения метода `SumTo(3)` равен `6`.

### Анализ некорректной рекурсии и исключение StackOverflowException

Что произойдет, если допустить ошибку при проектировании метода и забыть прописать базовый случай либо составить рекурсивный шаг так, что параметр не приближается к базе?

Рассмотрим ошибочную реализацию того же метода `SumTo`:

```csharp
static int BadSumTo(int n)
{
    // ОШИБКА: отсутствует проверка n == 0 (базовый случай)
    return n + BadSumTo(n - 1);
}
```

Если мы вызовем `BadSumTo(3)`, произойдет следующее:
1. Метод `BadSumTo(3)` вызывает `BadSumTo(2)`.
2. Метод `BadSumTo(2)` вызывает `BadSumTo(1)`.
3. Метод `BadSumTo(1)` вызывает `BadSumTo(0)`.
4. Метод `BadSumTo(0)` вызывает `BadSumTo(-1)`.
5. Метод `BadSumTo(-1)` вызывает `BadSumTo(-2)` и так далее до бесконечности.

Каждый вызов метода в оперативной памяти компьютера требует выделения специального участка памяти под служебную информацию (адрес возврата, локальные переменные, параметры). Эта область памяти называется **стеком вызовов**. Объем стека для каждого потока в операционных системах строго ограничен (обычно составляет около 1 мегабайта в средах .NET).

Поскольку при бесконечной рекурсии новые кадры (блоки памяти) непрерывно добавляются в стек, а старые не могут быть удалены (потому что ни один вызов еще не завершился), свободная память стека быстро исчерпывается. Когда память заканчивается, среда выполнения .NET генерирует фатальное исключение:

> **Исключение.** `System.StackOverflowException` — это системное исключение, возникающее в результате переполнения стека вызовов из-за слишком глубокой или бесконечной рекурсии.

Важная особенность исключения `StackOverflowException` в платформе .NET заключается в том, что его **нельзя перехватить** с помощью блока `try-catch`. При возникновении этого исключения приложение аварийно завершает свою работу, так как повреждение структур данных стека делает дальнейшее безопасное выполнение кода невозможным.

Другая частая ошибка — некорректное уменьшение аргумента. Например, если написать `BadSumTo(n + 1)` вместо `BadSumTo(n - 1)`, значение параметра будет расти в сторону удаления от базового нуля, что также неминуемо приведет к `StackOverflowException`.

### Сравнение итеративного и рекурсивного подходов

Любую задачу, решенную с помощью рекурсии, можно переписать с использованием циклов (`while` или `for`) и явно управляемой структуры данных «стек». И наоборот, любой цикл можно представить в виде рекурсивной функции. Тем не менее, выбор между итерациями и рекурсией диктуется удобством и архитектурой задачи.

Сравним оба подхода по ключевым критериям:

| Критерий | Итеративный подход (циклы) | Рекурсивный подход |
|---|---|---|
| **Производительность** | Выше. Выполнение циклов на уровне процессора происходит быстрее, так как не тратится время на постоянное создание и уничтожение кадров стека. | Ниже. Накладные расходы на вызовы методов и управление стеком замедляют выполнение программы. |
| **Потребление памяти** | Минимальное ($O(1)$). Используется фиксированный набор переменных независимо от числа итераций. | Зависит от глубины ($O(n)$). Каждый уровень рекурсии резервирует память под кадр в стеке вызовов. |
| **Читаемость кода** | Проста для линейных алгоритмов (обход массива, подсчет суммы в один проход). | Идеальна для задач с естественной древовидной или вложенной структурой (обход каталогов файлов, деревья, комбинаторный перебор, алгоритмы «разделяй и властвуй»). |
| **Риск ошибок** | Риск уйти в бесконечный цикл при неверном изменении счетчика. | Риск переполнения стека (`StackOverflowException`) при отсутствии или недостижимости базового случая. |

#### Пример: вычисление факториала итеративно и рекурсивно

Для закрепления сравним две реализации одной математической задачи — вычисление факториала числа $n$ ($n! = 1 \cdot 2 \cdot \dots \cdot n$).

Итеративная реализация через цикл `for`:
```csharp
static long FactorialIterative(int n)
{
    long result = 1;
    for (int i = 1; i <= n; i++)
    {
        result *= i;
    }
    return result;
}
```

Рекурсивная реализация:
```csharp
static long FactorialRecursive(int n)
{
    // Базовый случай: 0! = 1 и 1! = 1
    if (n <= 1)
    {
        return 1;
    }
    
    // Рекурсивный случай: n! = n * (n - 1)!
    return n * FactorialRecursive(n - 1);
}
```

В итеративном варианте мы управляем состоянием явным образом через переменную `result` в теле одного метода. В рекурсивном варианте состояние вычислений распределено по кадрам стека, создаваемым системой автоматически. Для факториала итеративный подход предпочтительнее с точки зрения производительности, однако рекурсивная запись гораздо ближе к исходному математическому определению функции.

### Разбор полного примера: метод рекурсивного суммирования цифр числа

Чтобы закрепить понимание принципа построения рекурсии, рассмотрим задачу, которую сложно интуитивно решить через простые циклы без предварительного знания количества разрядов числа.

#### Условие задачи
Написать статический метод на языке C#, который принимает целое неотрицательное число $n$ и с помощью рекурсии вычисляет сумму всех его цифр. Использование циклов запрещено.

#### Ход рассуждений
1. **Как уменьшить задачу?** Мы умеем легко отделять последнюю цифру числа с помощью операции взятия остатка от деления на 10 ($n \% 10$) и уменьшать число в 10 раз с помощью целочисленного деления ($n / 10$). Например, если число равно $487$, то последняя цифра равна $7$, а оставшаяся часть числа — $48$.
2. **Как выразить ответ через подзадачу?** Сумма цифр числа $487$ равна «последняя цифра ($7$) плюс сумма цифр оставшейся части числа ($48$)». В общем виде для числа $n$: `(n % 10) + SumDigits(n / 10)`.
3. **Какой самый простой вход (базовый случай)?** Когда в числе осталась всего одна цифра, то есть когда $n < 10$. В этом случае сумма цифр самого числа равна самому числу $n$. (Также корректен базовый случай $n == 0$, возвращающий $0$).

#### Реализация на C#

```csharp
using System;

class Program
{
    static void Main()
    {
        int number = 487;
        int result = SumDigits(number);
        Console.WriteLine($"Число: {number}, сумма цифр: {result}");
        
        // Дополнительная проверка на граничном случае
        int singleDigit = 5;
        Console.WriteLine($"Число: {singleDigit}, сумма цифр: {SumDigits(singleDigit)}");
    }

    /// <summary>
    /// Рекурсивный метод для нахождения суммы цифр целого неотрицательного числа.
    /// </summary>
    /// <param name="n">Исходное число</param>
    /// <returns>Сумма цифр числа</returns>
    static int SumDigits(int n)
    {
        // Базовый случай: если число однозначное, сумма равна самому числу
        if (n < 10)
        {
            return n;
        }

    // Рекурсивный случай: последняя цифра + сумма цифр оставшейся части
    return (n % 10) + SumDigits(n / 10);
}
}
```

#### Пошаговый расчет для входного значения `n = 487`
1. Вызывается `SumDigits(487)`. Условие `487 < 10` ложно. Вычисляется выражение: `(487 % 10) + SumDigits(487 / 10)`, что эквивалентно `7 + SumDigits(48)`.
2. Вызывается `SumDigits(48)`. Условие `48 < 10` ложно. Вычисляется выражение: `(48 % 10) + SumDigits(48 / 10)`, что эквивалентно `8 + SumDigits(4)`.
3. Вызывается `SumDigits(4)`. Условие `4 < 10` истинно! Метод возвращает число `4` без новых рекурсивных вызовов.
4. Производится обратная размотка стека вызовов:
   - Для `SumDigits(48)` возвращается значение `8 + 4 = 12`.
   - Для `SumDigits(487)` возвращается значение `7 + 12 = 19`.
5. Итоговый результат выполнения программы: `19`.

#### Проверка и правдоподобие
- Проверим вручную сумму цифр: $4 + 8 + 7 = 19$. Результаты совпадают.
- Единицы измерения: задача оперирует целыми числами, размерность не применима, логических противоречий нет.
- Глубина рекурсии равна количеству разрядов числа (в данном случае 3 уровня), что ничтожно мало для возникновения риска переполнения стека.

Ответ: `19`.

## Устройство стека вызовов и жизненный цикл кадров

### Архитектура оперативной памяти процесса: стек и куча

Когда программа на C# запускается операционной системой, ей выделяется виртуальное адресное пространство. Для управления данными и памятью среда выполнения .NET (`CLR` — *Common Language Runtime*) разделяет эту память на несколько логических областей, среди которых ключевую роль для выполнения методов играют **стек** (*Stack*) и **куча** (*Heap*).

Понимание различий между стеком и кучей критически важно для анализа работы рекурсивных алгоритмов.

> **Определение.** **Стек (Stack)** — это область оперативной памяти, организованная по принципу LIFO (*Last In, First Out* — «последним пришел — первым ушел»). Память в стеке выделяется и освобождается автоматически при вызове и завершении работы методов, а управление ею происходит за счет изменения специального указателя вершины стека (*Stack Pointer*).

Характеристики стека:
1. **Фиксированный размер.** Объем стека для каждого потока в .NET задается заранее (обычно по умолчанию составляет около 1 МБ). Если программа исчерпывает этот объем, происходит аварийное завершение.
2. **Высокая скорость работы.** Выделение памяти сводится к простому смещению указателя вершины стека на несколько байт вперед или назад.
3. **Строгая дисциплина хранения.** Данные добавляются и удаляются исключительно в порядке строгой очередности: последний добавленный элемент всегда удаляется первым.

> **Определение.** **Куча (Heap)** — это область динамической памяти общего назначения, предназначенная для хранения объектов и массивов, время жизни которых не ограничено рамками одного метода.

Характеристики кучи:
1. **Динамический размер.** Куча может расти и сжиматься по мере необходимости в пределах доступной оперативной памяти компьютера.
2. **Управление через сборщик мусора (*Garbage Collector*).** Объекты в куче размещаются с помощью оператора `new`, а их удаление происходит автоматически, когда на них больше не остается активных ссылок в коде.
3. **Производительность.** Доступ к данным в куче медленнее, чем в стеке, так как требуется поиск свободных блоков памяти и работа механизма сборки мусора.

Все локальные переменные типов значений (например, `int`, `double`, `bool`, структуры `struct`) и параметры методов размещаются непосредственно в стеке. Ссылочные типы хранят в стеке только ссылку (адрес в памяти), в то время как сами данные объекта располагаются в куче. Рекурсивные вызовы опираются исключительно на механизмы стека.

### Создание кадра стека при вызове метода

Каждый раз, когда в программе происходит вызов любого метода (включая рекурсивный самовызов), в оперативной памяти стека выделяется специальная структура данных — **кадр стека** (*stack frame*), или активационная запись.

Кадр стека содержит всю необходимую информацию для корректного выполнения и последующего завершения метода:
1. **Аргументы (параметры) метода** — значения, переданные в метод при вызове.
2. **Локальные переменные** — переменные, объявленные внутри тела метода.
3. **Адрес возврата** — точный адрес инструкции в машинном коде, к которой выполнение программы должно вернуться после завершения текущего метода.
4. **Регистровый контекст** — состояние процессорных регистров на момент вызова, чтобы восстановить их после выхода из метода.

Рассмотрим, что происходит на уровне процессора и памяти при вызове метода:
- Программа доходит до строки вызова метода.
- В стеке поверх уже существующих данных выделяется новый блок памяти под кадр вызываемого метода. Указатель вершины стека смещается.
- Значения аргументов копируются в соответствующие параметры нового кадра.
- Управление передается началу кода вызываемого метода.
- По завершении работы метода его кадр «снимается» со стека (указатель возвращается в исходное положение до вызова), а программа продолжает выполнение с адреса возврата, восстанавливая состояние предыдущего метода.

При обычной вложенности вызовов (`Main` вызывает метод `A`, метод `A` вызывает метод `B`) в стеке одновременно находится небольшое количество кадров. При глубокой рекурсии кадры нагромождаются друг на друга, образуя длинную цепочку.

### Пошаговая трассировка вычисления факториала

Чтобы наглядно увидеть, как формируются кадры стека и как работает механизм возврата значений, проанализируем выполнение классической рекурсивной функции вычисления факториала.

Математически факториал числа $n$ (обозначается как $n!$) определяется следующим образом:
$$n! = \begin{cases} 1, & \text{при } n = 0 \text{ или } n = 1 \\ n \cdot (n - 1)!, & \text{при } n > 1 \end{cases}$$

Напишем соответствующий метод на языке C#:

```csharp
static long Factorial(int n)
{
    // Базовый случай
    if (n <= 1)
    {
        return 1;
    }
    
    // Рекурсивный случай
    return n * Factorial(n - 1);
}
```

Представим, что в главной программе вызывается метод: `long result = Factorial(4);`. Проследим за состоянием стека вызовов шаг за шагом.

#### Фаза погружения (прямой ход рекурсии)

1. **Вызов `Factorial(4)`:**
   - В стеке создается кадр № 1.
   - Параметр `n = 4`.
   - Проверка условия `4 <= 1` дает ложь (`false`).
   - Метод должен вернуть `4 * Factorial(3)`. Чтобы это вычислить, приостанавливается выполнение текущего метода и совершается новый вызов — `Factorial(3)`.

2. **Вызов `Factorial(3)`:**
   - Поверх первого кадра в стеке создается кадр № 2.
   - Параметр `n = 3`.
   - Проверка `3 <= 1` ложна.
   - Метод возвращает `3 * Factorial(2)`. Выполнение приостанавливается, происходит вызов `Factorial(2)`.

3. **Вызов `Factorial(2)`:**
   - Поверх второго кадра создается кадр № 3.
   - Параметр `n = 2`.
   - Проверка `2 <= 1` ложна.
   - Метод возвращает `2 * Factorial(1)`. Выполнение приостанавливается, вызывается `Factorial(1)`.

4. **Вызов `Factorial(1)`:**
   - Поверх третьего кадра создается кадр № 4.
   - Параметр `n = 1`.
   - Проверка `1 <= 1` дает истину (`true`).
   - Срабатывает базовый случай: метод **не** делает новых вызовов, а сразу возвращает число `1`.

На этом этапе погружение завершено. В памяти стека одновременно находятся 4 активных кадра вызовов.

### Достижение базового случая и размотка стека

После того как достигнут базовый случай, начинается процесс **размотки стека** (*stack unwinding*). Вычисленные значения передаются из самых глубоких вызовов обратно к точкам их порождения.

#### Фаза всплытия (обратный ход рекурсии)

1. **Возврат из `Factorial(1)`:**
   - Метод возвращает `1` в кадр № 3, где ожидал вызов `Factorial(1)`.
   - Кадр № 4 удаляется из стека, указатель смещается назад.
   - В кадре № 3 возобновляется вычисление выражения: `2 * 1 = 2`. Метод `Factorial(2)` возвращает число `2` в кадр № 2.

2. **Возврат из `Factorial(2)`:**
   - Кадр № 3 удаляется из стека.
   - В кадре № 2 возобновляется вычисление: `3 * 2 = 6`. Метод `Factorial(3)` возвращает число `6` в кадр № 1.

3. **Возврат из `Factorial(3)`:**
   - Кадр № 2 удаляется из стека.
   - В кадре № 1 возобновляется вычисление: `4 * 6 = 24`. Метод `Factorial(4)` возвращает окончательный результат `24` в метод `Main`.
   - Кадр № 1 удаляется из стека. Стек возвращается в исходное состояние.

Ниже приведена полная таблица состояния стека вызовов для вызова `Factorial(4)` в момент максимального погружения (перед срабатыванием базового случая):

| Уровень стека | Имя метода | Значение параметра `n` | Выражение, ожидающее результат | Состояние кадра |
|---|---|---|---|---|
| 4 (Вершина) | `Factorial` | `1` | Базовый случай (возврат `1`) | Активен (выполняется) |
| 3 | `Factorial` | `2` | `2 * Factorial(1)` | Приостановлен |
| 2 | `Factorial` | `3` | `3 * Factorial(2)` | Приостановлен |
| 1 (Основание) | `Factorial` | `4` | `4 * Factorial(3)` | Приостановлен |

Как видно из таблицы, каждый кадр хранит ровно ту информацию, которая нужна для продолжения работы именно на этом уровне после получения ответа от нижележащей подзадачи.

### Наблюдение за кадрами стека в Visual Studio

Современные среды разработки предоставляют мощные инструменты для визуализации и отладки процессов, происходящих в оперативной памяти. В Visual Studio для анализа рекурсии используется окно **Call Stack** (Стек вызовов).

Чтобы увидеть стек вызовов на практике:
1. Откройте проект с рекурсивным методом в Visual Studio.
2. Установите точку останова (*Breakpoint*, клавиша F9) на строке с базовым случаем внутри рекурсивного метода (например, на строке `return 1;` в методе `Factorial`).
3. Запустите программу в режиме отладки (клавиша F5).
4. Когда программа остановится на точке останова, откройте окно отладки: в верхнем меню выберите **Debug -> Windows -> Call Stack** (или используйте комбинацию клавиш `Ctrl + Alt + C`).

В окне **Call Stack** вы увидите список всех активных на данный момент вызовов методов, упорядоченных сверху вниз: от текущего (самого глубокого) до метода `Main`, который запустил всю цепочку. 

Двойной клик по любой строке в окне Call Stack позволяет переключаться между контекстами выполнения различных кадров стека. В этот момент в окне редактора кода будут подсвечиваться локальные переменные и параметры именно того кадра, который вы выбрали, что позволяет детально проанализировать состояние программы на любом уровне рекурсии. Для пошагового выполнения программы и наблюдения за погружением или всплытием используется клавиша **F11** (*Step Into*).

### Оценка потребления памяти: линейная зависимость $O(n)$

Каждый вызов метода требует выделения фиксированного (или зависящего от локальных переменных) объема памяти под новый кадр стека. 

Пусть глубина рекурсии (количество последовательных самовызовов до достижения базового случая) равна $n$. 
Если на один кадр стека затрачивается в среднем $C$ байт памяти (включая адрес возврата, параметры и локальные переменные), то общий объем памяти, занимаемый рекурсивными вызовами в пиковой точке (при максимальном погружении), составит:
$$M(n) = C \cdot n$$

С точки зрения асимптотической сложности (*Big O notation*), константа $C$ отбрасывается, что дает нам оценку требуемой памяти:
$$O(n)$$

Это означает, что потребление памяти рекурсивным алгоритмом растет **линейно** пропорционально глубине рекурсии. 

> **Важное следствие.** Если глубина рекурсии окажется слишком большой (например, метод вызовется 50 000 раз подряд), суммарный объем всех кадров стека превысит выделенный операционной системой лимит (1 МБ). В этот момент .NET сгенерирует исключение времени выполнения:
> 
> `System.StackOverflowException: "Произошло переполнение стека."`
> 
> Исключение `StackOverflowException` является фатальным: его невозможно перехватить с помощью блока `try-catch` в обычном управляемом коде, и программа аварийно завершает свою работу. Поэтому для задач с большой глубиной рекурсии (или заранее неизвестным количеством шагов) разработчики обязаны либо увеличивать размер стека, либо переписывать алгоритм в итеративной форме (с использованием циклов и явных структур данных, хранящихся в куче).

### Разобранный пример: Полная трассировка вызова `Factorial(4)`

**Условие задачи:**
Требуется выполнить полный анализ и составить схему изменения памяти стека для статического метода `Factorial(int n)`, вызванного с аргументом `4`. Зафиксировать все состояния погружения и возврата данных.

**Ход рассуждений:**
1. Метод принимает целое число `n`.
2. Базовый случай срабатывает при `n <= 1`. На каждом шаге рекурсии параметр уменьшается на единицу (`n - 1`), что гарантирует обязательное достижение базового случая за 4 шага.
3. Нам необходимо расписать создание кадров, вычисление промежуточных выражений и финальную сборку результата.

**Решение в общем виде и по шагам:**

Запишем развертывание формулы в виде цепочки подстановок:
$$\text{Factorial}(4) = 4 \cdot \text{Factorial}(3)$$
$$\text{Factorial}(3) = 3 \cdot \text{Factorial}(2)$$
$$\text{Factorial}(2) = 2 \cdot \text{Factorial}(1)$$
$$\text{Factorial}(1) = 1 \quad (\text{базовый случай})$$

Теперь выполним обратную подстановку (свертку стека):
1. Подставляем результат `Factorial(1)` в выражение для `Factorial(2)`:
   $$\text{Factorial}(2) = 2 \cdot 1 = 2$$
2. Подставляем результат `Factorial(2)` в выражение для `Factorial(3)`:
   $$\text{Factorial}(3) = 3 \cdot 2 = 6$$
3. Подставляем результат `Factorial(3)` в выражение для `Factorial(4)`:
   $$\text{Factorial}(4) = 4 \cdot 6 = 24$$

**Проверка:**
- Проверим единицы измерения и типы: аргументы имеют тип `int`, результат возвращается как `long`, переполнения для небольших чисел не происходит.
- Правдоподобность: $4! = 1 \cdot 2 \cdot 3 \cdot 4 = 24$. Расчет математически верен.

Ответ: `24` (максимальная глубина стека — 4 кадра).

## Прямой и обратный ход рекурсии: порядок выполнения инструкций

### Размещение инструкций относительно строки рекурсивного вызова

Когда метод вызывает сам себя, выполнение текущего экземпляра метода приостанавливается, а управление передается новому экземпляру. То положение в коде, где произошел вызов, фиксируется в стеке вызовов вместе с локальными переменными. Ключевое понимание работы рекурсии кроется в том, **где именно** относительно строки рекурсивного вызова располагаются остальные инструкции метода.

> **Правило порядка выполнения.** Все инструкции метода, расположенные физически *выше* (до) строки рекурсивного вызова, выполняются в процессе погружения в глубь рекурсии (вниз по стеку). Все инструкции, расположенные *ниже* (после) строки рекурсивного вызова, выполняются в процессе всплытия (возврата управления наверх по стеку).

Рассмотрим общую структуру рекурсивного метода с точки зрения расположения кода:

```csharp
static void ExampleMethod(int n)
{
    // Базовый случай
    if (n <= 0) return;

    // --- КОД ДО РЕКУРСИВНОГО ВЫЗОВА ---
    // Выполняется при погружении (прямой ход)
    Console.WriteLine($"Погружение: n = {n}");

    // Рекурсивный вызов
    ExampleMethod(n - 1);

    // --- КОД ПОСЛЕ РЕКУРСИВНОГО ВЫЗОВА ---
    // Выполняется при возврате (обратный ход)
    Console.WriteLine($"Возврат: n = {n}");
}
```

Если вызвать `ExampleMethod(3)`, порядок вывода на консоль будет строго определенным и наглядным:
1. Вызов `ExampleMethod(3)`: условие `n <= 0` ложно. Выполняется код «до»: выводится `Погружение: n = 3`. Происходит вызов `ExampleMethod(2)`.
2. Вызов `ExampleMethod(2)`: условие ложно. Код «до»: выводится `Погружение: n = 2`. Вызов `ExampleMethod(1)`.
3. Вызов `ExampleMethod(1)`: условие ложно. Код «до»: выводится `Погружение: n = 1`. Вызов `ExampleMethod(0)`.
4. Вызов `ExampleMethod(0)`: условие `n <= 0` истинно, срабатывает `return`, управление возвращается в метод `ExampleMethod(1)` сразу после строки рекурсивного вызова.
5. В `ExampleMethod(1)` выполняется код «после»: выводится `Возврат: n = 1`. Метод завершается, возврат в `ExampleMethod(2)`.
6. В `ExampleMethod(2)` выполняется код «после»: выводится `Возврат: n = 2`. Метод завершается, возврат в `ExampleMethod(3)`.
7. В `ExampleMethod(3)` выполняется код «после»: выводится `Возврат: n = 3`. Программа завершает работу метода.

Итоговый вывод на экран:
```text
Погружение: n = 3
Погружение: n = 2
Погружение: n = 1
Возврат: n = 1
Возврат: n = 2
Возврат: n = 3
```

Это поведение демонстрирует фундаментальное свойство стековой архитектуры: симметрию «первым пришел — последним вышел» (Last In, First Out).

### Прямой и обратный ход рекурсии

Процесс выполнения рекурсивного алгоритма традиционно делят на две фазы:

1. **Прямой ход (forward phase / unwinding down)** — этап погружения. Вычислитель идет от исходного большого значения параметра к базовому случаю. На этом этапе создаются новые кадры стека, выполняются все инструкции, написанные до рекурсивного вызова, а сама задача дробится на более мелкие подзадачи.
2. **Обратный ход (backward phase / winding up / возвратно-поступательный этап)** — этап всплытия. По достижении базового случая самый глубокий вызов завершается без новых порождений, и процессор начинает последовательно «раскручивать» стек в обратном направлении, возвращая управление в вызывающие методы. На этом этапе выполняются все инструкции, написанные после рекурсивного вызова, и происходит агрегация (сборка) окончательного результата из ответов подзадач.

Понимание этой разницы позволяет решать задачи разворота последовательностей, обработки данных с конца и построения зеркальных структур без использования громоздких вспомогательных циклов или ручных коллекций.

### Разобранный пример: печать чисел в прямом и обратном порядке

Рассмотрим метод `Show(int n)`, который принимает целое положительное число $n$ и должен напечатать числа от $1$ до $n$ (прямой порядок) и от $n$ до $1$ (обратный порядок), используя единственную рекурсивную функцию.

#### Условие и постановка задачи
Написать статический метод в C#, принимающий `int n`. Метод должен выводить на консоль два ряда чисел:
- Ряд 1 (при погружении/возврате): в зависимости от размещения инструкций.
- Требуется спроектировать метод так, чтобы одна строка кода печатала числа по возрастанию (от $1$ до $n$), а другая — по убыванию (от $n$ до $1$).

#### Рисунок схемы работы (словесное описание)
Представим память как вертикальную стопку листов бумаги (стек), куда мы записываем состояние метода при каждом вызове.
- Вниз по стопке (погружение): параметр $n$ уменьшается от исходного значения до $1$. Если инструкция печати стоит *до* вызова, число записывается на консоль в момент закладывания листа в стопку ($n, n-1, \dots, 1$).
- Вверх по стопке (возврат): когда мы достигаем дна ($n = 0$), стопка начинает разбираться сверху вниз (от единицы обратно к $n$). Если инструкция печати стоит *после* вызова, число выводится в момент снятия листа со стопки ($1, 2, \dots, n$).

#### Ход рассуждений
1. **Базовый случай:** когда $n$ становится равным нулю ($n = 0$), делать больше нечего, рекурсию нужно остановить. Используем оператор `if (n == 0) return;`.
2. **Уменьшение задачи:** на каждом шаге мы переходим к числу на единицу меньше, то есть передаем в следующий вызов `n - 1`.
3. **Вывод по убыванию ($n \to 1$):** этот порядок совпадает с порядком уменьшения переменной $n$ при погружении. Значит, команду `Console.Write` нужно разместить **до** рекурсивного вызова.
4. **Вывод по возрастанию ($1 \to n$):** этот порядок совпадает с порядком возврата управления из глубин стека (сначала обрабатывается самый мелкий оставшийся подвызов, затем более крупный). Значит, команду `Console.Write` нужно разместить **после** рекурсивного вызова.

#### Полный код программы

```csharp
using System;

class Program
{
    static void Main()
    {
        int n = 4;
        Console.WriteLine($"Демонстрация для n = {n}:");
        
        Console.Write("Обратный порядок (при погружении): ");
        ShowDescending(n);
        Console.WriteLine(); // перевод строки
        
        Console.Write("Прямой порядок (при возврате):     ");
        ShowAscending(n);
        Console.WriteLine();
    }

    // Метод 1: печать по убыванию (код ДО вызова)
    static void ShowDescending(int n)
    {
        if (n == 0) return; // Базовый случай

        // Инструкция ДО рекурсивного вызова выполняется при погружении
        Console.Write(n + " "); 

        ShowDescending(n - 1); // Рекурсивный шаг
    }

    // Метод 2: печать по возрастанию (код ПОСЛЕ вызова)
    static void ShowAscending(int n)
    {
        if (n == 0) return; // Базовый случай

        ShowAscending(n - 1); // Рекурсивный шаг

        // Инструкция ПОСЛЕ рекурсивного вызова выполняется при возврате
        Console.Write(n + " "); 
    }
}
```

#### Трассировка и проверка выполнения для `ShowAscending(3)`
1. Вызов `ShowAscending(3)`: $3 \neq 0$. Вызывается `ShowAscending(2)`. Текущий кадр ($n=3$) ждет возврата.
2. Вызов `ShowAscending(2)`: $2 \neq 0$. Вызывается `ShowAscending(1)`. Кадр ($n=2$) ждет.
3. Вызов `ShowAscending(1)`: $1 \neq 0$. Вызывается `ShowAscending(0)`. Кадр ($n=1$) ждет.
4. Вызов `ShowAscending(0)`: $0 == 0$, срабатывает `return`. Возврат в кадр с $n=1$.
5. В кадре $n=1$ возобновляется работа после строки вызова: выполняется `Console.Write("1 ")`. На экран выводится `1`. Метод завершается, возврат в кадр с $n=2$.
6. В кадре $n=2$ выполняется `Console.Write("2 ")`. На экран дописывается `2`. Возврат в кадр с $n=3$.
7. В кадре $n=3$ выполняется `Console.Write("3 ")`. На экран дописывается `3`. Завершение работы программы.

Итоговый вывод метода `ShowAscending(3)`: `1 2 3 `.

#### Проверка единиц и правдоподобие
- При $n = 0$ оба метода корректно завершают работу мгновенно, ничего не выводя, что соответствует граничному условию.
- Потребление памяти стека для обоих методов составляет $O(n)$ кадров, что безопасно для небольших значений $n$ (например, до нескольких тысяч).

### Обработка строк и массивов с конца к началу и обратно

Механизм прямого и обратного хода активно применяется при обработке линейных структур данных — массивов и строк. Поскольку строка в C# представляет собой неизменяемый массив символов (`string`), а стандартные циклы обрабатывают элементы от индекса $0$ до $Length - 1$, рекурсия позволяет легко развернуть эту логику.

#### Пример: Рекурсивный вывод символов строки в обратном порядке
Требуется вывести все символы заданной строки `s` с конца к началу, не используя циклы (`for`, `while`) и не разворачивая строку физически в памяти.

```csharp
using System;

class Program
{
    static void Main()
    {
        string text = "COMPUTER";
        Console.Write("Исходная строка: ");
        Console.WriteLine(text);
        
        Console.Write("Строка задом наперед: ");
        PrintReverse(text, text.Length - 1);
        Console.WriteLine();
    }

    static void PrintReverse(string s, int index)
    {
        // Базовый случай: если индекс вышел за границы начала строки
        if (index < 0) return;

        // 1. Сначала обрабатываем текущий символ (печатаем с конца)
        Console.Write(s[index]);

        // 2. Затем уменьшаем индекс и вызываем метод для предыдущего символа
        PrintReverse(s, index - 1);
    }
}
```

*Пояснение по строкам кода:*
- Параметр `index` выполняет роль счетчика, который на старте равен последнему индексу строки (`text.Length - 1`).
- Инструкция `Console.Write(s[index]);` расположена **до** рекурсивного вызова. Это означает, что программа выведет символ с наибольшим индексом (самый правый), затем уменьшит индекс на единицу и погрузится глубже. В результате строка будет напечатана задом наперед.
- Если бы мы поменяли местами `Console.Write` и рекурсивный вызов, строка напечаталась бы в обычном порядке, но обход элементов происходил бы рекурсивно от конца к началу.

### Сравнение рекурсивного обхода со стеком, смоделированным вручную

Любой рекурсивный алгоритм, использующий системный стек вызовов, теоретически может быть переписан в итеративную форму. Для этого программисту приходится самостоятельно создавать структуру данных «стек» в куче памяти (например, используя класс `Stack<T>` из пространства имен `System.Collections.Generic`) и вручную управлять сохранением контекста.

Сравним два подхода к обходу последовательности или дерева вызовов:

| Критерий | Системная рекурсия (на стеке вызовов) | Итеративный алгоритм с ручным стеком (`Stack<T>`) |
|---|---|---|
| **Читаемость кода** | Высокая, код компактен и математически прозрачен. | Низкая, код обрастает вспомогательными классами узлов и циклами. |
| **Управление памятью** | Управляется платформой .NET и средой выполнения CLR автоматически. | Управляется разработчиком (явное выделение памяти под коллекцию `Stack`). |
| **Риск аварийного завершения** | Высокий при большой глубине (возникает `StackOverflowException`). | Низкий (при переполнении памяти в куче генерируется `OutOfMemoryException`, который можно перехватить через `try-catch`). |
| **Накладные расходы** | Минимальные аппаратные расходы на создание стандартных кадров процессора. | Дополнительные расходы на распределение объектов в управляемой куче (Heap). |
| **Область применения** | Деревья, графы, алгоритмы «разделяй и властвуй», простые обходы. | Высоконагруженные системы с глубокой рекурсией, где критически важно избегать падения потока. |

Пример эмуляции прямого и обратного хода через ручной стек в C# (для концептуального понимания того, как среда выполняет рекурсию «под капотом»):

```csharp
using System;
using System.Collections.Generic;

class Program
{
    static void Main()
    {
        int n = 3;
        Console.WriteLine("Эмуляция рекурсии через ручной стек (обратный порядок):");
        IterativeShow(n);
    }

    static void IterativeShow(int n)
    {
        // Создаем явную коллекцию-стек в памяти
        Stack<int> stack = new Stack<int>();

        // Фаза погружения (закладываем элементы в стек)
        for (int i = 1; i <= n; i++)
        {
            stack.Push(i);
        }

        // Фаза возврата (извлекаем элементы в обратном порядке)
        while (stack.Count > 0)
        {
            int current = stack.Pop();
            Console.Write(current + " ");
        }
    }
}
```

В реальной разработке для простых линейных задач предпочтительнее использовать стандартные циклы или чистую рекурсию, однако понимание того, как системный стек обрабатывает порядок инструкций «до» и «после», является базовым навыком при отладке сложных алгоритмов перебора и синтаксических анализаторов.

Когда структуру данных или математическую формулу можно определить через саму себя меньшего размера, рекурсия становится самым читаемым и элегантным инструментом. В этом разделе мы разберем четыре фундаментальные задачи, которые регулярно встречаются как в учебной практике, так и на экзаменах: вычисление факториала, нахождение суммы цифр числа, расчет наибольшего общего делителя по алгоритму Евклида и проверка строки на палиндром методом сужения границ.

### Вычисление факториала

Факториал целого неотрицательного числа $n$ (обозначается как $n!$) — это произведение всех натуральных чисел от $1$ до $n$ включительно. По определению, факториал нуля равен единице:

$$
n! = \begin{cases} 1, & \text{при } n = 0 \text{ или } n = 1 \\ n \cdot (n - 1)!, & \text{при } n > 1 \end{cases}
$$

Математическая формула факториала изначально задана рекурсивно: значение для $n$ выражается через значение для $(n - 1)$. Переведем это определение на язык C#, используя статический метод, возвращающий тип `long` (так как факториал растет очень быстро и тип `int` переполнится уже при $n = 13$):

```csharp
using System;

class FactorialDemo
{
    static long Factorial(int n)
    {
        // 1. Базовый случай: 0! = 1 и 1! = 1
        if (n <= 1)
        {
            return 1;
        }

        // 2. Рекурсивный случай: n! = n * (n - 1)!
        return n * Factorial(n - 1);
    }

    static void Main()
    {
        int n = 5;
        long result = Factorial(n);
        Console.WriteLine($"Факториал числа {n} равен {result}.");
    }
}
```

**Разбор кода:**
1. Метод `Factorial` принимает параметр `n` типа `int` и возвращает `long`.
2. Условие `if (n <= 1)` представляет собой базовый случай. Если функция вызвана с аргументом `0` или `1`, рекурсия прекращает углубляться и возвращает `1` без дополнительных вызовов.
3. Строка `return n * Factorial(n - 1);` реализует рекурсивный шаг. Здесь метод умножает текущее значение `n` на результат выполнения того же метода, но с уменьшенным на единицу аргументом (`n - 1`).
4. Каждый такой вызов порождает новый кадр в системном стеке, где хранится своя собственная локальная копия переменной `n`.

### Сумма цифр целого числа

Пусть требуется найти сумму цифр заданного целого неотрицательного числа $n$. Например, для числа $487$ сумма цифр составляет $4 + 8 + 7 = 19$. 

Чтобы решить эту задачу рекурсивно, необходимо выразить задачу для числа $n$ через аналогичную задачу для меньшего числа. В позиционной системе счисления любое число можно разделить на две части: последнюю цифру (младший разряд) и все остальные цифры, стоящие слева. 
- Последняя цифра числа получается с помощью операции взятия остатка от деления на $10$: `n % 10`.
- Оставшаяся часть числа получается с помощью целочисленного деления на $10$: `n / 10`.

Например, для числа $487$:
- `487 % 10` дает `7` (последняя цифра).
- `487 / 10` дает `48` (остаток числа).

Базовым случаем здесь будет ситуация, когда от числа ничего не осталось, то есть когда `n == 0`. В этом случае сумма цифр равна нулю.

> **Правило:** При проектировании рекурсивных функций, работающих с числами, уменьшение задачи почти всегда достигается через целочисленное деление `n / 10` (для десятичной системы) или сдвиг указателей в массивах и строках.

Рассмотрим полностью реализованный пример для входного значения $487$:

```csharp
using System;

class SumDigitsDemo
{
    static int SumDigits(int n)
    {
        // 1. Базовый случай: если число стало равным 0, цифр больше нет
        if (n == 0)
        {
            return 0;
        }

        // 2. Рекурсивный случай: последняя цифра + сумма цифр оставшейся части
        int lastDigit = n % 10;
        int remainingNumber = n / 10;

        return lastDigit + SumDigits(remainingNumber);
    }

    static void Main()
    {
        int number = 487;
        int totalSum = SumDigits(number);
        Console.WriteLine($"Сумма цифр числа {number} равна {totalSum}.");
    }
}
```

#### Пошаговый расчет и трассировка для входного значения 487

Проследим, как именно выполняются вызовы и возвраты значений в системном стеке для метода `SumDigits(487)`:

1. **Вызов `SumDigits(487)`**:
   - `487 == 0` — ложь. Базовый случай не достигнут.
   - Вычисляем последнюю цифру: `lastDigit = 487 % 10 = 7`.
   - Вычисляем оставшуюся часть: `remainingNumber = 487 / 10 = 48`.
   - Метод приостанавливает свое выполнение и вызывает `SumDigits(48). Ждет возврата результата.

2. **Вызов `SumDigits(48)` (внутри первого вызова)**:
   - `48 == 0` — ложь.
   - `lastDigit = 48 % 10 = 8`.
   - `remainingNumber = 48 / 10 = 4`.
   - Метод приостанавливает выполнение и вызывает `SumDigits(4). Ждет возврата результата.

3. **Вызов `SumDigits(4)` (внутри второго вызова)**:
   - `4 == 0` — ложь.
   - `lastDigit = 4 % 10 = 4`.
   - `remainingNumber = 4 / 10 = 0`.
   - Метод приостанавливает выполнение и вызывает `SumDigits(0). Ждет возврата результата.

4. **Вызов `SumDigits(0)` (достижение базового случая)**:
   - `0 == 0` — истина!
   - Метод возвращает `0` наверх в предыдущий кадр стека.

5. **Возврат из `SumDigits(0)` в кадр `SumDigits(4)`**:
   - Вызов `SumDigits(0)` завершился со значением `0`.
   - Теперь выражение `lastDigit + SumDigits(remainingNumber)` превращается в `4 + 0 = 4`.
   - Кадр `SumDigits(4)` завершает работу и возвращает `4` наверх.

6. **Возврат из `SumDigits(4)` в кадр `SumDigits(48)`**:
   - Вызов `SumDigits(4)` завершился со значением `4`.
   - Выражение в кадре `SumDigits(48)` превращается в `8 + 4 = 12`.
   - Кадр `SumDigits(48)` завершает работу и возвращает `12` наверх.

7. **Возврат из `SumDigits(48)` в исходный кадр `SumDigits(487)`**:
   - Вызов `SumDigits(48)` завершился со значением `12`.
   - Исходное выражение превращается в `7 + 12 = 19`.
   - Исходный метод возвращает итоговый результат `19` в метод `Main`.

`Ответ:` Сумма цифр числа 487 равна 19.

### Наибольший общий делитель (НОД): Алгоритм Евклида

Наибольшим общим делителем (НОД) двух целых неотрицательных чисел $a$ и $b$ (не равных нулю одновременно) называется наибольшее целое число, на которое оба числа делятся без остатка.

Классический и наиболее эффективный способ нахождения НОД — это **алгоритм Евклида**, который в своей основе является рекурсивным. Математически он формулируется так:

$$
\text{NOD}(a, b) = \begin{cases} a, & \text{при } b = 0 \\ \text{NOD}(b, a \pmod b), & \text{при } b \neq 0 \end{cases}
$$

Алгоритм утверждает, что НОД двух чисел не изменится, если большее число заменить остатком от деления большего числа на меньшее. На каждом шаге один из аргументов уменьшается, и процесс гарантированно сходится к нулю в качестве второго аргумента.

Реализуем алгоритм Евклида на C# в виде рекурсивного метода с двумя параметрами:

```csharp
using System;

class GcdDemo
{
    static int GetGcd(int a, int b)
    {
        // 1. Базовый случай: если второй аргумент равен 0, то НОД найден — это первое число
        if (b == 0)
        {
            return a;
        }

        // 2. Рекурсивный случай: передаем b и остаток от деления a на b
        return GetGcd(b, a % b);
    }

    static void Main()
    {
        int x = 1071;
        int y = 462;
        int gcd = GetGcd(x, y);
        
        Console.WriteLine($"Наибольший общий делитель чисел {x} и {y} равен {gcd}.");
    }
}
```

**Анализ работы метода `GetGcd` для чисел 1071 и 462:**
1. `GetGcd(1071, 462)`: `b` не равно нулю. Вызывает `GetGcd(462, 1071 % 462)`. Так как `1071 = 2 * 462 + 147`, остаток равен `147`. Метод вызывает `GetGcd(462, 147)`.
2. `GetGcd(462, 147)`: вызывает `GetGcd(147, 462 % 147)`. Так как `462 = 3 * 147 + 21`, остаток равен `21`. Метод вызывает `GetGcd(147, 21)`.
3. `GetGcd(147, 21)`: вызывает `GetGcd(21, 147 % 21)`. Так как `147` делится на `21` нацело (`147 = 7 * 21`), остаток равен `0`. Метод вызывает `GetGcd(21, 0)`.
4. `GetGcd(21, 0)`: срабатывает базовый случай (`b == 0`), метод возвращает `21`.
5. Значение `21` последовательно передается наверх без изменений.

`Ответ:` Наибольший общий делитель чисел 1071 и 462 равен 21.

### Проверка строки на палиндром

Палиндром — это строка, которая читается одинаково как слева направо, так и справа налево (например, «шалаш», «топот», «а роза упала на лапу Азора»). 

Эту задачу можно решить с помощью рекурсивного метода сужения границ. Идея заключается в следующем:
1. Сравниваем первый и последний символы строки.
2. Если они не равны, строка точно не является палиндромом (возвращаем `false`).
3. Если они равны, отбрасываем первый и последний символы (сужаем задачу) и проверяем оставшуюся центральную подстроку рекурсивно.

Каковы базовые случаи для этой задачи?
- Если длина строки равна `0` или `1`, все символы успешно проверены, строка является палиндромом (возвращаем `true`).
- Если на каком-то шаге символы на концах не совпали, это второй базовый случай (возвращаем `false`).

Напишем метод проверки на палиндром на C# (для упрощения примера будем считать, что входная строка очищена от пробелов и знаков препинания, а регистр символов приведен к единому):

```csharp
using System;

class PalindromeDemo
{
    static bool IsPalindrome(string s)
    {
        // 1. Базовый случай 1: если строка пустая или состоит из одного символа
        if (s.Length <= 1)
        {
            return true;
        }

        // 2. Базовый случай 2: если крайние символы не равны, это не палиндром
        if (s[0] != s[s.Length - 1])
        {
            return false;
        }

        // 3. Рекурсивный случай: отбрасываем первый и последний символы с помощью Substring
        // Подстрока начинается с индекса 1 и имеет длину s.Length - 2
        string innerSubstring = s.Substring(1, s.Length - 2);

        return IsPalindrome(innerSubstring);
    }

    static void Main()
    {
        string text = "шалаш";
        bool result = IsPalindrome(text);

        if (result)
        {
            Console.WriteLine($"Строка \"{text}\" является палиндромом.");
        }
        else
        {
            Console.WriteLine($"Строка \"{text}\" не является палиндромом.");
        }
    }
}
```

**Разбор работы метода `IsPalindrome` для строки `"шалаш"`:**
1. `IsPalindrome("шалаш")`: длина равна 5 ($\le 1$ — нет). Первый символ `'ш'` равен последнему `'ш'`. Создается подстрока без крайних символов: `"ала"`. Вызывается `IsPalindrome("ала")`.
2. `IsPalindrome("ала")`: длина равна 3. Первый символ `'а'` равен последнему `'а'`. Создается подстрока: `"л"`. Вызывается `IsPalindrome("л")`.
3. `IsPalindrome("л")`: длина равна 1. Срабатывает базовый случай (`s.Length <= 1`), метод возвращает `true`.
4. Результат `true` передается через всю цепочку вызовов обратно в `Main`.

`Ответ:` Строка "шалаш" является палиндромом.

### Правила оформления возвращаемых значений в рекурсивных методах

Одна из самых частых ошибок начинающих программистов при написании рекурсивных алгоритмов — попытка использовать внешние (глобальные) переменные-накопители вместо передачи и возврата данных через механизм функций.

> **Важное правило:** Рекурсивный метод должен вычислять и возвращать результат своей подзадачи с помощью оператора `return`, передавая его предыдущему уровню стека. Использование статических полей класса для накопления промежуточных результатов в рекурсии делает код уязвимым к багам, небезопасным при многопоточном выполнении и нарушает принципы модульного проектирования.

Сравним два подхода на примере суммирования элементов массива:

**Неправильный подход (с использованием глобального накопителя — антипаттерн):**
```csharp
class BadExample
{
    static int globalSum = 0; // Глобальная переменная — зло в рекурсии

    static void SumArray(int[] arr, int index)
    {
        if (index >= arr.Length) return;
        globalSum += arr[index]; // Модификация внешнего состояния
        SumArray(arr, index + 1);
    }
}
```
*Почему это плохо:* если вы вызовете метод `SumArray` второй раз в той же программе, переменная `globalSum` не обнулится автоматически, и результат окажется неверным. Такой метод нельзя вызвать параллельно или вложенно.

**Правильный подход (чистая рекурсия с возвратом значений):**
```csharp
class GoodExample
{
    static int SumArray(int[] arr, int index)
    {
        // Базовый случай: если индекс вышел за границы массива, сумма пустой части равна 0
        if (index >= arr.Length)
        {
            return 0;
        }

        // Рекурсивный случай: текущий элемент + сумма оставшейся части массива
        return arr[index] + SumArray(arr, index + 1);
    }
}
```
*Почему это правильно:* метод не зависит от внешнего состояния, каждый вызов изолирован в своем кадре стека, функция возвращает чистое математическое значение, которое легко тестировать и использовать в любых выражениях.

## Проблема повторных вычислений и мемоизация на примере чисел Фибоначчи

### Математическое определение чисел Фибоначчи

Числа Фибоначчи образуют числовую последовательность, в которой первые два элемента равны единице (или нулю и единице, в зависимости от соглашения, но для программирования удобнее принять первые члены за единицу), а каждый последующий элемент равен сумме двух предыдущих. 

Запишем математическое определение (рекуррентную формулу) для $n$-го числа Фибоначчи $F(n)$:

$$
F(n) = \begin{cases} 
1, & \text{если } n = 1 \text{ или } n = 2 \\ 
F(n-1) + F(n-2), & \text{если } n > 2 
\end{cases}
$$

В этом определении четко прослеживаются оба обязательных условия рекурсии:
1. **Базовый случай:** для $n = 1$ и $n = 2$ значение известно сразу и равно $1$. Никаких дополнительных вызовов не требуется.
2. **Рекурсивный случай:** для любого $n > 2$ задача вычисления $F(n)$ сводится к вычислению двух меньших подзадач — $F(n-1)$ и $F(n-2)$, результаты которых складываются.

---

### Реализация наивного метода и дерево вызовов

Перенесем математическое определение напрямую на язык C# в виде статического метода. Такой подход называется «наивной» (или прямой) рекурсией:

```csharp
using System;

class Program
{
    static long FibNaive(int n)
    {
        // Базовый случай
        if (n == 1 || n == 2)
        {
            return 1;
        }
        // Рекурсивный случай
        return FibNaive(n - 1) + FibNaive(n - 2);
    }

    static void Main()
    {
        int n = 5;
        Console.WriteLine($"FibNaive({n}) = {FibNaive(n)}");
    }
}
```

Давайте разберем, как работает этот код при вызове `FibNaive(5)`. Чтобы понять причину неэффективности такого подхода, построим дерево вызовов. Каждый узел дерева представляет собой отдельный вызов метода, а разветвления показывают порождение двух новых рекурсивных вызовов.

```
                    FibNaive(5)
                   /           \
        FibNaive(4)             FibNaive(3)
        /         \             /         \
  FibNaive(3)   FibNaive(2)  FibNaive(2)  FibNaive(1)
   /       \         (1)          (1)          (1)
FibNaive(2) FibNaive(1)
    (1)         (1)
```

Посчитаем общее количество вызовов метода `FibNaive` для каждого уровня этого дерева:
- Для $n = 1$: 1 вызов (возвращает 1).
- Для $n = 2$: 1 вызов (возвращает 1).
- Для $n = 3$: вызывает `FibNaive(2)` и `FibNaive(1)` + сам вызов = 3 вызова.
- Для $n = 4$: вызывает `FibNaive(3)` и `FibNaive(2)` + сам вызов = $3 + 1 + 1 = 5$ вызовов.
- Для $n = 5$: вызывает `FibNaive(4)` и `FibNaive(3)` + сам вызов = $5 + 3 + 1 = 9$ вызовов.

Обратите внимание на структуру дерева. Одни и те же подзадачи вычисляются многократно независимо друг от друга. Например, вызов `FibNaive(3)` происходит дважды, а вызов `FibNaive(2)` — трижды. 

---

### Анализ сложности наивной рекурсии

С ростом параметра $n$ количество дублирующих вызовов начинает расти лавинообразно. 

Строгое математическое доказательство показывает, что число операций для вычисления $n$-го числа Фибоначчи наивным методом пропорционально золотому сечению в степени $n$:

$$
T(n) = O\left(\left(\frac{1 + \sqrt{5}}{2}\right)^n\right) \approx O(1{,}618^n)
$$

На практике это означает экспоненциальную сложность $O(2^n)$. Оценим время работы программы для небольших входных данных:
- При $n = 10$: около $55$ вызовов (моментально).
- При $n = 30$: более $1{,}3 \cdot 10^6$ вызовов (около доли секунды).
- При $n = 40$: более $2 \cdot 10^8$ вызовов (несколько секунд ожидания).
- При $n = 50$: более $2 \cdot 10^{10}$ вызовов (программа «зависнет» на несколько минут или даже часов).

Такое поведение делает наивную реализацию непригодной для практического использования при $n > 40$. Причина кроется в избыточности: компьютер тратит колоссальные ресурсы на повторное решение одних и тех же подзадач, которые он уже решал ранее.

### Понятие мемоизации

Чтобы избавиться от повторных вычислений, применяется техника **мемоизации** (от слова *memo*, а не *memory* — «памятка»). Идея заключается в том, чтобы запоминать (кэшировать) результат вычисления для каждого нового аргумента.

Когда методу требуется найти значение $F(n)$, он выполняет следующие действия:
1. Проверяет, был ли этот результат вычислен ранее.
2. Если результат уже есть в хранилище (кэше), метод мгновенно возвращает его, не выполняя новые рекурсивные погружения в стек.
3. Если результата нет, метод вычисляет его стандартным способом через рекурсию, но перед возвратом обязательно сохраняет в хранилище.

В качестве хранилища в языке C# удобно использовать вспомогательный массив (если диапазон индексов заранее известен) или структуру `Dictionary<int, long>` (для произвольных или больших значений).

---

### Реализация мемоизации на массиве

Рассмотрим реализацию вычисления чисел Фибоначчи с использованием массива для кэширования промежуточных результатов.

```csharp
using System;

class Program
{
    static long FibMemoized(int n, long[] memo)
    {
        // Базовый случай
        if (n == 1 || n == 2)
        {
            return 1;
        }

        // Шаг 1: Проверка наличия уже вычисленного значения в кэше.
        // Так как индексы массива начинаются с 0, а числа Фибоначчи с 1,
        // сохраним значение для n в ячейке memo[n].
        if (memo[n] != 0)
        {
            return memo[n];
        }

        // Шаг 2: Если в кэше пусто, вычисляем рекурсивно
        memo[n] = FibMemoized(n - 1, memo) + FibMemoized(n - 2, memo);

        // Шаг 3: Возвращаем посчитанное значение
        return memo[n];
    }

    static void Main()
    {
        int n = 5;
        
        // Создаем массив для мемоизации размером (n + 1), 
        // чтобы индексы совпадали с номерами чисел Фибоначчи.
        // По умолчанию все элементы массива типа long инициализируются нулями.
        long[] memo = new long[n + 1];

        long result = FibMemoized(n, memo);
        Console.WriteLine($"FibMemoized({n}) = {result}");
    }
}
```

## Типичные ошибки

1. **Отсутствие базового случая (условия выхода)**
   * *В чём ошибка:* Метод вызывает сам себя бесконечно, не имея точки остановки.
   * *Почему возникает:* Забыли прописать проверку `if (n == 0)` или `if (arr.Length == 0)`.
   * *Как избежать:* Всегда начинайте проектирование рекурсии с ответа на вопрос: «При каком самом простом аргументе ответ очевиден?» Запишите этот базовый случай в самом начале метода.
   * *Пример:* `static int Bad(int n) { return n + Bad(n - 1); }` приводит к фатальному `StackOverflowException`.

2. **Отсутствие изменения аргумента (удаления от базового случая)**
   * *В чём ошибка:* Базовый случай написан, но аргумент при вызове не приближается к нему (например, передается `n` вместо `n - 1` или `n + 1`).
   * *Почему возникает:* Опечатка в формуле рекурсивного шага.
   * *Как избежать:* Убедитесь, что на каждом шаге параметр строго уменьшается (или увеличивается) в сторону базового значения.
   * *Пример:* `if (n == 0) return 0; return n + Rec(n);` — аргумент не меняется, стек переполняется.

3. **Использование глобальных переменных вместо возврата значений через `return`**
   * *В чём ошибка:* Накопление результатов в статических полях класса (`sum += x`).
   * *Почему возникает:* Перенос привычки использовать линейные циклы внутрь рекурсивной функции.
   * *Как избежать:* Проектируйте чистые функции: каждый вызов должен возвращать результат подзадачи через `return`, а родительский метод — принимать его и объединять.
   * *Пример:* `static int total = 0; static void Add(int n) { total += n; Add(n-1); }` — делает метод небезопасным при повторных вызовах.

4. **Путаница между прямым и обратным ходом рекурсии**
   * *В чём ошибка:* Инструкция печати или обработки данных написана до рекурсивного вызова, хотя требовалось получить обратный порядок (или наоборот).
   * *Почему возникает:* Непонимание того, в какой момент выполняются строчки кода — при погружении или при размотке стека.
   * *Как избежать:* Помните правило: код *до* вызова выполняется сверху вниз (прямой ход), код *после* вызова — снизу вверх (обратный ход, при размотке стека).

5. **Переполнение стека вызовов (`StackOverflowException`) на больших данных**
   * *В чём ошибка:* Попытка решить рекурсивно задачу с большой глубиной (например, обход массива из 100 000 элементов).
   * *Почему возникает:* Игнорирование аппаратных ограничений стека оперативной памяти (обычно около 1 МБ).
   * *Как избежать:* Если глубина рекурсии превышает несколько тысяч шагов или заранее неизвестна, переписывайте алгоритм в итеративной форме (через циклы `for`/`while`) или используйте явные структуры данных в куче (`Stack<T>`).

6. **Игнорирование мемоизации в задачах с пересекающимися подзадачами**
   * *В чём ошибка:* Прямая реализация рекурсии для чисел Фибоначчи или задач комбинаторики с экспоненциальной сложностью $O(2^n)$.
   * *Почему возникает:* Слепое перенесение рекуррентной формулы без анализа дерева вызовов.
   * *Как избежать:* Если дерево вызовов разветвляется и одни и те же аргументы вычисляются повторно, обязательно добавляйте кэширование (массив `memo` или `Dictionary`).

7. **Некорректная обработка граничных значений (нуль, отрицательные числа, пустые строки)**
   * *В чём ошибка:* Метод падает с исключением `ArgumentOutOfRangeException` или `IndexOutOfRangeException` при передаче нуля или отрицательного числа.
   * *Почему возникает:* Базовый случай покрывает только $n = 1$, но метод вызывают с $n = 0$.
   * *Как избежать:* Расширяйте условие базового случая на все допустимые граничные значения (`if (n <= 1)` вместо `if (n == 1)`).
