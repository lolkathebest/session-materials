## 1. Теоретический фундамент проектирования иерархий классов

### Понятие иерархии классов и отношение «is-a»

Объектно-ориентированное программирование (ООП) позволяет моделировать сложные предметные области, организуя типы данных в древовидные структуры — **иерархии классов**. В основе построения любой иерархии лежит отношение **«is-a»** (рус. *«является»*). 

> **Определение.** Отношение «is-a» — это концептуальная связь между двумя классами, при которой один класс (производный, или подкласс) представляет собой частный случай другого класса (базового, или суперкласса).

Например, если у нас есть класс `Employee` (Сотрудник), а также классы `Manager` (Менеджер) и `Developer` (Разработчик), то между ними выполняются утверждения: «Менеджер — это сотрудник» (`Manager is-a Employee`) и «Разработчик — это сотрудник» (`Developer is-a Employee`). Это означает, что `Manager` и `Developer` могут перенимать все общие свойства и поведение класса `Employee`, добавляя при этом собственную уникальную функциональность.

В языке C# наследование реализуется с помощью двоеточия `:` в объявлении класса:

```csharp
public class Employee 
{
    // Общие члены для всех сотрудников
}

public class Manager : Employee 
{
    // Уникальные члены для менеджера
}
```

Важно понимать архитектурный смысл: базовый класс аккумулирует универсальную логику, характерную для всех элементов группы, а производные классы специализируют эту логику под конкретные требования.

### Роль абстрактных классов как контрактов и базовых шаблонов

Иногда базовый класс представляет собой настолько общую концепцию, что создание его экземпляров в реальном мире не имеет никакого смысла. Например, абстрактное понятие «Фигура» (`Shape`) или «Сотрудник» (`Employee`) в чистом виде не существует — в компании работают конкретные люди: менеджеры, разработчики, бухгалтеры. Для реализации таких концепций в C# используются **абстрактные классы**.

> **Определение.** Абстрактный класс — это класс, помеченный ключевым словом `abstract`, экземпляр которого невозможно создать напрямую с помощью оператора `new`. Он служит базовым шаблоном (или контрактом) для других классов и может содержать как реализованные методы, так и абстрактные методы без тела.

Абстрактный метод объявляется с ключевым словом `abstract` и не содержит фигурных скобок реализации — только сигнатуру и точку с запятой. Любой неабстрактный производный класс *обязан* переопределить все унаследованные абстрактные методы, выполняя тем самым «контракт», навязанный базовым классом.

Рассмотрим пример на языке C#:

```csharp
public abstract class Employee 
{
    public string Name { get; set; }
    
    // Абстрактный метод: у каждого сотрудника расчет премии свой, 
    // поэтому тела здесь быть не может
    public abstract decimal CalculateBonus();
}

public class Developer : Employee 
{
    public int CompletedTasks { get; set; }

    // Обязательная реализация абстрактного метода базового класса
    public override decimal CalculateBonus() 
    {
        return CompletedTasks * 1500m;
    }
}
```

Если программист забудет реализовать метод `CalculateBonus()` в классе `Developer`, компилятор C# выдаст ошибку, гарантируя соблюдение архитектурного контракта.

### Механизм переопределения методов и позднее связывание

Чтобы производный класс мог изменить поведение метода, унаследованного от базового класса, используется механизм переопределения. В C# этот процесс разделен на два этапа:
1. В базовом классе метод помечается ключевым словом `virtual`, что разрешает его переопределение в потомках.
2. В производном классе метод помечается ключевым словом `override`.

> **Определение.** Позднее связывание (или динамическое диспетчеризация, *dynamic dispatch*) — это механизм времени выполнения программы, при котором вызов виртуального метода разрешается не по типу ссылки (переменной), а по фактическому типу объекта, на который эта ссылка указывает в памяти.

Без виртуальных методов C# использует раннее связывание (статическое полиморфное поведение), при котором тип вызываемого метода определяется на этапе компиляции на основе типа переменной. С ключевыми словами `virtual` и `override` компилятор генерирует специальную таблицу виртуальных методов (vtable), благодаря чему программа «знает», чей именно метод нужно запустить, даже если объект спрятан за ссылкой базового типа.

Пример реализации:

```csharp
public class Animal 
{
    public virtual void MakeSound() 
    {
        Console.WriteLine("Животное издает звук.");
    }
}

public class Cat : Animal 
{
    public override void MakeSound() 
    {
        Console.WriteLine("Мяу!");
    }
}

// Использование:
Animal myPet = new Cat();
myPet.MakeSound(); // Выведет: «Мяу!», несмотря на то, что тип ссылки — Animal
```

### Правила использования модификатора protected для инкапсуляции состояния внутри иерархии

При проектировании классов важно соблюдать принцип инкапсуляции, скрывая внутреннее состояние объекта от внешнего мира. Однако внутри иерархии классов часто возникает необходимость предоставить производным классам доступ к полям и методам родителя, оставляя их закрытыми для остальной программы. Для этой цели служит модификатор доступа `protected`.

> **Определение.** Модификатор доступа `protected` делает член класса видимым внутри самого класса, а также во всех классах-наследниках (включая многоуровневое наследование), независимо от того, находятся они в том же пространстве имен или в других сборках. Для всех остальных внешних классов члены с модификатором `protected` ведут себя точно так же, как `private`.

Сравним уровни доступа в таблице:

| Модификатор | Доступ внутри класса | Доступ в классах-наследниках | Доступ из любого другого кода |
| :--- | :--- | :--- | :--- |
| `public` | Да | Да | Да |
| `protected` | Да | Да | Нет |
| `internal` | Да | Да (внутри сборки) | Да (внутри сборки) |
| `private` | Да | Нет | Нет |

Правильное использование `protected` предотвращает загрязнение публичного интерфейса базового класса служебными методами и переменными, которые нужны исключительно для внутренней реализации потомков.

### Использование ключевого слова base

Когда создается объект производного класса, в памяти сначала выделяется место под все поля базового класса, а затем — под поля потомка. Это означает, что конструктор базового класса должен быть вызван *до* того, как начнет выполняться код конструктора производного класса.

> **Определение.** Ключевое слово `base` в C# используется внутри производного класса для обращения к членам непосредственного базового класса. Чаще всего оно применяется для явного вызова конструктора родителя с передачей ему необходимых параметров.

Если в базовом классе определен конструктор с параметрами, компилятор C# не создает конструктор по умолчанию автоматически. В этом случае производный класс обязан явно вызвать родительский конструктор через `base(...)`:

```csharp
public class Employee 
{
    public string Name { get; protected set; }
    public decimal BaseSalary { get; protected set; }

    public Employee(string name, decimal baseSalary) 
    {
        Name = name;
        BaseSalary = baseSalary;
    }
}

public class Manager : Employee 
{
    public decimal Allowance { get; set; }

    // Конструктор Manager вызывает конструктор базового класса Employee через base
    public Manager(string name, decimal baseSalary, decimal allowance) 
        : base(name, baseSalary) 
    {
        Allowance = allowance;
    }
}
```

Кроме инициализации конструкторов, `base` может применяться для вызова переопределенных методов родителя, если в потомке требуется дополнить, а не полностью заменить родительскую логику.

### Полиморфные коллекции

Одним из главных преимуществ иерархий классов является возможность работы с разнородными объектами единообразным способом. Это достигается за счет использования полиморфных коллекций.

> **Определение.** Полиморфная коллекция — это массив или обобщенный список (`List<T>`), объявленный с типом базового класса (или интерфейса), в котором хранятся экземпляры различных производных классов.

Благодаря восходящему преобразованию типов (*upcasting*), любой объект класса-наследника может быть без проблем помещен в коллекцию родительского типа. Когда программа перебирает элементы такой коллекции в цикле и вызывает виртуальный метод, срабатывает позднее связывание: для каждого конкретного объекта выполняется его собственная реализация метода.

```csharp
// Создаем список базового типа Employee, куда помещаем объекты разных подклассов
List<Employee> staff = new List<Employee>();
staff.Add(new Manager("Анна", 80000m, 15000m));
staff.Add(new Developer("Иван", 90000m, 12));

// Полиморфный обход коллекции: для каждого сотрудника вызывается свой метод расчета премии
foreach (Employee emp in staff) 
{
    Console.WriteLine($"{emp.Name}: бонус = {emp.CalculateBonus()} руб.");
}
```

Этот подход избавляет разработчика от необходимости писать громоздкие условные конструкции (`if-else` или `switch`) для проверки типа каждого объекта.

### Принцип подстановки Лисков (LSP) на практике

При проектировании иерархий необходимо следовать фундаментальному принципу объектно-ориентированного дизайна — **принципу подстановки Барбары Лисков (LSP)**.

> **Определение.** Принцип подстановки Лисков гласит: функции, которые используют базовые типы, должны иметь возможность работать с производными типами без необходимости знать об этом. Иными словами, объект базового класса может быть заменен объектом производного класса без нарушения корректности работы программы.

На практике в C# это означает:
1. Производный класс не должен усиливать требования к входным данным (предварительные условия), сужая логику базового класса.
2. Производный класс не должен ослаблять гарантии результатов (постусловия).
3. Производный класс не должен выбрасывать исключения (например, `NotImplementedException`), если базовый класс этого не предполагает.

Типичным нарушением LSP является ситуация, когда класс `Square` (Квадрат) наследуется от класса `Rectangle` (Прямоугольник) и переопределяет методы установки ширины и высоты так, чтобы они всегда были равны. Если участок кода ожидает прямоугольник и независимо меняет его стороны, логика для квадрата нарушится. Правильным решением в данном случае является отказ от наследования в пользу общих абстракций или интерфейсов.

### Типичные ошибки при проектировании глубоких и запутанных иерархий

Начинающие разработчики часто совершают типичные архитектурные ошибки:

1. **Избыточная глубина наследования (Deep Hierarchies).** Построение цепочек из 5–7 и более уровней классов (например, `Entity` -> `Actor` -> `Character` -> `MobileCharacter` -> `Humanoid` -> `Player` -> `Warrior`). Это приводит к сильной связанности кода, когда изменение в базовом классе случайно ломает работу всех нижележащих уровней.
2. **Наследование ради повторения кода (Code Reuse Abuse).** Использование наследования исключительно для того, чтобы «поделиться» методами между несвязанными классами. Если отношение «is-a» не выполняется (например, класс `Engine` наследуется от класса `Car`), такое наследование ошибочно. В таких случаях следует применять композицию (включение объектов одного класса в качестве полей другого).
3. **Нарушение инкапсуляции через чрезмерное использование `protected`.** Открытие слишком большого количества полей через `protected` превращает производные классы в «хрупкие», так как они начинают напрямую зависеть от внутренней структуры родителя.

### Разобранный пример: Иерархия сотрудников компании

#### Условие задачи
Спроектировать и реализовать консольное приложение на C# для учета сотрудников компании. 
1. Создать абстрактный базовый класс `Employee` со свойствами: имя (`Name`, доступное для чтения всем, запись защищена), базовый оклад (`BaseSalary`, защищенный). Класс должен содержать конструктор для инициализации этих полей и абстрактный метод `CalculateBonus()`, возвращающий премию в виде числа с плавающей точкой (`decimal`).
2. Создать производный класс `Manager` (Менеджер), который добавляет поле «сумма продаж» (`SalesAmount`) и реализует расчет премии: премия составляет $5{,}0\,\%$ от суммы продаж.
3. Создать производный класс `Developer` (Разработчик), который добавляет поле «количество закрытых задач» (`CompletedTasks`) и реализует расчет премии: по $1200{,}00$ рублей за каждую закрытую задачу.
4. В методе `Main` создать список сотрудников, содержащий объекты обоих производных классов, пройти по нему в цикле, вывести имя сотрудника и рассчитанную премию.

#### Рисунок схемы классов (в виде текста)
```
     +-----------------------------------+
     |        abstract class Employee    |
     +-----------------------------------+
     | - name: string                    |
     | - baseSalary: decimal             |
     +-----------------------------------+
     | + Employee(name, baseSalary)      |
     | + CalculateBonus(): abstract      |
     +-----------------------------------+
                   ^       ^
                   |       |
         +---------+       +---------+
         |                           |
+------------------------+ +------------------------+
|    class Manager       | |    class Developer     |
+------------------------+ +------------------------+
| - salesAmount: decimal | | - completedTasks: int  |
+------------------------+ +------------------------+
| + Manager(...)         | | + Developer(...)       |
| + CalculateBonus(): ovr| | + CalculateBonus(): ovr|
+------------------------+ +------------------------+
```

#### Ход рассуждений
1. **Абстрактный класс `Employee`**: Поскольку расчет премии у каждого сотрудника свой, единой формулы на уровне базового класса быть не может. Поэтому метод `CalculateBonus()` объявляется с ключевым словом `abstract`, а сам класс — как `abstract class`.
2. **Защита данных**: Поля `name` и `baseSalary` скрыты от внешнего кода с помощью модификатора `protected` для оклада и публичного свойства с защищенным сеттером (`public string Name { get; protected set; }`) для имени. Это обеспечивает соблюдение инкапсуляции.
3. **Конструкторы**: В классах `Manager` и `Developer` мы принимаем параметры для уникальных полей, а общие параметры (имя и оклад) передаем в родительский конструктор через ключевое слово `base(name, baseSalary)`.
4. **Полиморфизм**: Объявляя коллекцию как `List<Employee>`, мы можем добавлять в нее экземпляры `Manager` и `Developer`. Вызов метода `CalculateBonus()` внутри цикла `foreach` автоматически разрешится в нужную реализацию благодаря позднему связыванию (`virtual` / `override`).

#### Полный исходный код программы

```csharp
using System;
using System.Collections.Generic;

namespace CompanyApp
{
    // Абстрактный базовый класс
    public abstract class Employee 
    {
        public string Name { get; protected set; }
        protected decimal baseSalary;

        // Конструктор базового класса
        protected Employee(string name, decimal baseSalary) 
        {
            Name = name;
            this.baseSalary = baseSalary;
        }

        // Абстрактный метод для расчета премии (должен быть переопределен в потомках)
        public abstract decimal CalculateBonus();

        // Виртуальный метод для получения общей информации
        public virtual void DisplayInfo() 
        {
            Console.WriteLine($"Сотрудник: {Name}, Базовый оклад: {baseSalary:F2} руб.");
        }
    }

    // Производный класс: Менеджер
    public class Manager : Employee 
    {
        private decimal salesAmount;

        public Manager(string name, decimal baseSalary, decimal salesAmount) 
            : base(name, baseSalary) 
        {
            this.salesAmount = salesAmount;
        }

        // Реализация абстрактного метода для менеджера (5% от продаж)
        public override decimal CalculateBonus() 
        {
            return salesAmount * 0.05m;
        }

        public override void DisplayInfo() 
        {
            base.DisplayInfo();
            Console.WriteLine($"  Должность: Менеджер (Продажи: {salesAmount:F2} руб.)");
        }
    }

    // Производный класс: Разработчик
    public class Developer : Employee 
    {
        private int completedTasks;

        public Developer(string name, decimal baseSalary, int completedTasks) 
            : base(name, baseSalary) 
        {
            this.completedTasks = completedTasks;
        }

        // Реализация абстрактного метода для разработчика (1200 руб. за задачу)
        public override decimal CalculateBonus() 
        {
            return completedTasks * 1200.00m;
        }

        public override void DisplayInfo() 
        {
            base.DisplayInfo();
            Console.WriteLine($"  Должность: Разработчик (Закрыто задач: {completedTasks})");
        }
    }

    class Program 
    {
        static void Main(string[] args) 
        {
            // Настройка кодировки консоли для корректного отображения кириллицы
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            // Создание полиморфной коллекции сотрудников
            List<Employee> companyStaff = new List<Employee>();

            companyStaff.Add(new Manager("Елена Смирнова", 50000.00m, 400000.00m));
            companyStaff.Add(new Developer("Алексей Петров", 75000.00m, 15));
            companyStaff.Add(new Manager("Дмитрий Иванов", 55000.00m, 650000.00m));

            // Обход коллекции и полиморфный вызов методов
            foreach (Employee emp in companyStaff) 
            {
                emp.DisplayInfo();
                decimal bonus = emp.CalculateBonus();
                Console.WriteLine($"  Расчетная премия: {bonus:F2} руб.\n");
            }
        }
    }
}
```

## 2. Задачи базового уровня: простые иерархии и переопределение методов

### Анализ условия задачи с выделением общих свойств и уникального поведения

Прежде чем приступать к написанию кода на C#, необходимо спроектировать будущую иерархию классов. Любое объектно-ориентированное решение начинается с анализа предметной области и выявления отношений между сущностями. В основе проектирования лежит отношение *«is-a»* («является»).

Если у нас есть несколько различных объектов (например, круг, прямоугольник, автомобиль, велосипед), у которых есть общие характеристики и общее поведение, но реализованное по-разному, мы выделяем общий базовый класс.
1. **Общие свойства (поля и свойства C#)** — это характеристики, присущие всем объектам рассматриваемой категории. Например, транспортное средство всегда имеет марку и скорость. Фигура на плоскости в рамках конкретной задачи может не иметь общих числовых характеристик координат, но её ключевое поведение — вычисление площади — свойственно им всем.
2. **Уникальное поведение (методы)** — это действия, которые выполняют объекты, но алгоритм выполнения зависит от конкретного типа. Например, транспортное средство движется (`Move()`), но автомобиль едет по дороге, используя двигатель, а велосипед катится за счет мускульной силы педалирования. Фигура вычисляет площадь (`GetArea()`), но формула для круга ($\pi r^2$) кардинально отличается от формулы для прямоугольника ($w \cdot h$).

Для реализации такого подхода в C# используются механизмы виртуальных (`virtual`) и переопределенных (`override`) методов. Базовый класс предоставляет «интерфейс по умолчанию» или объявляет метод виртуальным, а производные классы уточняют или полностью переопределяют эту логику под свои нужды.

---

### Создание базового класса с защищенными полями и конструктором

Инceğiализация объектов в иерархии идет снизу вверх: сначала отрабатывает конструктор базового класса, а затем конструктор производного класса. Для обеспечения инкапсуляции поля базового класса объявляются с модификатором доступа `protected`, что делает их доступными внутри самого базового класса и во всех его потомках, но скрывает от внешнего мира.

Рассмотрим первый пример из нашего плана: иерархия геометрических фигур.

```csharp
using System;

// Базовый класс для всех геометрических фигур
public class Shape
{
    // Защищенное поле, доступное в производных классах
    protected string name;

    // Конструктор базового класса
    public Shape(string name)
    {
        this.name = name;
    }

    // Виртуальный метод для вычисления площади. 
    // По умолчанию возвращает 0, так как у абстрактной "фигуры вообще" площади нет.
    public virtual double GetArea()
    {
        return 0.0;
    }

    // Виртуальный метод для получения информации о фигуре
    public virtual void PrintInfo()
    {
        Console.WriteLine($"Фигура: {name}");
    }
}
```

В данном коде класс `Shape` инкапсулирует общую концепцию фигуры. Модификатор `virtual` перед методом `GetArea()` разрешает производным классам переопределять этот метод с помощью ключевого слова `override`.

---

### Реализация производных классов с переопределением виртуальных методов

Производные классы наследуют все члены базового класса (кроме конструкторов) и могут добавлять собственные поля, свойства и методы, а также изменять унаследованное поведение. 

Для создания производного класса используется двоеточие (`:`), после которого указывается имя базового класса. Ключевое слово `base` позволяет передать параметры в конструктор базового класса.

Реализуем классы `Circle` (круг) и `Rectangle` (прямоугольник), унаследовав их от `Shape`:

```csharp
// Производный класс Круг
public class Circle : Shape
{
    // Уникальное поле для круга — радиус
    private double radius;

    // Конструктор класса Circle принимает имя и радиус
    public Circle(string name, double radius) : base(name)
    {
        // Проверка входных данных на корректность
        if (radius <= 0)
        {
            throw new ArgumentException("Радиус должен быть положительным числом.", nameof(radius));
        }
        this.radius = radius;
    }

    // Переопределение виртуального метода вычисления площади
    public override double GetArea()
    {
        return Math.PI * radius * radius;
    }

    // Переопределение метода вывода информации
    public override void PrintInfo()
    {
        Console.WriteLine($"Круг: {name}, Радиус: {radius}, Площадь: {GetArea():F2}");
    }
}

// Производный класс Прямоугольник
public class Rectangle : Shape
{
    // Уникальные поля для прямоугольника — ширина и высота
    private double width;
    private double height;

    // Конструктор класса Rectangle
    public Rectangle(string name, double width, double height) : base(name)
    {
        if (width <= 0 || height <= 0)
        {
            throw new ArgumentException("Ширина и высота должны быть положительными числами.");
        }
        this.width = width;
        this.height = height;
    }

    // Переопределение виртуального метода вычисления площади
    public override double GetArea()
    {
        return width * height;
    }

    // Переопределение метода вывода информации
    public override void PrintInfo()
    {
        Console.WriteLine($"Прямоугольник: {name}, Ширина: {width}, Высота: {height}, Площадь: {GetArea():F2}");
    }
}
```

### Полный пример 1: Расчет площадей фигур с использованием полиморфизма

Соберем компоненты первой задачи в единую консольную программу. Мы создадим массив ссылок базового типа `Shape[]`, заполним его объектами классов `Circle` и `Rectangle`, а затем в цикле вызовем методы вывода информации и вычисления площади. Благодаря механизму полиморфизма (позднего связывания), на этапе выполнения программы компилятор сам определит, чей именно метод `GetArea()` или `PrintInfo()` необходимо вызвать для каждого конкретного элемента массива.

```csharp
using System;

namespace ShapeHierarchyApp
{
    // Определение классов Shape, Circle, Rectangle (см. код выше)
    public class Shape
    {
        protected string name;

        public Shape(string name)
        {
            this.name = name;
        }

        public virtual double GetArea()
        {
            return 0.0;
        }

        public virtual void PrintInfo()
        {
            Console.WriteLine($"Фигура: {name}");
        }
    }

    public class Circle : Shape
    {
        private double radius;

        public Circle(string name, double radius) : base(name)
        {
            if (radius <= 0)
                throw new ArgumentException("Радиус должен быть больше нуля.");
            this.radius = radius;
        }

        public override double GetArea()
        {
            return Math.PI * radius * radius;
        }

        public override void PrintInfo()
        {
            Console.WriteLine($"Круг '{name}': радиус = {radius}, площадь = {GetArea():F2}");
        }
    }

    public class Rectangle : Shape
    {
        private double width;
        private double height;

        public Rectangle(string name, double width, double height) : base(name)
        {
            if (width <= 0 || height <= 0)
                throw new ArgumentException("Стороны должны быть больше нуля.");
            this.width = width;
            this.height = height;
        }

        public override double GetArea()
        {
            return width * height;
        }

        public override void PrintInfo()
        {
            Console.WriteLine($"Прямоугольник '{name}': ширина = {width}, высота = {height}, площадь = {GetArea():F2}");
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Установка кодировки для корректного отображения кириллицы в консоли
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            // Создание массива базового типа Shape, содержащего разнородные объекты
            Shape[] shapes = new Shape[]
            {
                new Circle("Большой круг", 5.0),
                new Rectangle("Квадратный стол", 4.0, 4.0),
                new Circle("Маленькая монетка", 1.2),
                new Rectangle("Строительный блок", 2.5, 6.0)
            };

            Console.WriteLine("--- Обработка полиморфного массива фигур ---");
            double totalArea = 0;

            // Обход массива в цикле
            foreach (Shape shape in shapes)
            {
                // Вызывается метод PrintInfo() конкретного производного класса
                shape.PrintInfo();
                
                // Суммирование площадей
                totalArea += shape.GetArea();
            }

            Console.WriteLine("--------------------------------------------");
            Console.WriteLine($"Суммарная площадь всех фигур: {totalArea:F2}");
        }
    }
}
```

### Анализ сложности алгоритмов создания и обхода объектов

При работе с иерархиями классов и массивами объектов важно понимать вычислительную сложность и затраты памяти.

1. **Сложность создания объектов ($O(1)$):**
   Выделение памяти под один объект производного класса происходит за константное время $O(1)$. Конструкторы базового и производного класса выполняют фиксированное число операций присваивания и проверки условий (если они есть).

2. **Сложность обхода полиморфной коллекции ($O(N)$):**
   Если у нас есть массив или список (например, `List<Shape>`) размером $N$, то проход по нему в цикле для вызова метода (например, `GetArea()` или `PrintInfo()`) имеет линейную сложность времени $O(N)$, где $N$ — количество элементов в коллекции.

3. **Накладные расходы полиморфизма (динамическое связывание):**
   В C# механизм виртуальных методов реализуется через таблицу виртуальных методов (*vtable*). При вызове виртуального метода через ссылку базового типа происходит один дополнительный уровень косвенной адресации (обращение к *vtable* для определения точного адреса метода выполняемого объекта). На современных процессорах эти накладные расходы ничтожно малы и не оказывают заметного влияния на производительность типичных бизнес-приложений, но их следует учитывать в системах реального времени с жесткими ограничениями по ресурсам.

### Проверка корректности работы конструкторов и инициализации через `base(...)`

Одной из самых частых ошибок начинающих программистов при проектировании иерархий является попытка напрямую обратиться к приватным (`private`) полям базового класса из производного класса или забыть вызвать конструктор базового класса.

* **Правило 1:** Если базовый класс не имеет конструктора без параметров (конструктора по умолчанию), компилятор C# выдаст ошибку в производном классе, если тот явно не вызовет доступный конструктор базового класса с помощью ключевого слова `base(...)`.
* **Правило 2:** Поля базового класса, к которым должен быть доступ у наследников, должны быть помечены модификатором `protected`, а не `private`. Однако лучшей практикой инкапсуляции считается оставление полей закрытыми (`private`) и предоставление доступа к ним через защищенные свойства (`protected properties`).

Пример правильной организации через защищенное свойство:

```csharp
public class Employee
{
    private string fullName; // Закрытое поле

    // Защищенное свойство для доступа из потомков
    protected string FullName
    {
        get => fullName;
        set => fullName = string.IsNullOrWhiteSpace(value) ? "Неизвестно" : value;
    }

    public Employee(string name)
    {
        FullName = name;
    }
}
```

Это гарантирует, что даже внутри производных классов данные проходят валидацию, заложенную в базовом классе, что повышает общую надежность разрабатываемого программного обеспечения.

## 3. Задачи среднего уровня: абстрактные классы и полиморфные коллекции

### Абстрактные классы и полиморфные коллекции как инструменты проектирования

На предыдущих этапах изучения объектно-ориентированного программирования мы рассматривали стандартное наследование, где базовый класс содержал вполне рабочую реализацию методов, которую производные классы могли переопределять. Однако на практике часто возникают ситуации, когда базовое понятие является слишком общим, чтобы иметь конкретную реализацию. 

> **Определение.** *Абстрактный класс* — это класс, предназначенный исключительно для роли базового для других классов, который не позволяет создавать свои экземпляры напрямую через оператор `new`. Абстрактный класс может содержать как обычные поля, свойства и методы с готовой реализацией, так и *абстрактные методы* — методы без тела, которые производные классы обязаны реализовать принудительно.

Ключевые особенности абстрактных классов в C#:
1. Объявляются с ключевым словом `abstract`.
2. Экземпляр абстрактного класса создать нельзя (вызов `new MyAbstractClass()` приведёт к ошибке компиляции).
3. Абстрактный метод (`abstract void MethodName()`) не имеет реализации (нет фигурных скобок `{}`); он автоматически является виртуальным (`virtual`).
4. Любой неабстрактный производный класс *обязан* переопределить все унаследованные абстрактные методы с помощью ключевого слова `override`.

Такой подход гарантирует соблюдение контракта: программист, создающий новый подкласс, не сможет «забыть» реализовать ключевую функциональность, так как код просто не скомпилируется.

---

### Хранение разнородных объектов в коллекциях базового типа

Благодаря принципу подстановки (LSP), объект производного класса может быть присвоен переменной базового типа или помещён в коллекцию, параметризованную базовым классом. Например, если у нас есть абстрактный класс `Account`, то список `List<Account>` может содержать элементы типов `SavingsAccount`, `CreditAccount` и любых других потомков `Account` одновременно.

Когда мы вызываем метод у элементов такого списка, благодаря механизму позднего связывания (dynamic dispatch) среда выполнения .NET сама определяет, чей именно метод (`override`) нужно запустить для конкретного объекта в памяти. Это и есть классический *полиморфизм*.

---

### Проверка типов и безопасное приведение: операторы `is` и `as`

При работе с полиморфными коллекциями `List<BaseClass>` часто возникает задача: получить доступ к специфическому методу или свойству производного класса, которого нет в базовом классе. Поскольку коллекция хранит элементы как `BaseClass`, прямой вызов уникального метода вызовет ошибку компиляции.

Для решения этой проблемы в C# используются два оператора:
1. `is` — проверяет, совместим ли объект с заданным типом, возвращая `true` или `false`.
2. `as` — выполняет попытку приведения объекта к указанному типу. Если приведение невозможно, результат равен `null` (в отличие от прямого приведения в круглых скобках `(TargetType)obj`, которое выбрасывает исключение `InvalidCastException` при ошибке).

Пример безопасного использования:
```csharp
Account item = list[0];

// Проверяем тип и приводим в одну строчку (современный синтаксис C#)
if (item is SavingsAccount savings)
{
    // Переменная savings уже приведена и доступна здесь
    savings.AddBonus(); 
}
```

### Задача 1. Система учета банковских счетов

#### Условие
Разработать консольную систему учета банковских счетов на C#. 
1. Создать абстрактный базовый класс `Account`, содержащий защищенные поля: номер счета (`string accountNumber`) и текущий баланс (`decimal balance`). Предусмотреть защищенный конструктор, свойства с проверкой корректности данных (баланс не может быть отрицательным при инициализации, номер счета не должен быть пустым) и абстрактный метод `CalculateInterest()` для начисления процентов или списания комиссий.
2. Реализовать производный класс `SavingsAccount` (сберегательный счет), который хранит фиксированную процентную ставку (например, в процентах годовых) и реализует метод начисления процентов: увеличивает баланс на сумму начисленных процентов (`balance * rate / 100`).
3. Реализовать производный класс `CreditAccount` (кредитный счет), который хранит фиксированную комиссию за обслуживание и реализует метод расчета: уменьшает баланс на величину комиссии.
4. В методе `Main` создать список счетов `List<Account>`, добавить туда не менее трех объектов разных типов, программно запустить начисление для каждого счета через полиморфный вызов, а затем вычислить и вывести общую сумму денежных средств на всех счетах.

#### Рисунок схемы данных (текстовая схема)
```text
      +-------------------------ros------------------------+
      |               abstract class Account               |
      |----------------------------------------------------|
      | # accountNumber : string                           |
      | # balance : decimal                                |
      |----------------------------------------------------|
      | + Account(number: string, initialBalance: decimal) |
      | + Balance : decimal { get }                        |
      | + AccountNumber : string { get }                   |
      | + abstract CalculateInterest() : void              |
      +----------------------------------------------------+
                                ^
                                |  наследование
                +---------------+---------------+
                |                               |
+-------------------------------+ +-------------------------------+
|     class SavingsAccount      | |      class CreditAccount      |
|-------------------------------| |-------------------------------|
| - interestRate : decimal      | | - monthlyFee : decimal        |
|-------------------------------| |-------------------------------|
| + SavingsAccount(...)         | | + CreditAccount(...)          |
| + override CalculateInterest()| | + override CalculateInterest()|
+-------------------------------+ +-------------------------------+
```

#### Ход рассуждений
1. **Инкапсуляция и защита данных**: Поля `accountNumber` и `balance` делаем `protected`, чтобы производные классы имели к ним прямой доступ, но внешний код мог взаимодействовать с ними только через публичные свойства `AccountNumber` и `Balance`. В свойствах пропишем валидацию: если передано пустой номер счета, выбрасываем исключение `ArgumentException`.
2. **Конструкторы**: Базовый класс должен инициализировать общие поля. В производных классах используем ключевое слово `base(number, balance)` для передачи аргументов в конструктор предка.
3. **Полиморфизм**: Метод `CalculateInterest()` объявляется как `abstract` в `Account`, а в классах `SavingsAccount` и `CreditAccount` переопределяется через `override`. Это позволит в главном цикле программы вызывать `acc.CalculateInterest()` для каждого элемента списка `List<Account>`, не вдаваясь в подробности конкретного типа счета.

#### Полный исходный код программы

```csharp
using System;
using System.Collections.Generic;

namespace BankSystemApp
{
    // Абстрактный базовый класс банковского счета
    public abstract class Account
    {
        protected string accountNumber;
        protected decimal balance;

        // Конструктор базового класса
        protected Account(string accountNumber, decimal initialBalance)
        {
            if (string.IsNullOrWhiteSpace(accountNumber))
            {
                throw new ArgumentException("Номер счета не может быть пустым.", nameof(accountNumber));
            }
            if (initialBalance < 0)
            {
                throw new ArgumentException("Начальный баланс не может быть отрицательным.", nameof(initialBalance));
            }

            this.accountNumber = accountNumber;
            this.balance = initialBalance;
        }

        // Публичные свойства для безопасного чтения данных (инкапсуляция)
        public string AccountNumber => accountNumber;
        
        public decimal Balance => balance;

        // Абстрактный метод для расчета процентов или комиссий
        public abstract void CalculateInterest();

        // Виртуальный метод для вывода базовой информации
        public virtual void DisplayInfo()
        {
            Console.WriteLine($"Счет: {accountNumber}, Баланс: {balance:0.00} руб.");
        }
    }

    // Сберегательный счет
    public class SavingsAccount : Account
    {
        private decimal interestRate; // Процентная ставка (например, 5.0 для 5%)

        public SavingsAccount(string accountNumber, decimal initialBalance, decimal interestRate) 
            : base(accountNumber, initialBalance)
        {
            if (interestRate < 0)
            {
                throw new ArgumentException("Процентная ставка не может быть отрицательной.");
            }
            this.interestRate = interestRate;
        }

        // Реализация абстрактного метода
        public override void CalculateInterest()
        {
            decimal interest = balance * (interestRate / 100m);
            balance += interest;
            Console.WriteLine($"[Сберегательный] Начислены проценты ({interestRate}%): +{interest:0.00} руб.");
        }

        public override void DisplayInfo()
        {
            Console.Write($"[Сберегательный] ");
            base.DisplayInfo();
            Console.WriteLine($"  Ставка: {interestRate}% годовых");
        }
    }

    // Кредитный счет
    public class CreditAccount : Account
    {
        private decimal monthlyFee; // Ежемесячная комиссия за обслуживание

        public CreditAccount(string accountNumber, decimal initialBalance, decimal monthlyFee) 
            : base(accountNumber, initialBalance)
        {
            if (monthlyFee < 0)
            {
                throw new ArgumentException("Комиссия не может быть отрицательной.");
            }
            this.monthlyFee = monthlyFee;
        }

        // Реализация абстрактного метода
        public override void CalculateInterest()
        {
            balance -= monthlyFee;
            Console.WriteLine($"[Кредитный] Списана комиссия за обслуживание: -{monthlyFee:0.00} руб.");
        }

        public override void DisplayInfo()
        {
            Console.Write($"[Кредитный] ");
            base.DisplayInfo();
            Console.WriteLine($"  Комиссия: {monthlyFee:0.00} руб.");
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Установка кодировки для корректного отображения кириллицы в консоли
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            // Создание полиморфного списка счетов
            List<Account> accounts = new List<Account>
            {
                new SavingsAccount("ACC-101", 50000.00m, 7.5m),
                new CreditAccount("ACC-102", 15000.00m, 350.00m),
                new SavingsAccount("ACC-103", 120000.00m, 6.0m),
                new CreditAccount("ACC-104", 5400.00m, 200.00m)
            };

            Console.WriteLine("=== Состояние счетов до обработки ===");
            foreach (var acc in accounts)
            {
                acc.DisplayInfo();
            }
            Console.WriteLine();

            Console.WriteLine("=== Выполнение расчетного периода (начисление процентов/комиссий) ===");
            foreach (var acc in accounts)
            {
                // Полиморфный вызов: для сберегательного сработает свой метод, для кредитного — свой
                acc.CalculateInterest();
            }
            Console.WriteLine();

            Console.WriteLine("=== Состояние счетов после обработки ===");
            decimal totalBalance = 0;
            foreach (var acc in accounts)
            {
                acc.DisplayInfo();
                totalBalance += acc.Balance; // Суммируем балансы всех счетов
                Console.WriteLine();
            }

            Console.WriteLine($"--------------------------------------------------");
            Console.WriteLine($"Общая сумма денежных средств на всех счетах: {totalBalance:0.00} руб.");
        }
    }
}
```

### Задача 2. Иерархия медиафайлов и фильтрация коллекции

#### Условие
Создать иерархию классов для учета медиафайлов в цифровом каталоге.
1. Разработать абстрактный базовый класс `MediaFile`, содержащий защищенные поля: название файла (`string title`) и размер в мегабайтах (`double sizeMb`). Предусмотреть абстрактный метод `GetFileInfo()` возвращающий подробную строку с описанием характеристик файла, а также публичные свойства для получения значений полей.
2. Создать производный класс `AudioFile` (аудиофайл), содержащий дополнительное поле: длительность в секундах (`int durationSeconds`).
3. Создать производный класс `VideoFile` (видеофайл), содержащий дополнительное поле: разрешение экрана (`string resolution`, например, `"1920x1080"`).
4. Написать консольную программу, которая формирует список медиафайлов (`List<MediaFile>`), содержащий объекты обоих типов. Программа должна пройти по списку, вывести информацию о каждом файле, а также вычислить и вывести **суммарный объем (в мегабайтах) только видеофайлов**, используя оператор `is` для проверки типа элементов.

#### Ход рассуждений
1. **Проектирование иерархии**: Базовый класс инкапсулирует общие свойства файлов (`title` и `sizeMb`). Длительность и разрешение — это уникальные характеристики, поэтому они размещаются строго в соответствующих подклассах.
2. **Использование оператора `is`**: Поскольку задача требует вычислить суммарный объем *только видеофайлов*, на каждой итерации цикла по списку `List<MediaFile>` мы проверяем условие: `if (file is VideoFile video)`. Если объект является видеофайлом, переменная `video` автоматически получает правильный тип, и мы можем суммировать его свойство `SizeMb` (а также при необходимости использовать специфические для видео поля вроде разрешения).

#### Полный исходный код программы

```csharp
using System;
using System.Collections.Generic;

namespace MediaCatalogApp
{
    // Абстрактный базовый класс медиафайла
    public abstract class MediaFile
    {
        protected string title;
        protected double sizeMb;

        protected MediaFile(string title, double sizeMb)
        {
            if (string.IsNullOrWhiteSpace(title))
            {
                throw new ArgumentException("Название файла не может быть пустым.");
            }
            if (sizeMb <= 0)
            {
                throw new ArgumentException("Размер файла должен быть больше нуля.");
            }

            this.title = title;
            this.sizeMb = sizeMb;
        }

        public string Title => title;
        public double SizeMb => sizeMb;

        // Абстрактный метод возвращает строковое описание специфики файла
        public abstract string GetFileInfo();
    }

    // Производный класс: Аудиофайл
    public class AudioFile : MediaFile
    {
        private int durationSeconds;

        public AudioFile(string title, double sizeMb, int durationSeconds) 
            : base(title, sizeMb)
        {
            if (durationSeconds <= 0)
            {
                throw new ArgumentException("Длительность аудио должна быть положительной.");
            }
            this.durationSeconds = durationSeconds;
        }

        public int DurationSeconds => durationSeconds;

        public override string GetFileInfo()
        {
            int minutes = durationSeconds / 60;
            int seconds = durationSeconds % 60;
            return $"[Аудио] Название: \"{title}\", Размер: {sizeMb} МБ, Длительность: {minutes} мин {seconds} сек";
        }
    }

    // Производный класс: Видеофайл
    public class VideoFile : MediaFile
    {
        private string resolution;

        public VideoFile(string title, double sizeMb, string resolution) 
            : base(title, sizeMb)
        {
            if (string.IsNullOrWhiteSpace(resolution))
            {
                throw new ArgumentException("Разрешение видео не может быть пустым.");
            }
            this.resolution = resolution;
        }

        public string Resolution => resolution;

        public override string GetFileInfo()
        {
            return $"[Видео] Название: \"{title}\", Размер: {sizeMb} МБ, Разрешение: {resolution}";
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            // Формируем коллекцию разнородных медиафайлов
            List<MediaFile> catalog = new List<MediaFile>
            {
                new AudioFile("Rock Anthem", 8.5, 215),
                new VideoFile("Documentary Wildlife", 1450.0, "1920x1080"),
                new AudioFile("Classical Symphony", 25.4, 640),
                new VideoFile("Tutorial C# OOP", 850.5, "1280x720"),
                new AudioFile("Podcast Episode 12", 45.1, 1800),
                new VideoFile("Short Film Animation", 2100.0, "3840x2160")
            };

            Console.WriteLine("=== Полный каталог медиафайлов ===");
            foreach (var file in catalog)
            {
                // Полиморфный вызов GetFileInfo()
                Console.WriteLine(file.GetFileInfo());
            }
            Console.WriteLine();

            // Вычисление суммарного объема только видеофайлов с использованием оператора is
            double totalVideoSizeMb = 0;
            int videoCount = 0;

            foreach (var file in catalog)
            {
                // Проверяем, является ли элемент экземпляром класса VideoFile
                if (file is VideoFile video)
                {
                    totalVideoSizeMb += video.SizeMb;
                    videoCount++;
                    // Обратите внимание: здесь мы можем использовать уникальное свойство видеофайла
                    // Console.WriteLine($"Обработано видео с разрешением: {video.Resolution}");
                }
            }

            Console.WriteLine("=== Результаты анализа каталога ===");
            Console.WriteLine($"Найдено видеофайлов: {videoCount}");
            Console.WriteLine($"Суммарный объем видеофайлов: {totalVideoSizeMb:0.00} МБ");
        }
    }
}
```

## 4. Задачи сложного уровня: многоуровневое наследование и сложные бизнес-логики

### Архитектура многоуровневых иерархий и сложные бизнес-логики

В предыдущих разделах мы рассмотрели базовые и двухуровневые иерархии, где производные классы наследовались непосредственно от общего предка. Однако реальные предметные области обладают сложной структурой, в которой сущности образуют длинные цепочки специализации. Такие структуры требуют применения многоуровневого наследования, комбинации абстрактных классов, виртуальных и абстрактных методов, а также аккуратного управления состоянием на каждом уровне иерархии.

> **Определение.** Многоуровневое наследование — это организация классов, при которой производный класс сам является базовым для другого класса (цепочка наследования вида $A \to B \to C$).

В C# каждый класс может иметь только один прямой базовый класс (одиночное наследование реализации), что предотвращает проблему неоднозначности («проблема ромба»). Тем не менее, цепочки наследования могут быть любой глубины. Главное правило проектирования глубоких иерархий гласит: каждый следующий уровень должен добавлять новые специализированные характеристики или уточнять поведение, но не нарушать принцип подстановки Лисков (LSP).

Рассмотрим ключевые архитектурные приемы, которые применяются при создании сложных иерархий:

1. **Комбинация абстрактных и конкретных классов в цепочке.** Промежуточный класс в иерархии может быть абстрактным (`abstract`). Он может как реализовывать часть функционала, унаследованного от верхнего предка, так и оставлять некоторые методы абстрактными для реализации в конечных (листовых) классах.
2. **Делегирование инициализации через `base(...)`.** В многоуровневой иерархии каждый конструктор обязан корректно передать данные своему непосредственному предку. Цепочка вызовов конструкторов всегда идет снизу вверх (от дочернего класса к базовому), а выполнение кода конструкторов — сверху вниз.
3. **Защита инвариантов в конструкторах.** Сложные бизнес-логики часто накладывают строгие ограничения на значения полей (например, цена не может быть отрицательной, вес не может быть нулевым). Валидация должна производиться на ранних этапах — в конструкторах и свойствах — с генерацией исключений (`ArgumentException`, `ArgumentOutOfRangeException`).

### Разбор комплексной задачи: Иерархия интернет-магазина

Для закрепления материала спроектируем систему интернет-магазина с разветвленной трехуровневой иерархией товаров.

#### Условие задачи

Спроектировать иерархию классов для системы интернет-магазина со следующей структурой:
- Базовый класс `Product` (название, базовая цена).
- Промежуточный абстрактный класс `PhysicalProduct` (наследует `Product`), добавляющий вес и расчет стоимости доставки.
- Конечные классы `Book` (наследует `PhysicalProduct`, добавляет количество страниц) и `Electronics` (наследует `PhysicalProduct`, добавляет гарантийный срок в месяцах).
- Конечный класс `DigitalProduct` (наследует напрямую `Product`, добавляет объем в гигабайтах).

Требуется разработать консольное приложение на C#, которое:
1. Создает коллекцию полиморфных товаров различных типов.
2. Проверяет корректность входных данных (выбрасывает исключения при некорректной цене, весе или объеме).
3. Рассчитывает итоговую стоимость каждого товара по индивидуальным правилам:
   - Для `Book`: базовая цена + фиксированная стоимость доставки за килограмм.
   - Для `Electronics`: базовая цена + повышенная стоимость доставки + налог на сложное оборудование.
   - Для `DigitalProduct`: базовая цена + лицензионный налог, зависящий от объема в ГБ.
4. Выводит общую информацию о товарах, выполняет фильтрацию по типу с использованием оператора `is` и вычисляет общую стоимость заказа.

### Пошаговый ход рассуждений

1. **Проектирование класса `Product`:**
   У любого товара есть название (`string name`) и базовая цена (`decimal basePrice`). Поскольку `Product` является базовым понятием, сделаем его абстрактным классом с абстрактным методом `CalculateFinalPrice()`, который каждый потомок обязан реализовать по-своему. Защищенный модификатор `protected` или свойства с закрытыми сеттерами (`private set`) обеспечат инкапсуляцию.

2. **Проектирование промежуточного класса `PhysicalProduct`:**
   Физические товары обладают весом (`decimal weightInKg`). Стоимость доставки зависит от веса. Мы можем реализовать часть логики прямо здесь: например, сделать метод расчета доставки общим, но оставить расчет полной стоимости (`CalculateFinalPrice`) на усмотрение конкретных товаров (`Book` и `Electronics`).

3. **Проектирование конечных классов (`Book`, `Electronics`, `DigitalProduct`):**
   - `Book` добавляет количество страниц (`int pageCount`). Стоимость доставки физического товара умножается на его вес.
   - `Electronics` добавляет гарантию (`int warrantyMonths`). Если гарантия больше 12 месяцев, добавляется страховой коэффициент к доставке.
   - `DigitalProduct` наследуется от `Product` напрямую, так как у него нет физического веса и доставки, но есть налог за скачивание, зависящий от объема (`double sizeInGb`).

### Полный исходный код программы

Ниже представлен полностью компилируемый код программы на языке C# (.NET 8), реализующий описанную бизнес-логику.

```csharp
using System;
using System.Collections.Generic;

namespace InternetShop
{
    // Базовый абстрактный класс товара
    public abstract class Product
    {
        private string _name;
        private decimal _basePrice;

        public string Name
        {
            get => _name;
            set
            {
                if (string.IsNullOrWhiteSpace(value))
                    throw new ArgumentException("Название товара не может быть пустым.");
                _name = value.Trim();
            }
        }

        public decimal BasePrice
        {
            get => _basePrice;
            set
            {
                if (value < 0m)
                    throw new ArgumentOutOfRangeException(nameof(value), "Базовая цена не может быть отрицательной.");
                _basePrice = value;
            }
        }

        protected Product(string name, decimal basePrice)
        {
            Name = name;
            BasePrice = basePrice;
        }

        // Абстрактный метод для расчета итоговой стоимости с учетом специфики товара
        public abstract decimal CalculateFinalPrice();

        public virtual void DisplayInfo()
        {
            Console.WriteLine($"Товар: {Name}, Базовая цена: {BasePrice:0{,}00} руб.");
        }
    }

    // Промежуточный абстрактный класс для физических товаров
    public abstract class PhysicalProduct : Product
    {
        private decimal _weightInKg;

        public decimal WeightInKg
        {
            get => _weightInKg;
            set
            {
                if (value <= 0m)
                    throw new ArgumentOutOfRangeException(nameof(value), "Вес физического товара должен быть больше нуля.");
                _weightInKg = value;
            }
        }

        protected PhysicalProduct(string name, decimal basePrice, decimal weightInKg)
            : base(name, basePrice)
        {
            WeightInKg = weightInKg;
        }

        // Базовый расчет стоимости доставки: 150 рублей за каждый килограмм веса
        public virtual decimal CalculateDeliveryCost()
        {
            return WeightInKg * 150.0m;
        }

        public override void DisplayInfo()
        {
            base.DisplayInfo();
            Console.WriteLine($"  [Физический товар] Вес: {WeightInKg:0{,}0} кг, Доставка: {CalculateDeliveryCost():0{,}00} руб.");
        }
    }

    // Класс Книга (наследник PhysicalProduct)
    public class Book : PhysicalProduct
    {
        private int _pageCount;

        public int PageCount
        {
            get => _pageCount;
            set
            {
                if (value <= 0)
                    throw new ArgumentOutOfRangeException(nameof(value), "Количество страниц должно быть положительным числом.");
                _pageCount = value;
            }
        }

        public Book(string name, decimal basePrice, decimal weightInKg, int pageCount)
            : base(name, basePrice, weightInKg)
        {
            PageCount = pageCount;
        }

        // Итоговая цена книги = базовая цена + доставка (без дополнительных налогов)
        public override decimal CalculateFinalPrice()
        {
            return BasePrice + CalculateDeliveryCost();
        }

        public override void DisplayInfo()
        {
            Console.Write("Книга -> ");
            base.DisplayInfo();
            Console.WriteLine($"  Страниц: {PageCount}, Итоговая стоимость: {CalculateFinalPrice():0{,}00} руб.");
        }
    }

    // Класс Электроника (наследник PhysicalProduct)
    public class Electronics : PhysicalProduct
    {
        private int _warrantyMonths;

        public int WarrantyMonths
        {
            get => _warrantyMonths;
            set
            {
                if (value < 0)
                    throw new ArgumentOutOfRangeException(nameof(value), "Гарантийный срок не может быть отрицательным.");
                _warrantyMonths = value;
            }
        }

        public Electronics(string name, decimal basePrice, decimal weightInKg, int warrantyMonths)
            : base(name, basePrice, weightInKg)
        {
            WarrantyMonths = warrantyMonths;
        }

        // Для электроники доставка дороже на 30%, плюс страховка за каждый месяц гарантии (по 50 руб.)
        public override decimal CalculateDeliveryCost()
        {
            decimal baseDelivery = base.CalculateDeliveryCost();
            decimal insurance = WarrantyMonths * 50.0m;
            return (baseDelivery * 1{,}3m) + insurance;
        }

        // Итоговая цена электроники = базовая цена + усложненная доставка + налог на сложность (5% от базы)
        public override decimal CalculateFinalPrice()
        {
            decimal complexityTax = BasePrice * 0{,}05m;
            return BasePrice + CalculateDeliveryCost() + complexityTax;
        }

        public override void DisplayInfo()
        {
            Console.Write("Электроника -> ");
            base.DisplayInfo();
            Console.WriteLine($"  Гарантия: {WarrantyMonths} мес., Итоговая стоимость: {CalculateFinalPrice():0{,}00} руб.");
        }
    }

    // Цифровой товар (наследуется напрямую от Product)
    public class DigitalProduct : Product
    {
        private double _sizeInGb;

        public double SizeInGb
        {
            get => _sizeInGb;
            set
            {
                if (value <= 0)
                    throw new ArgumentOutOfRangeException(nameof(value), "Объем цифрового файла должен быть больше нуля.");
                _sizeInGb = value;
            }
        }

        public DigitalProduct(string name, decimal basePrice, double sizeInGb)
            : base(name, basePrice)
        {
            SizeInGb = sizeInGb;
        }

        // Итоговая цена цифрового товара = базовая цена + лицензионный сбор (10 рублей за каждый гигабайт)
        public override decimal CalculateFinalPrice()
        {
            decimal licenseFee = (decimal)SizeInGb * 10.0m;
            return BasePrice + licenseFee;
        }

        public override void DisplayInfo()
        {
            Console.Write("Цифровой товар -> ");
            base.DisplayInfo();
            Console.WriteLine($"  Объем: {SizeInGb:0{,}0} ГБ, Итоговая стоимость: {CalculateFinalPrice():0{,}00} руб.");
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Установка кодировки консоли для корректного отображения кириллицы
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            try
            {
                // Создание полиморфной коллекции товаров
                List<Product> cart = new List<Product>
                {
                    new Book("Программирование на C#", 1200.0m, 0{,}8m, 450),
                    new Electronics("Смартфон", 35000.0m, 0{,}4m, 24),
                    new DigitalProduct("Операционная система", 5000.0m, 15.5),
                    new Book("Алгоритмы и структуры данных", 1800.0m, 1{,}2m, 600),
                    new Electronics("Беспроводные наушники", 4500.0m, 0{,}2m, 12)
                };

                Console.WriteLine("=== СОДЕРЖИМОЕ КОРЗИНЫ ЗАКАЗА ===");
                Console.WriteLine(new string('-', 50));

                decimal totalOrderCost = 0m;
                int physicalCount = 0;
                int digitalCount = 0;

                // Обход коллекции с использованием полиморфизма
                foreach (var product in cart)
                {
                    product.DisplayInfo();
                    
                    decimal finalPrice = product.CalculateFinalPrice();
                    totalOrderCost += finalPrice;

                    // Анализ типа с помощью оператора is
                    if (product is PhysicalProduct)
                    {
                        physicalCount++;
                    }
                    else if (product is DigitalProduct)
                    {
                        digitalCount++;
                    }

                    Console.WriteLine(new string('-', 50));
                }

                // Вывод агрегированных результатов
                Console.WriteLine("\n=== ИТОГИ ПО ЗАКАЗУ ===");
                Console.WriteLine($"Всего товаров в заказе: {cart.Count}");
                Console.WriteLine($"Физических товаров: {physicalCount}");
                console.WriteLine($"Цифровых товаров: {digitalCount}");
                Console.WriteLine($"Общая стоимость заказа: {totalOrderCost:0{,}00} руб.");

                // Демонстрация обработки исключений при некорректных данных
                Console.WriteLine("\n=== ТЕСТИРОВАНИЕ ВАЛИДАЦИИ ===");
                // Следующая строка вызовет исключение ArgumentOutOfRangeException
                // Product invalidProduct = new Book("Брак", -100m, 0.5m, 100);
                Console.WriteLine("Проверка конструкторов пройдена успешно. Ошибок валидации не обнаружено.");
            }
            catch (Exception ex)
            {
                Console.WriteLine($"Произошла ошибка: {ex.Message}");
            }
        }
    }
}
```

### Разбор кода и архитектурных решений

1. **Многоуровневая структура:** Цепочка `Product` $\to$ `PhysicalProduct` $\to$ `Book` / `Electronics` демонстрирует разделение обязанностей. Абстрактный класс `PhysicalProduct` инкапсулирует логику веса и базовой доставки, избавляя конечные классы от дублирования кода.
2. **Переопределение виртуальных методов (`override` и `virtual`):** Метод `CalculateDeliveryCost()` в классе `PhysicalProduct` объявлен как `virtual`. Класс `Electronics` переопределяет его (`override`), добавляя расчет страховки и надбавку за сложность, в то время как `Book` использует стандартную реализацию предка.
3. **Безопасное приведение типов и оператор `is`:** В цикле `foreach` мы обрабатываем разнородные объекты через базовую ссылку `Product`. Для подсчета количества физических и цифровых товаров применен оператор проверки типов `is`, который возвращает `true`, если объект принадлежит указанному типу или его наследникам.
4. **Инкапсуляция и защита инвариантов:** Свойства классов (`Name`, `BasePrice`, `WeightInKg`, `PageCount`, `WarrantyMonths`, `SizeInGb`) содержат жесткие проверки на уровне сеттеров и конструкторов. Это гарантирует, что в системе не появится товар с отрицательной ценой или нулевым весом.

### Оценка сложности и оптимизация памяти

- **Временная сложность:** Обход коллекции товаров для расчета итоговой стоимости занимает $O(n)$, где $n$ — количество элементов в списке `cart`. Вызов метода `CalculateFinalPrice()` разрешается во время выполнения через таблицу виртуальных методов (vtable), что добавляет минимальные накладные расходы, пренебрежимо малые для современных процессоров ($O(1)$ на один вызов).
- **Пространственная сложность:** Коллекция `List<Product>` хранит ссылки на объекты в куче (heap), в то время как сами ссылочные переменные размещаются в памяти. Для $n$ объектов пространственная сложность составляет $O(n)$.
- **Управление памятью:** В языке C# сборщик мусора (.NET GC) автоматически освобождает память из кучи, когда на объекты больше нет активных ссылок. Использование абстрактных классов и полиморфных ссылок не создает утечек памяти, если не удерживать ссылки на списки глобально без необходимости.

## Типичные ошибки

1. **Попытка создать экземпляр абстрактного класса.**
   * *Ошибка:* Написание кода вроде `Employee emp = new Employee("Иван", 50000);`, где `Employee` объявлен как `abstract class`.
   * *Почему возникает:* Непонимание природы абстрактных классов как неполных шаблонов, у которых нет полной реализации.
   * *Как избежать:* Создавать экземпляры только конкретных (неабстрактных) классов-потомков (`new Manager(...)`), сохраняя ссылку в переменной базового типа.

2. **Забытый вызов конструктора базового класса через `base(...)`.**
   * *Ошибка:* В производном классе объявлен конструктор, но компилятор выдает ошибку: *«У класса нет доступного конструктора без параметров»*.
   * *Почему возникает:* Если в базовом классе создан конструктор с параметрами, компилятор C# перестает генерировать конструктор по умолчанию. Потомок обязан явно указать, какой родительский конструктор вызвать.
   * *Как избежать:* Всегда добавлять двоеточие и вызов `base(param1, param2)` в заголовке конструктора производного класса.

3. **Использование модификатора `private` вместо `protected` для полей, к которым нужен доступ у потомков.**
   * *Ошибка:* Код в производном классе не может обратиться к полю родителя, компилятор жалуется на уровень доступа.
   * *Почему возникает:* Путаница между сокрытием данных от внешнего мира (`private`) и видимостью внутри иерархии.
   * *Как избежать:* Делать общие поля и методы защищенными (`protected`) либо использовать защищенные свойства с валидацией.

4. **Забытое ключевое слово `override` при переопределении метода.**
   * *Ошибка:* Метод в потомке скрывает метод родителя (warning CS0108), но полиморфизм через базовую ссылку не работает — вызывается метод предка.
   * *Почему возникает:* Пропуск ключевого слова `override` или отсутствие `virtual` у метода в базовом классе.
   * *Как избежать:* Всегда проверять сигнатуру: в базовом классе метод помечен как `virtual` (или `abstract`), в потомке — строго как `override`.

5. **Небезопасное приведение типов через круглые скобки `(TargetType)obj`.**
   * *Ошибка:* Возникновение исключения `InvalidCastException` во время выполнения программы при попытке привести объект одного подкласса к другому.
   * *Почему возникает:* Слепая уверенность в том, что элемент коллекции имеет конкретный тип, без предварительной проверки.
   * *Как избежать:* Использовать безопасное приведение с помощью оператора `is` (или паттерн-матчинга `if (obj is TargetType t)`) либо оператора `as`.

6. **Нарушение принципа подстановки Лисков (LSP).**
   * *Ошибка:* Переопределение метода в потомке так, что он выбрасывает `NotImplementedException` или меняет базовое поведение самым неожиданным образом.
   * *Почему возникает:* Проектирование иерархии ради «простоты общих названий», когда отношение «is-a» на самом деле не выполняется.
   * *Как избежать:* Убедиться, что любой объект потомка может полностью заменить объект предка в любом месте кода без нарушения логики.

7. **Прямое обращение к невалидным данным без проверки в конструкторах.**
   * *Ошибка:* Создание объектов с отрицательным балансом, нулевыми или пустыми строками параметров.
   * *Почему возникает:* Отсутствие валидации входных данных в конструкторах и свойствах.
   * *Как избежать:* Всегда проверять аргументы в конструкторах базовых и производных классов, выбрасывая `ArgumentException` или `ArgumentOutOfRangeException`.
