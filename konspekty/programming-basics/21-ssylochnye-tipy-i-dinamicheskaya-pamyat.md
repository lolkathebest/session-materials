## 1. Архитектура памяти в .NET: Стек и Куча

### Организация оперативной памяти в платформах .NET

Когда программа на C# запускается операционной системой, среда выполнения .NET (Common Language Runtime, CLR) запрашивает у операционной системы блок оперативной памяти. Эта память не используется хаотично: она строго структурирована. Для эффективного размещения данных и обеспечения высокой скорости выполнения кода CLR разделяет выделенную память на две основные логические области: **стек** (Stack) и **управляемую кучу** (Managed Heap).

> **Определение.** Стек (Stack) — это область памяти, организованная по принципу LIFO (Last In, First Out — «последним пришёл — первым ушёл»), которая используется для хранения локальных переменных методов, параметров методов и служебной информации о вызовах подпрограмм.

> **Определение.** Управляемая куча (Managed Heap) — это большая область динамической памяти, которой управляет сборщик мусора .NET (Garbage Collector), предназначенная для размещения объектов и массивов, размер или время жизни которых заранее неизвестны в момент компиляции.

Понимание того, как данные распределяются между стеком и кучей, является фундаментальным навыком для программиста. От этого зависит не только производительность разрабатываемых приложений, но и корректность их работы.

### Значимые и ссылочные типы на уровне памяти

Все типы данных в языке C# делятся на две большие категории: значимые типы (value types) и ссылочные типы (reference types). Различие между ними кроется в том, как именно их значения хранятся в памяти.

Значимые типы хранят сами данные непосредственно в том месте, где была объявлена переменная. Если переменная является локальной внутри метода, она размещается прямо в стеке. К значимым типам относятся все встроенные числовые типы (`int`, `double`, `float`, `decimal`, `char`, `bool`), перечисления (`enum`), а также структуры (`struct`).

Ссылочные типы устроены сложнее. Переменная ссылочного типа хранит не сами данные объекта, а адрес в памяти (ссылку), по которому эти данные располагаются. Сами данные (поля объекта) всегда размещаются в управляемой куче. К ссылочным типам относятся классы (`class`), интерфейсы (`interface`), делегаты (`delegate`), массивы (`array`) и строковый тип (`string`).

Сравним их характеристики в таблице ниже:

| Характеристика | Значимые типы (Value Types) | Ссылочные типы (Reference Types) |
|---|---|---|
| **Где хранятся** | Обычно в стеке (или внутри объекта в куче, если поле является частью класса) | В управляемой куче (переменная-ссылка лежит в стеке или куче, а сам объект — в куче) |
| **Что содержит переменная** | Само значение (например, число `42`) | Адрес ячейки памяти в куче (ссылка) |
| **Управление памятью** | Автоматически при выходе из области видимости | Автоматически с помощью сборщика мусора (Garbage Collector) |
| **Примеры в C#** | `int`, `double`, `bool`, `struct Point` | `string`, `int[]`, экземпляры пользовательских классов (`class`) |

### Поведение переменных при присваивании

Разница в хранении данных кардинально меняет поведение переменных при операциях присваивания и копирования.

При присваивании переменной значимого типа одной переменной другой происходит полное копирование содержимого. Создаётся независимый дубликат данных в новой ячейке памяти. Изменение одной переменной никак не отразится на значении другой.

При присваивании переменной ссылочного типа копируется не сам объект из кучи, а его адрес (ссылка). В результате обе переменные начинают указывать на один и тот же участок памяти в куче. Если изменить состояние объекта через первую переменную, эти изменения станут видны и при обращении ко второй переменной, так как сущность в куче всего одна.

---

### Передача параметров в методы

Аналогичное правило действует при передаче аргументов в методы. По умолчанию в C# все параметры передаются **по значению** (by value):

1. Для значимых типов в стек вызываемого метода копируется само значение переменной. Изменение параметра внутри метода не меняет исходную переменную, переданную при вызове.
2. Для ссылочных типов в стек вызываемого метода копируется значение адресной ссылки. Сам объект в куче не дублируется. Если внутри метода обратиться к полям переданного объекта и изменить их, то после выхода из метода изменения сохранятся, потому что метод работал с тем же самым объектом в куче. Однако если внутри метода присвоить параметру новый объект через оператор `new`, это изменит только локальную копию ссылки, а внешняя переменная продолжит указывать на старый объект.

---

### Управление временем жизни данных в стеке

Память в стеке работает чрезвычайно быстро. Когда выполнение программы доходит до объявления локальной переменной, в стеке под неё выделяется место. Управление этим процессом встроено в саму архитектуру процессорных инструкций.

Время жизни данных в стеке жестко привязано к блоку кода (фигурным скобкам `{ }`), в котором они объявлены:
- Когда управление входит в метод или блок кода, под его локальные переменные выделяется память на вершине стека («стековый кадр»).
- Когда выполнение выходит за пределы этого блока (например, метод завершает работу по оператору `return`), указатель стека просто смещается назад. Вся память, занятая локальными переменными этого метода, мгновенно становится доступной для перезаписи новыми данными. Никакого фонового процесса очистки для стека не требуется.

### Разобранный пример: трассировка памяти для значимых и ссылочных типов

Рассмотрим подробный пример, демонстрирующий совместную работу стека и управляемой кучи. Напишем фрагмент кода и проследим по шагам, как меняется состояние памяти.

```csharp
using System;

class Program
{
    static void Main()
    {
        int a = 5;
        Point p = new Point { X = 1, Y = 2 };
        
        ProcessData(a, p);
        
        Console.WriteLine($"a = {a}, p.X = {p.X}");
    }

    static void ProcessData(int val, Point pt)
    {
        val = 10;
        pt.X = 20;
    }
}

class Point
{
    int x_val;
    int y_val;

    public int X 
    { 
        get => x_val; 
        set => x_val = value; 
    }
    
    public int Y 
    { 
        get => y_val; 
        set => y_val = value; 
    }
}
```

#### Пошаговый разбор и трассировка

1. **Запуск метода `Main`**:
   Создается стековый кадр для метода `Main`.
   - Объявляется переменная `int a = 5`. Поскольку `int` — значимый тип, число `5` записывается прямо в ячейку памяти стека, выделенную под переменную `a`.
   - Выполняется инструкция `new Point { X = 1, Y = 2 }`. Ключевое слово `new` выделяет память в **управляемой куче** под экземпляр класса `Point`. Внутри этой области кучи размещаются поля объекта: `x_val = 1` и `y_val = 2`. Затем адрес этого участка кучи (например, `0x1000`) записывается в стековую переменную `p`, которая является ссылочным типом.

   *Состояние памяти после инициализации в `Main`:*
   - Стек `Main`:
     - `a` = `5`
     - `p` = `0x1000` (ссылка)
   - Управляемая куча:
     - адрес `0x1000`: объект `Point` (поля `x_val = 1`, `y_val = 2`)

2. **Вызов метода `ProcessData(a, p)`**:
   Создается новый стековый кадр для метода `ProcessData`, который располагается поверх стека `Main`.
   - Параметр `val` принимает копию значения переменной `a`. Теперь в стеке `ProcessData` существует независимая переменная `val` со значением `5`.
   - Параметр `pt` принимает копию значения переменной `p`. В переменную `pt` записывается тот же адрес `0x1000`. Теперь и `p` из `Main`, и `pt` из `ProcessData` указывают на один и тот же объект в куче.

   *Состояние памяти внутри `ProcessData`:*
   - Стек `ProcessData`:
     - `val` = `5`
     - `pt` = `0x1000` (ссылка)
   - Стек `Main` (временно недоступен для изменения):
     - `a` = `5`
     - `p` = `0x1000`
   - Управляемая куча:
     - адрес `0x1000`: объект `Point` (`x_val = 1`, `y_val = 2`)

3. **Выполнение инструкций внутри `ProcessData`**:
   - Строка `val = 10;` изменяет значение локальной переменной `val` в стеке `ProcessData`. Значение переменной `a` в стеке `Main` остается равным `5`.
   - Строка `pt.X = 20;` обращается по адресу `0x1000`, хранящемуся в `pt`, находит объект в куче и изменяет его поле `x_val` на `20`.

   *Состояние памяти после выполнения инструкций в `ProcessData`:*
   - Стек `ProcessData`:
     - `val` = `10`
     - `pt` = `0x1000`
   - Управляемая куча:
     - адрес `0x1000`: объект `Point` (`x_val = 20`, `y_val = 2`)

4. **Завершение метода `ProcessData` и возвращение в `Main`**:
   Стековый кадр метода `ProcessData` удаляется из памяти (указатель стека смещается назад). Переменные `val` и `pt` прекращают своё существование.
   Объект в куче по адресу `0x1000` продолжает жить, но теперь его поле `X` равно `20`.
   В методе `Main` выполняется вывод на консоль: `Console.WriteLine($"a = {a}, p.X = {p.X}");`

#### Проверка и анализ результата
- Переменная `a` сохранила свое исходное значение `5`, так как передавалась по значению как значимый тип.
- Свойство `p.X` выведет `20`, так как метод `ProcessData` изменил состояние объекта в управляемой куче, на который ссылалась переменная `p`.

Ответ:
```text
a = 5, p.X = 20
```

## 2. Ключевые слова new и null, исключения времени выполнения

### Назначение и работа оператора `new`

Как было показано в предыдущем разделе, переменные ссылочных типов хранят в стеке не сами данные объекта, а адрес памяти в управляемой куче, по которому эти данные расположены. Сама по себе объявленная переменная ссылочного типа в стеке занимает фиксированный объем памяти (4 байта в 32-битной архитектуре или 8 байт в 64-битной архитектуре), но этот ящичек в стеке изначально пуст или содержит недействительный адрес.

Чтобы создать полноценный объект в управляемой куче и связать его с переменной в стеке, используется ключевое слово `new`. 

> **Определение.** Оператор `new` в C# — это языковая конструкция, которая выполняет два основных действия: запрашивает у среды .NET выделение непрерывного блока памяти в управляемой куче под все поля объекта указанного типа, а затем вызывает специальный метод — конструктор — для инициализации этих полей начальными значениями.

Рассмотрим подробно по шагам, что происходит в памяти при выполнении строки кода:

```csharp
Student s = new Student();
```

1. **Фаза компиляции:** Компилятор C# проверяет, существует ли тип `Student`, доступен ли его конструктор и соответствуют ли типы данных.
2. **Фаза выполнения (выделение памяти):** Среда выполнения .NET (`CLR`) обращается к управляемой куче. Свободное пространство в куче организовано в виде указателя на следующий свободный байт. CLR вычисляет суммарный размер всех полей класса `Student` (с учетом служебных полей заголовка объекта, таких как индекс блока синхронизации и указатель на таблицу методов), увеличивает указатель свободного места на это значение и возвращает адрес только что выделенного блока памяти.
3. **Фаза инициализации:** Вызывается конструктор объекта (`Student()`). Поля объекта заполняются значениями по умолчанию (числа нулями, булевы переменные значением `false`, ссылки значением `null`), после чего выполняются инструкции, написанные внутри тела конструктора.
4. **Связывание:** Полученный в результате адрес памяти записывается в ячейку переменной `s`, которая располагается в стеке текущего метода.

Если памяти в управляемой куче недостаточно для размещения нового объекта, CLR инициирует работу сборщика мусора. Если и после этого свободное место не освободилось в нужном объеме, генерируется системное исключение `OutOfMemoryException`.

### Понятие нулевой ссылки (`null`) и инициализация по умолчанию

Что происходит с переменной ссылочного типа, если ее объявили, но оператор `new` для нее еще не вызывали? 

> **Определение.** Ключевое слово `null` в C# представляет собой литерал, обозначающий отсутствие ссылки, то есть состояние, когда ссылочная переменная не указывает ни на один объект в управляемой куче.

Физически в памяти для 64-битной архитектуры значение `null` записывается как последовательность из 64 нулей (`0x0000000000000000`), то есть нулевой адрес памяти. В операционных системах и средах выполнения адрес `0` зарезервирован и никогда не используется для размещения реальных пользовательских объектов, что позволяет однозначно отличать существующие объекты от их отсутствия.

Правила инициализации переменных по умолчанию в языке C# зависят от контекста их объявления:

- **Локальные переменные** (объявленные внутри методов) компилятор C# требует обязательно инициализировать перед первым использованием. Если написать код:
  ```csharp
  Student s;
  Console.WriteLine(s.Name); // Ошибка компиляции: Use of unassigned local variable 's'
  ```
  Компилятор не позволит скомпилировать такую программу, защищая от неопределенного поведения.
- **Поля классов и структур** (члены типов), напротив, автоматически инициализируются значениями по умолчанию при создании родительского объекта. Для всех ссылочных типов значением по умолчанию является `null`.

### Отличие пустой ссылки от пустого объекта

Начинающие разработчики часто путают два принципиально разных состояния: переменную, равную `null`, и объект, который существует в памяти, но не содержит полезных данных (например, все его строковые поля пустые или равны пустым строкам `""`).

Рассмотрим наглядное сравнение с помощью ASCII-схемы:

```text
СИТУАЦИЯ А: Ссылка равна null (объект не создан)
[ Стек ]                          [ Управляемая куча ]
 переменная s: [ 0x00000000 ] ---> (объекта нет, адрес нулевой)

СИТУАЦИЯ Б: Пустой объект (объект создан, но поля пустые)
[ Стек ]                          [ Управляемая куча ]
 переменная s: [ 0x007F10A0 ] ---> Адрес 0x007F10A0:
                                   ├── Имя: null (или "")
                                   └── Возраст: 0
```

В **ситуации А** попытка обратиться к любому полю или методу через переменную `s` приведет к аварийному завершению работы программы. В **ситуации Б** объект физически существует в памяти, у него есть выделенный адрес, и обращение к его полям или методам выполнится успешно, вернув значения по умолчанию (`0` или `null` для внутренних полей).

### Исключение времени выполнения: `NullReferenceException`

Самая частая ошибка при работе со ссылочными типами в C# — это попытка разыменования нулевой ссылки, то есть попытка прочитать или записать поле, либо вызвать метод у объекта, переменная которого равна `null`.

> **Определение.** `NullReferenceException` — это исключение времени выполнения (runtime exception), которое генерируется средой .NET, когда код пытается выполнить операцию доступа к члену объекта (поле, свойство, метод, индекс) через переменную, значение которой равно `null`.

Это ошибка проектирования программы, которая обнаруживается не на этапе компиляции, а в процессе работы приложения при наступлении определенного сценария ввода данных или логики.

#### Разобранный пример падения программы и его исправление

Представим класс, описывающий сотрудника компании, и консольное приложение, которое выводит информацию о его отделе.

**Ошибочный код (приводит к аварийному завершению):**

```csharp
using System;

class Department
{
    public string Title { get; set; }
}

class Employee
{
    public string FullName { get; set; }
    public Department WorkDepartment { get; set; } // Ссылка на отдел
}

class Program
{
    static void Main()
    {
        // Создаем сотрудника, но отдел ему НЕ назначаем (WorkDepartment останется равным null)
        Employee emp = new Employee
        {
            FullName = "Иванов Иван Иванович",
            WorkDepartment = null 
        }

        // Пытаемся получить название отдела
        Console.WriteLine("Сотрудник: " + emp.FullName);
        Console.WriteLine("Отдел: " + emp.WorkDepartment.Title); // ОШИБКА: NullReferenceException!
    }
}
```

**Ход рассуждений при поиске ошибки:**
1. Строка `Employee emp = new Employee ...` создает объект в куче, поле `FullName` получает строку `"Иванов Иван Иванович"`.
2. Поле `WorkDepartment` явно установлено в `null` (или не инициализировано, что дает тот же результат). В памяти в поле `WorkDepartment` записан адрес `0x0`.
3. В строке `Console.WriteLine("Отдел: " + emp.WorkDepartment.Title);` компилятор пытается выполнить две операции слева направо: сначала взять значение из поля `emp.WorkDepartment` (получает `null`), а затем попытаться прочитать свойство `.Title` по адресу `null`.
4. Так как по адресу `0x0` физически ничего нет, процессор и среда CLR прерывают выполнение программы и выбрасывают исключение `System.NullReferenceException: Object reference not set to an instance of an object.`

**Исправление ошибки с помощью проверки `if (obj != null)`:**

Чтобы программа не падала, перед обращением к членам ссылочного типа необходимо убедиться, что объект действительно создан в памяти.

```csharp
using System;

class Department
{
    public string Title { get; set; }
}

class Employee
{
    public string FullName { get; set; }
    public Department WorkDepartment { get; set; }
}

class Program
{
    static void Main()
    {
        Employee emp = new Employee
        {
            FullName = "Иванов Иван Иванович",
            WorkDepartment = null
        };

        Console.WriteLine("Сотрудник: " + emp.FullName);

        // Безопасная проверка перед доступом к членам объекта
        if (emp.WorkDepartment != null)
        {
            Console.WriteLine("Отдел: " + emp.WorkDepartment.Title);
        }
        else
        {
            Console.WriteLine("Отдел: Не назначен");
        }
    }
}
```

**Проверка и результат выполнения:**
* **Ввод:** отсутствуют внешние данные, значения заданы в коде.
* **Вывод программы:**
  ```text
  Сотрудник: Иванов Иван Иванович
  Отдел: Не назначен
  ```
* **Правдоподобность:** Программа не аварийно завершила работу, а корректно обработала отсутствие данных, выведя понятный пользователю текст.

### Современные средства защиты от `NullReferenceException` в C#

Помимо классической проверки через оператор `if`, современный язык C# (.NET 8) предоставляет мощные синтаксические инструменты для безопасной работы с потенциально нулевыми ссылками.

#### 1. Оператор условного доступа (`?.` — Null-conditional operator)
Этот оператор позволяет выполнить обращение к члену объекта или вызов метода только в том случае, если левая часть выражения не равна `null`. Если же там `null`, то все выражение целиком не вызывает исключение, а просто возвращает `null`.

Пример использования:
```csharp
// Если WorkDepartment равен null, код не упадет, а переменная departmentTitle получит значение null
string departmentTitle = emp.WorkDepartment?.Title; 
```

#### 2. Оператор объединения с нулем (`??` — Null-coalescing operator)
Оператор `??` позволяет указать альтернативное (значение по умолчанию), которое будет возвращено, если левая часть выражения окажется равной `null`.

Пример использования:
```csharp
// Если WorkDepartment равен null или его Title равен null, выведется строка "Без отдела"
string departmentTitle = emp.WorkDepartment?.Title ?? "Без отдела";
Console.WriteLine("Отдел: " + departmentTitle);
```

Связка операторов `?.` и `??` является стандартом безопасного и лаконичного написания кода при обработке сложных иерархических данных, в которых некоторые связи могут отсутствовать (`null`).

## 3. Сборщик мусора (Garbage Collector)

### Проблема управления памятью и автоматизация в .NET

В языках программирования с ручным управлением памятью (например, C или C++) разработчик самостоятельно выделяет память в куче с помощью функций вроде `malloc` или оператора `new`, а затем обязан вручную освобождать её с помощью `free` или `delete`. Это порождает два критических класса ошибок:

1. **Утечки памяти (Memory Leaks)** — ситуация, когда объект больше не нужен программе, но программист забыл освободить занимаемую им память. Память постепенно исчерпывается, что приводит к аварийному завершению приложения (OutOfMemoryException).
2. **Ошибки висячих указателей (Dangling Pointers) и двойного освобождения (Double Free)** — когда память освобождается раньше времени, но указатель на неё продолжает использоваться, либо одна и та же область памяти освобождается дважды. Это приводит к непредсказуемому поведению программы и уязвимостям безопасности.

Платформа .NET и среда выполнения Common Language Runtime (CLR) решают эту проблему радикально: разработчик только создаёт объекты с помощью ключевого слова `new`, а за их уничтожение и освобождение памяти отвечает специальный фоновый компонент — **сборщик мусора (Garbage Collector, GC)**.

> **Определение.** Сборщик мусора в .NET — это автоматический менеджер памяти, который отслеживает распределение объектов в управляемой куче, определяет неиспользуемые объекты и освобождает занимаемую ими память без участия программиста.

Сборщик мусора работает в фоновом режиме и запускается автоматически по эвристическим алгоритмам (например, когда памяти в куче начинает не хватать) или по явному требованию через вызов метода `System.GC.Collect()`. Однако злоупотреблять ручным вызовом GC настоящим разработчикам категорически не рекомендуется, так как это нарушает внутреннюю оптимизацию среды выполнения.

---

### Принцип работы GC: Корневые объекты и граф достижимости

Сборщик мусора не ищет мёртвые объекты — вместо этого он ищет **живые** объекты. Всё остальное считается «мусором» и подлежит удалению. Для поиска живых объектов используется концепция **корневых объектов (Roots)** и обход **графа достижимости**.

> **Определение.** Корневые объекты (GC Roots) — это ссылки на объекты в управляемой куче, которые доступны коду напрямую в любой момент времени вне зависимости от самого сборщика мусора. К корням относятся:
> - Локальные переменные и параметры методов, находящиеся в данный момент в стеке вызовов.
> - Статические поля классов (хранящиеся на протяжении всей жизни домена приложения).
> - Указатели из неуправляемого кода (например, COM-интерфейсы или дескрипторы Win32 API).

Алгоритм работы сборщика основан на построении графа объектов:

1. GC начинает поиск с **корней (Roots)**.
2. Проверяются все ссылки, хранящиеся в корневых переменных. Если ссылка указывает на объект в управляемой куче, этот объект помечается как достижимый (живой).
3. Затем GC смотрит на поля этого объекта. Если они содержат ссылки на другие объекты в куче, те объекты также помечаются как достижимые.
4. Процесс рекурсивно повторяется для всех обнаруженных ссылок. Образуется так называемый *граф достижимости*.
5. Все объекты в управляемой куче, до которых нельзя добраться по ссылкам ни из одного корня, считаются недостижимыми. Память, занимаемая ими, считается свободной.

```
+---------------+      Ссылки       +-------------------+      Ссылки       +-------------------+
| Корни (Roots) | ----------------> | Объект А (Живой)  | ----------------> | Объект Б (Живой)  |
| (Стек / Статика)|                 +-------------------+                   +-------------------+
+---------------+
                                    +-------------------+
                                    | Объект В (Мусор)  |   <-- Нет путей от корней
                                    +-------------------+
```

В примере выше объекты А и Б образуют цепочку достижимости от корней, поэтому они сохраняются в памяти. Объект В изолирован от корней — до него невозможно дойти по ссылкам, поэтому он будет уничтожен сборщиком мусора.

---

### Поколения сборщика мусора и куча больших объектов (LOH)

Если бы сборщик мусора каждый раз сканировал всю память и все объекты в куче, производительность приложений падала бы до нуля. Для оптимизации .NET использует **поколенческий сборщик мусора (Generational GC)**. Он опирается на эмпирическое наблюдение: *большинство объектов живут недолго* (например, локальные переменные внутри метода или временные строки).

Управляемая куча логически разделена на три поколения:

| Поколение | Назначение и характеристики | Частота сборок |
|---|---|---|
| **Поколение 0 (Gen 0)** | Новые, только что созданные объекты. Самая маленькая область памяти. | Очень частая |
| **Поколение 1 (Gen 1)** | Буферный буфер между Gen 0 и Gen 2. Сюда попадают объекты, пережившие хотя бы одну сборку Gen 0. | Средняя |
| **Поколение 2 (Gen 2)** | Долгоживущие объекты (например, глобальные кэши, singleton-сервисы, статические структуры). | Редкая |

#### Куча больших объектов (Large Object Heap, LOH)
Объекты размером **85 000 байт (около 83 КБ) и более** выделяются в специальной области памяти — LOH ( Large Object Heap). К ним относятся, например, большие массивы байт или строк. 
- Объекты LOH сразу попадают в **поколение 2**, так как перемещать их туда-сюда при копировании слишком дорого с точки зрения производительности процессора.
- Долгое время LOH не подвергался сжатию, что приводило к фрагментации памяти, однако в современных версиях .NET сжатие LOH можно включать принудительно.

#### Алгоритм продвижения объектов (Promotion)
1. Новые объекты выделяются в поколении 0.
2. Когда поколение 0 заполнено, запускается сборка мусора первого уровня (проверяется только Gen 0).
3. Объекты, которые выжили после проверки в Gen 0, «продвигаются» (promotion) в поколение 1.
4. Когда заполняется поколение 1, запускается сборка, охватывающая Gen 0 и Gen 1. Выжившие объекты переходят в поколение 2.
5. Сборка поколения 2 (полная сборка) проверяет всю кучу целиком и выполняется крайне редко, так как требует больших вычислительных затрат.

---

### Фазы работы GC: Маркировка, сжатие и очистка

Когда запускается процесс сборки мусора (например, для Gen 0), среда выполнения приостанавливает работу всех потоков приложения на короткое время (**Stop-The-World** пауза), чтобы граф объектов не менялся в процессе анализа. Сборка проходит в три основных этапа:

1. **Фаза маркировки (Mark Phase):** 
   GC проходит по всем корневым объектам, строит граф достижимости и помечает каждый живой объект специальным битом в его служебном заголовке.
2. **Фаза очистки (Sweep Phase):** 
   GC сканирует кучу в поисках непомеченных объектов. Память, которую они занимали, объявляется свободной и добавляется в списки свободных блоков (free lists), чтобы её можно было использовать для размещения новых объектов.
3. **Фаза сжатия (Compact Phase):** 
   После удаления мусора в памяти могут остаться «дыры» (фрагментация). Чтобы избежать этого, GC физически сдвигает оставшиеся живые объекты ближе друг к другу, формируя непрерывный блок свободной памяти в конце кучи. При этом сборщик обновляет все ссылки на эти объекты по всей памяти, чтобы они продолжали указывать на свои новые адреса.

### Детерминированное освобождение ресурсов: IDisposable и блок using

Сборщик мусора отлично управляет **управляемой памятью** (памятью под объекты .NET в куче). Однако приложения часто используют **неуправляемые ресурсы** (Unmanaged Resources):
- Дескрипторы файлов (`FileStream`, сетевые сокеты).
- Дескрипторы графических окон и кистей в ОС Windows (`Graphics`, `Bitmap`).
- Подключения к базам данных (`SqlConnection`).

Сборщик мусора ничего не знает о размере неуправляемых ресурсов и не торопится их освобождать, так как объект .NET, завернувший этот ресурс, может занимать мало места в куче и долго ждать своей очереди на сборку. Это приводит к утечкам системных дескрипторов.

Для решения этой проблемы используется **интерфейс `IDisposable`** и синтаксический сахар — **блок `using`**.

> **Определение.** Интерфейс `IDisposable` содержит единственный метод `Void Dispose()`, реализация которого обязывает класс явно и немедленно освободить все захваченные неуправляемые ресурсы.

Конструкция `using` гарантирует вызов метода `Dispose()` даже в случае возникновения исключений в блоке кода.

Пример правильной работы с неуправляемыми ресурсами:

```csharp
using System;
using System.IO;

class Program
{
    static void Main()
    {
        // Блок using гарантирует вызов метода Dispose() для потока файла 
        // сразу после выхода из зоны видимости фигурных скобок, даже если произойдет ошибка.
        using (StreamWriter writer = new StreamWriter("report.txt"))
        {
            writer.WriteLine("Отчет о работе системы составлен успешно.");
        } 
        // Здесь файл уже гарантированно закрыт и освобожден для операционной системы.
    }
}
```

### Деструкторы и метод Finalize

Раньше для очистки неуправляемых ресурсов разработчики использовали **деструкторы** (финализаторы), синтаксически похожие на методы из C++:

```csharp
class ResourceHolder
{
    // Финализатор (не путать с конструктором)
    ~ResourceHolder()
    {
        // Код освобождения неуправляемых ресурсов
    }
}
```

#### Почему деструкторы вредны для производительности?
1. Когда объект с финализатором создается в памяти, сборщик мусора помечает его как «требующий финализации».
2. Когда объект становится мусором, GC *не удаляет* его память сразу. Вместо этого он помещает ссылку на объект в специальную очередь финализации (`Finalization Queue`).
3. В отдельном потоке работает специальный демон, который вызывает метод `Finalize()` для этих объектов. Только после этого на *следующем* цикле сборки мусора память этого объекта будет физически очищена.
4. Объекты с деструкторами обязательно доживают как минимум до **поколения 2**, увеличивая нагрузку на память.

> **Правило разработки в .NET:** Никогда не пишите финализаторы (`~ClassName`), если ваш класс не работает напрямую с сырыми неуправляемыми указателями или дескрипторами ОС. Для стандартных задач используйте только интерфейс `IDisposable`.

### Разобранный пример: Анализ работы поколений GC

#### Условие задачи
Написать консольную программу на C#, которая моделирует создание большого количества короткоживущих объектов в цикле (100 000 итераций). Внутри цикла для каждого шага создается объект вспомогательного класса `DataPacket`. Необходимо программно вывести в консоль статистику вызова сборщика мусора и распределение объектов по поколениям до и после завершения работы цикла, используя методы класса `System.GC`.

#### Ход рассуждений
1. Создадим класс `DataPacket` с небольшим массивом данных, чтобы объекты занимали память в поколении 0.
2. Перед началом цикла вызовем `GC.Collect()` и `GC.WaitForPendingFinalizers()`, чтобы очистить мусор от предыдущих операций и зафиксировать чистую стартовую позицию.
3. С помощью метода `GC.GetGeneration(obj)` мы можем узнать, в каком поколении в данный момент находится конкретный объект.
4. С помощью метода `GC.CollectionCount(int generation)` можно узнать, сколько раз сборщик мусора запускался для конкретного поколения (0, 1 или 2).
5. Запустим цикл на 100 000 итераций. На каждой итерации будем создавать объект. Часть объектов будет быстро терять ссылки, превращаясь в мусор, а на некоторых шагах будем сохранять ссылки в массив, чтобы они перешли в старшие поколения.

#### Решение на C#

```csharp
using System;

namespace GarbageCollectorDemo
{
    // Вспомогательный класс для демонстрации создания объектов
    class DataPacket
    {
        public int Id { get; set; }
        public byte[] Payload { get; set; }

        public DataPacket(int id)
        {
            Id = id;
            // Выделяем массив из 100 байт (размер много меньше 85 КБ, идет в Gen 0)
            Payload = new byte[100]; 
        }
    }

    class Program
    {
        static void Main()
        {
            // Шаг 1: Принудительно очищаем мусор для чистоты эксперимента
            GC.Collect();
            GC.WaitForPendingFinalizers();
            GC.Collect();

            Console.WriteLine("--- Статистика GC до запуска цикла ---");
            Console.WriteLine($"Сборок поколения 0: {GC.CollectionCount(0)}");
            Console.WriteLine($"Сборок поколения 1: {GC.CollectionCount(1)}");
            Console.WriteLine($"Сборок поколения 2: {GC.CollectionCount(2)}");
            Console.WriteLine();

            // Создадим массив для удержания части объектов живыми, 
            // чтобы они перешли в поколение 1 и 2
            DataPacket[] longLivedStorage = new DataPacket[1000];

            Console.WriteLine("Запуск цикла создания 100 000 объектов...");
            
            for (int i = 0; i < 100_000; i++)
            {
                // Создаем короткоживущий объект (теряет ссылку сразу после итерации)
                DataPacket tempPacket = new DataPacket(i);

                // Каждую 100-ю итерацию сохраняем объект в массив, делая его «долгоживущим»
                if (i % 100 == 0)
                {
                    int index = (i / 100) % 1000;
                    longLivedStorage[index] = tempPacket;
                }
            }

            Console.WriteLine("Цикл завершен.\n");

            // Проверим, в каких поколениях находятся выжившие объекты
            int genForSample0 = GC.GetGeneration(longLivedStorage[0]);
            int genForSample500 = GC.GetGeneration(longLivedStorage[500]);

            Console.WriteLine($"Поколение долгоживущего объекта 0: Gen {genForSample0}");
            Console.WriteLine($"Поколение долгоживущего объекта 500: Gen {genForSample500}");
            Console.WriteLine();

            // Шаг 2: Проверяем статистику GC после нагрузки
            Console.WriteLine("--- Статистика GC после завершения цикла ---");
            Console.WriteLine($"Сборок поколения 0: {GC.CollectionCount(0)}");
            Console.WriteLine($"Сборок поколения 1: {GC.CollectionCount(1)}");
            Console.WriteLine($"Сборок поколения 2: {GC.CollectionCount(2)}");
            Console.WriteLine();

            // Выведем общий объем памяти, занятый управляемой кучей в байтах
            long totalMemoryBytes = GC.GetTotalMemory(false);
            Console.WriteLine($"Общий объем памяти в куче: {totalMemoryBytes} байт ({totalMemoryBytes / 1024} КБ)");
        }
    }
}
```

```text

Сборок поколения 0: 0
Сборок поколения 1: 0
Сборок поколения 2: 0

Запуск цикла создания 100 000 объектов...
Цикл завершен.

Поколение долгоживущего объекта 500: Gen 2

```

#### Проверка и анализ результатов
1. **Единицы измерения:** Память измеряется в байтах и килобайтах, количество сборок — целые числа (счетчики).

   - Программа отработала корректно, утечек памяти не произошло благодаря автоматической очистке временных объектов.

## 4. Указатели и небезопасный код (unsafe) в C#

### 1. Концепция указателей и причины их ограничения в управляемом коде

В предыдущих разделах мы познакомились с тем, как платформа .NET и среда выполнения CLR (Common Language Runtime) автоматически управляют памятью. Мы используем ссылочные типы, оператор `new` и полностью полагаемся на сборщик мусора (Garbage Collector), который самостоятельно освобождает неиспользуемую память. При этом ссылки на объекты скрывают от программиста их реальные физические адреса в оперативной памяти.

Однако в системном программировании, при разработке драйверов, оптимизации высокопроизводительных вычислительных алгоритмов или при взаимодействии с низкоуровневыми библиотеками на языке C/C++ (через механизмы P/Invoke), стандартных механизмов управления памятью оказывается недостаточно. Для этого в C# предусмотрена возможность работы с прямыми адресами памяти с помощью **указателей**.

> **Определение.** **Указатель (pointer)** — это переменная, значением которой является адрес ячейки памяти, в которой хранится другое значение (данные или другой адрес).

В классических языках программирования, таких как C или C++, указатели являются базовым инструментом работы с памятью. Но их свободное использование порождает множество критических ошибок:
- **Утечки памяти:** если забыть освободить выделенную память.
- **Ошибки сегментации (Segmentation Fault) и зависания:** при попытке прочитать или записать данные по случайному или уже освобожденному адресу.
- **Уязвимости безопасности:** переполнение буфера (Buffer Overflow), когда злоумышленник через некорректный указатель перезаписывает соседние участки памяти, внедряя вредоносный код.

Платформа .NET создавалась как безопасная среда (Type-Safe и Memory-Safe). Среда CLR строго контролирует типы данных и доступ к памяти, исключая большинство подобных ошибок. По этой причине работа с указателями по умолчанию запрещена в обычном («управляемом») коде C#. 

Чтобы разрешить компилятору использовать прямые адреса памяти, в языке C# введен специальный контекст, называемый **небезопасным кодом** (`unsafe`).

---

### 2. Ключевое слово `unsafe` и настройка проекта

Чтобы написать код, использующий указатели, программист должен явно заявить компилятору о своих намерениях. Для этого используется модификатор `unsafe`.

Ключевое слово `unsafe` может применяться к разным программным конструкциям:
1. К методу целиком.
2. К блоку кода внутри метода (unsafe-блок).
3. К структуре или классу целиком.
4. К полям класса или структуры.

Пример объявления небезопасного метода и блока кода:

```csharp
// Небезопасный метод
unsafe void ProcessMemory()
{
    // Небезопасный блок внутри обычного метода
    int value = 42;
    int* ptr = &value; // & — взятие адреса
}
```

#### Настройка проекта для компиляции `unsafe`-кода

Поскольку работа с указателями потенциально опасна для целостности данных приложения, компилятор C# по умолчанию блокирует сборку программ, содержащих ключевое слово `unsafe`. Чтобы разрешить компиляцию, необходимо явно включить поддержку небезопасного кода в файле проекта (`.csproj`) вашей программы.

Откройте файл проекта в текстовом редакторе (например, в Visual Studio двойным кликом по названию проекта в обозревателе решений) и добавьте свойство `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` внутрь тега `<PropertyGroup>`:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
    <!-- Включаем поддержку небезопасного кода -->
    <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
  </PropertyGroup>

</Project>
```

Если вы используете командную строку .NET CLI, разрешить небезопасный код можно прямо при сборке через флаг `/unsafe`:
```bash
dotnet build /unsafe
```

### 3. Операторы работы с указателями: взятие адреса (`&`) и разименование (`*`)

Внутри контекста `unsafe` программист получает в свое распоряжение два основных унарных оператора для работы с адресами памяти:

1. **Оператор взятия адреса (`&`)** — возвращает адрес переменной в памяти. Применяется к переменным значимых типов (локальным переменным, полям структур).
2. **Оператор разименования (`*`)** — позволяет получить или изменить значение, хранящееся по адресу, на который указывает указатель.

Синтаксис объявления указателя выглядит следующим образом: `Тип* имя_переменной;` (звездочка ставится сразу после имени типа данных).

Рассмотрим подробный пример взаимодействия с переменной через указатель:

```csharp
using System;

class Program
{
    static unsafe void Main()
    {
        int originalValue = 100;
        
        // Объявляем указатель на целое число и записываем в него адрес переменной originalValue
        int* ptr = &originalValue;

        Console.WriteLine($"Значение переменной: {originalValue}");
        Console.WriteLine($"Адрес в памяти (в шестнадцатеричном виде): {(long)ptr:X}");
        Console.WriteLine($"Значение через разименование указателя (*ptr): {*ptr}");

        // Изменяем значение через указатель
        *ptr = 250;

        // Переменная originalValue изменилась, так как указатель ссылается на ту же ячейку памяти
        Console.WriteLine($"Новое значение originalValue: {originalValue}");
    }
}
```

#### Пояснение по шагам:
1. `int originalValue = 100;` — в стеке выделяется 4 байта памяти под целочисленную переменную со значением `100`.
2. `int* ptr = &originalValue;` — оператор `&` считывает адрес этой ячейки памяти в стеке. Переменная `ptr` сама является указателем (в 64-битной системе она занимает 8 байт в стеке) и хранит этот физический адрес.
3. `*ptr = 250;` — оператор `*` обращается по адресу, записанному в `ptr`, находит ячейку памяти переменной `originalValue` и перезаписывает туда число `250`.

### 4. Фиксация объектов в памяти: ключевое слово `fixed`

Если с переменными значимых типов (которые обычно лежат в стеке) работать относительно просто, то со ссылочными типами (массивами, объектами классов в управляемой куче) ситуация принципиально иная.

Как мы знаем из предыдущих тем, сборщик мусора (GC) в .NET периодически проводит оптимизацию памяти методом уплотнения (компактификации). Во время этой фазы GC может физически перемещать объекты в куче, чтобы уменьшить фрагментацию памяти и освободить непрерывное пространство. 

Представьте ситуацию: мы взяли адрес элемента массива в куче и сохранили его в указатель `int*`. В этот момент происходит сборка мусора, и массив перемещается по другому адресу. Наш указатель продолжит указывать на старый адрес, где теперь могут находиться совершенно другие данные. Попытка записи по такому указателю приведет к повреждению памяти и аварийному завершению программы (`AccessViolationException`).

Чтобы предотвратить перемещение объекта сборщиком мусора во время работы с ним через указатели, используется оператор **`fixed`** (фиксация).

> **Определение.** **Оператор `fixed`** сообщает сборщику мусора .NET, что указанный объект или массив временно запрещено перемещать в памяти. На время выполнения блока `fixed` объект «фиксируется» на своем физическом месте.

Пример использования `fixed` для работы с массивом:

```csharp
using System;

class Program
{
    static unsafe void Main()
    {
        int[] numbers = { 10, 20, 30, 40, 50 };

        // Фиксируем массив в памяти с помощью ключевого слова fixed
        fixed (int* pNumbers = numbers)
        {
            // Внутри этого блока массив гарантированно не будет перемещен GC
            Console.WriteLine($"Адрес первого элемента массива: {(long)pNumbers:X}");
            
            // Читаем первый элемент через указатель
            Console.WriteLine($"Первый элемент: {*pNumbers}");
        }
        // После выхода из блока fixed объект снова доступен для перемещения сборщиком мусора
    }
}
```

Важные правила работы с `fixed`:
- Переменная, объявленная в операторе `fixed`, автоматически считается доступной только для чтения (`readonly`) внутри блока — нельзя изменить сам адрес указателя `pNumbers` (например, написать `pNumbers++` прямо в заголовке `fixed`, хотя можно завести другой вспомогательный указатель внутри блока).
- Оператор `fixed` применяется главным образом к массивам, строкам (`string`) и буферам фиксированного размера.

### 5. Арифметика указателей в C#

Указатели в C# поддерживают арифметические операции. Поскольку указатель хранит точный адрес типа данных, прибавление единицы к указателю сдвигает адрес не на 1 байт, а ровно на столько байт, сколько весит этот тип данных в памяти.

Например:
- Если `p` — это `int*`, то `p + 1` сдвигает адрес на `4` байта (так как `sizeof(int) = 4`).
- Если `p` — это `long*`, то `p + 1` сдвигает адрес на `8` байт.

Это позволяет чрезвычайно эффективно обходить массивы и буферы данных, используя указатель вместо индексного доступа (`array[i]`).

Доступные арифметические операции с указателями:
- Сложение указателя с целым числом (`ptr + n`, `ptr += n`)
- Вычитание целого числа из указателя (`ptr - n`, `ptr -= n`)
- Вычитание двух указателей одного типа друг из друга (возвращает количество элементов между ними)
- Операции инкремента (`++`) и декремента (`--`)

### 6. Разобранный пример: обход массива через указатели с фиксацией

Решим учебную задачу: написать метод, который принимает массив целых чисел, умножает каждый элемент массива на заданный коэффициент с использованием указателей и арифметики указателей внутри блока `unsafe`, а затем возвращает сумму всех элементов массива после преобразования.

#### Условие задачи
- Входные данные: массив целых чисел `int[] data` и коэффициент умножения `int factor`.
- Требования: обработку массива выполнить **исключительно** через указатели (без использования циклов вида `for (int i = 0; ...)` и индексатора `data[i]`).
- Выходные данные: общая сумма элементов преобразованного массива.

#### Рисунок схемы памяти (словесное описание)
Представим управляемую кучу, где располагается наш массив `data` из 4 элементов: `[ 5, 10, 15, 20 ]`.
Когда мы выполняем `fixed (int* ptr = data)`, среда CLR закрепляет этот массив в куче. Указатель `ptr` указывает на самый первый элемент (`5`). 
В цикле мы обращаемся к значению через `*ptr`, умножаем его на `factor`, а затем с помощью выражения `ptr++` сдвигаем указатель на следующие 4 байта, пока не обойдем весь массив.

#### Ход рассуждений
1. Создаем метод `MultiplyAndSumUnsafe(int[] data, int factor)`.
2. Внутри метода открываем контекст `unsafe`.
3. Объявляем переменную для подсчета суммы: `long sum = 0;` (используем `long`, чтобы избежать возможного переполнения при суммировании).
4. Используем оператор `fixed`, чтобы получить указатель на начало массива: `fixed (int* startPtr = data)`.
5. Заводим рабочий указатель `int* current = startPtr;` и указатель на конец массива `int* endPtr = startPtr + data.Length;`.
6. Запускаем цикл `while (current < endPtr)`. Пока рабочий указатель не дошел до конца массива:
   - Умножаем значение: `*current *= factor;`
   - Добавляем в сумму: `sum += *current;`
   - Сдвигаем указатель на следующий элемент: `current++;`
7. Возвращаем полученную сумму.

#### Полный исходный код программы

```csharp
using System;

class Program
{
    // Небезопасный метод обработки массива
    static unsafe long MultiplyAndSumUnsafe(int[] data, int factor)
    {
        if (data == null)
        {
            throw new ArgumentNullException(nameof(data));
        }

        long sum = 0;

        // Фиксируем массив в памяти, чтобы сборщик мусора его не переместил
        fixed (int* startPtr = data)
        {
            int* current = startPtr;
            int* endPtr = startPtr + data.Length; // Адрес за последним элементом массива

            // Обход массива с помощью арифметики указателей
            while (current < endPtr)
            {
                *current *= factor; // Умножаем значение в памяти на коэффициент
                sum += *current;    // Добавляем измененное значение к сумме
                current++;          // Переходим к следующему элементу (сдвиг на sizeof(int) байт)
            }
        } // Здесь блок fixed заканчивается, фиксация массива снимается

        return sum;
    }

    static void Main()
    {
        // Исходные данные
        int[] numbers = { 2, 4, 6, 8, 10 };
        int multiplier = 3;

        Console.WriteLine("Исходный массив: " + string.Join(", ", numbers));
        Console.WriteLine($"Коэффициент умножения: {multiplier}");

        // Вызов метода
        long totalSum = MultiplyAndSumUnsafe(numbers, multiplier);

        // Вывод результатов
        Console.WriteLine("Массив после обработки (через указатели): " + string.Join(", ", numbers));
        Console.WriteLine($"Сумма элементов: {totalSum}");
    }
}
```

#### Проверка и тестирование
1. **Трассировка ручным счетом:**
   - Массив до: `[2, 4, 6, 8, 10]`, множитель `3`.
   - Итерация 1: `*current` равен `2`. Становится `2 * 3 = 6`. Сумма = `6`. Указатель сдвигается на следующий элемент.
   - Итерация 2: `*current` равен `4`. Становится `4 * 3 = 12`. Сумма = `6 + 12 = 18`. Указатель сдвигается.
   - Итерация 3: `*current` равен `6`. Становится `6 * 3 = 18`. Сумма = `18 + 18 = 36`. Указатель сдвигается.
   - Итерация 4: `*current` равен `8`. Становится `8 * 3 = 24`. Сумма = `36 + 24 = 60`. Указатель сдвигается.
   - Итерация 5: `*current` равен `10`. Становится `10 * 3 = 30`. Сумма = `60 + 30 = 90`. Указатель сдвигается и достигает `endPtr`. Цикл завершается.
   - Итоговый массив: `[6, 12, 18, 24, 30]`. Сумма: `90`.
2. **Проверка на граничные случаи:**
   - Пустой массив (`data.Length == 0`): `startPtr + 0` равно `endPtr`. Цикл `while (current < endPtr)` не выполнится ни разу, метод вернет `0`, исключений не возникнет.
   - Передача `null`: сработает встроенная проверка `if (data == null)`, будет выброшено исключение `ArgumentNullException`.

Ответ: Массив после обработки: `6, 12, 18, 24, 30`; Сумма элементов: `90`.

### 7. Сравнение производительности: управляемый код против небезопасных блоков

Зачем же рисковать безопасностью памяти и использовать сложный синтаксис `unsafe`, если в C# есть привычные безопасные циклы? Главный ответ — **производительность**.

В обычном (безопасном) режиме C# при каждом обращении к элементу массива по индексу (например, `data[i]`) среда выполнения CLR производит скрытую проверку границ (`Bounds Checking`). Компилятор и процессор гарантируют, что переменная `i` строго больше или равна нулю и строго меньше `data.Length`. Если индекс выходит за пределы, генерируется исключение `IndexOutOfRangeException`.

Хотя эта проверка оптимизирована компилятором Just-In-Time (JIT), на миллионах и миллиардах итераций (например, при обработке трехмерной графики, аудиопотоков, шифровании или обработке больших матриц) проверка границ вносит измеримые накладные расходы.

Внутри блока `unsafe` при работе с указателями **проверка границ отключена полностью**. Программист сам несет ответственность за то, чтобы указатель не вышел за пределы выделенной памяти. За счет этого код работает максимально быстро, сопоставимо по скорости с языком C++.

#### Сравнительная таблица подходов к работе с массивами

| Критерий | Безопасный код (`for / foreach`) | Небезопасный код (`unsafe` + `fixed`) |
|---|---|---|
| **Безопасность типов и памяти** | Абсолютная (контролируется CLR) | Отсутствует (ответственность программиста) |
| **Проверка границ массива** | Есть (автоматическая на каждой итерации) | Отсутствует (максимальная скорость) |
| **Требования к настройке проекта** | Стандартные настройки по умолчанию | Требует включения `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` |
| **Взаимодействие со сборщиком мусора** | Объекты свободно перемещаются GC | Требует явной фиксации через `fixed` |
| **Область применения** | 99% бизнес-логики и обычных приложений | Высокопроизводительные алгоритмы, обработка сигналов, системное ПО |

Используйте небезопасный код и указатели только тогда, когда это действительно обосновано требованиями к производительности или необходимостью интеграции с низкоуровневыми библиотеками, помня о потенциальных рисках повреждения памяти.

## Типичные ошибки

1. **Попытка чтения или записи по нулевой ссылке (`NullReferenceException`)**
   - *Почему возникает:* Обращение к полю, методу или свойству объекта через переменную ссылочного типа, которая имеет значение `null` (объект не был создан оператором `new`).
   - *Как избежать:* Всегда проверять объект на равенство с `null` перед использованием либо применять оператор условного доступа (`?.`).
   - *Пример ошибки:* `Employee emp = null; Console.WriteLine(emp.FullName);`

2. **Изменение значимого типа в методе в надежде повлиять на оригинал**
   - *Почему возникает:* Непонимание разницы между передачей параметров по значению для значимых и ссылочных типов.
   - *Как избежать:* Помнить, что значимые типы (`int`, `double`, `struct`) копируются при передаче в метод. Для изменения оригинала используйте ключевое слово `ref` или `out`.
   - *Пример ошибки:* Передача `int x = 5` в метод, изменяющий параметр на `10`, после чего `x` в вызывающем коде остается равным `5`.

3. **Забытый оператор `using` для работы с ресурсами**
   - *Почему возникает:* Надежда на то, что сборщик мусора сам освободит открытые файлы, сетевые соединения или подключения к базам данных.
   - *Как избежать:* Использовать конструкцию `using` для всех классов, реализующих интерфейс `IDisposable`. Это гарантирует вызов метода `Dispose()` даже при возникновении исключений.
   - *Пример ошибки:* Открытие `StreamWriter` без блока `using`, из-за чего дескриптор файла остается заблокированным операционной системой.

4. **Использование деструкторов (`~ClassName`) без реальной необходимости**
   - *Почему возникает:* Ошибочный перенос привычек из языка C++ в платформу .NET для очистки управляемой памяти.
   - *Как избежать:* Не писать финализаторы, если класс не управляет напрямую сырыми неуправляемыми дескрипторами. Финализаторы переводят объекты в поколение 2 и сильно замедляют работу сборщика мусора.
   - *Пример ошибки:* Написание пустого деструктора в классе бизнес-логики.

5. **Ошибки с перемещением указателей при отсутствии фиксации (`fixed`) в `unsafe`-коде**
   - *Почему возникает:* Сохранение адреса элемента массива из управляемой кучи в указатель `int*` без ключевого слова `fixed`, в результате чего сборщик мусора перемещает массив, а указатель начинает ссылаться на неверный участок памяти.
   - *Как избежать:* Всегда фиксировать объекты из кучи оператором `fixed` на время работы с их адресами.
   - *Пример ошибки:* Перемещение указателя `ptr++` за пределы зафиксированного блока памяти или обращение к памяти после выхода из блока `fixed`.

6. **Ошибки при арифметике указателей и выходе за границы массива**
   - *Почему возникает:* В блоке `unsafe` полностью отсутствуют автоматические проверки границ массивов (`IndexOutOfRangeException`), принятые в C#.
   - *Как избежать:* Строго контролировать начальные и конечные адреса буферов (например, вычислять `endPtr = startPtr + length`) и использовать строгие неравенства `current < endPtr`.
   - *Пример ошибки:* Цикл `while (current <= endPtr)`, приводящий к чтению памяти за пределами выделенного массива.

7. **Неправильное понимание времени жизни локальных переменных стека**
   - *Почему возникает:* Попытка вернуть адрес локальной переменной из метода через указатель наружу.
   - *Как избежать:* Помнить, что стековый кадр метода уничтожается сразу после завершения его работы, и возвращать указатели на локальные переменные стека категорически запрещено.
   - *Пример ошибки:* Возврат `int*` на локальную переменную метода, которая прекратила свое существование.
