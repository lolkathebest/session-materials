## 1. Понятие интерфейса в C#: контракт и синтаксис

### Понятие интерфейса: контракт поведения

> **Определение.** Интерфейс в языке C# (`interface`) — это ссылочный тип данных, который задает чистый контракт поведения (спецификацию возможностей), не содержащий реализации по умолчанию (в классическом понимании) и полей состояния. Класс или структура, реализующие интерфейс, обязуются предоставить конкретную реализацию для всех его членов.

Простыми словами, интерфейс — это соглашение или «протокол общения». Он не говорит *как* именно должна выполняться задача, но жестко определяет *что именно* объект должен уметь делать. Например, интерфейс `IComparable` говорит, что объект умеет сравнивать себя с другими объектами, но не предписывает, по какому конкретно алгоритму (по возрасту, по цене или по алфавиту) это сравнение должно происходить.

Рассмотрим ключевые отличия интерфейсов от абстрактных классов, которые мы изучали ранее. Путаница между ними — частая ошибка на экзамене.

| Характеристика | Абстрактный класс (`abstract class`) | Интерфейс (`interface`) |
|---|---|---|
| **Наличие полей состояния** | Может содержать любые поля (переменные класса). | Не может содержать поля экземпляра (состояние хранить нельзя). |
| **Конструкторы** | Может иметь конструкторы (вызываются через `base()`). | Не имеет конструкторов, так как объекты интерфейсов создавать нельзя. |
| **Множественное наследование** | Класс может наследоваться только от одного базового класса. | Класс может реализовать произвольное количество интерфейсов. |
| **Степень абстракции** | Может содержать как абстрактные члены, так и полностью реализованные методы. | Исторически содержит только сигнатуры (контракты) без тела. |

Ни один интерфейс нельзя инициализировать напрямую через оператор `new`. Попытка написать `ILoggable log = new ILoggable();` приведет к ошибке компиляции, так как у интерфейса нет памяти под поля и нет конструктора для инициализации объекта.

### Синтаксис объявления и правила именования

В экосистеме .NET и языке C# принято строгое соглашение об именовании (Naming Convention): имя любого интерфейса должно начинаться с заглавной латинской буквы **`I`** (например, `IDisposable`, `IEnumerable`, `ILoggable`). Это позволяет сразу визуально отличить интерфейс от класса или структуры в коде.

Объявление интерфейса выглядит следующим образом:

```csharp
public interface ILoggable
{
    // Свойство без реализации
    bool IsActive { get; set; }

    // Сигнатура метода без тела
    void Log(string message);
}
```

Внутри интерфейса можно объявлять:
1. **Методы**: только сигнатуры без тела (без фигурных скобок `{}`).
2. **Свойства**: указываются только аксессоры `{ get; set; }` без тел и без привязки к приватным полям (так как полей в интерфейсе нет).
3. **Индексаторы**: позволяют обращаться к объекту по индексу.
4. **События**: для реализации паттерна издатель-подписчик.

#### Модификаторы доступа и современные изменения в C# 8.0

Исторически все члены интерфейса являются общедоступными (`public`) по умолчанию, и указывать модификаторы доступа `public`, `private` или `protected` для них было запрещено компилятором. 

Начиная с **C# 8.0** и платформы **.NET Core**, в язык была добавлена поддержка *реализации по умолчанию для членов интерфейса* (Default Interface Methods - DIM). Теперь внутри интерфейса можно создавать методы с телом. Это сделано для безопасного эволюционирования библиотек (например, добавление нового метода в интерфейс без поломки старых классов-реализаций). Однако для учебных и базовых архитектурных задач мы проектируем интерфейсы в их классическом виде — как чистые контракты без реализации.

### Реализация интерфейса классом

Чтобы класс начал поддерживать контракт интерфейса, используется двоеточие `:` после имени класса. Если класс наследует базовый класс *и* реализует интерфейсы, то сначала всегда указывается базовый класс, а затем через запятую перечисляются интерфейсы.

```csharp
public class ConsoleLogger : ILogger, IDisposable
{
    // Обязательная реализация членов интерфейсов...
}
```

Главное правило компилятора: **класс обязан реализовать абсолютно все члены интерфейса**, в противном случае код не скомпилируется. При этом реализующие методы в классе должны иметь модификатор `public` и точно такую же сигнатуру, как в интерфейсе.

### Полиморфное использование интерфейсов

Главная сила интерфейсов заключается в обеспечении полиморфизма. Переменная, объявленная с типом интерфейса, может ссылаться на экземпляр *любого* класса, который этот интерфейс реализует.

Пусть у нас есть интерфейс `IWidget` и два разных класса `Button` и `TextBox`, реализующие его. Мы можем создать коллекцию (например, массив или список) типа `IWidget[]` и положить туда оба объекта:

```csharp
IWidget[] widgets = new IWidget[2];
widgets[0] = new Button();
widgets[1] = new TextBox();

foreach (var w in widgets)
{
    w.Render(); // Вызывается метод соответствующего класса (динамический полиморфизм)
}
```

Код, работающий с интерфейсной ссылкой (`w`), ничего не знает о конкретных классах `Button` или `TextBox`. Он знает только о контракте `IWidget`. Это снижает связанность кода (Loose Coupling) и делает архитектуру гибкой к изменениям.

### Разобранный пример: реализация интерфейса `ILoggable`

Давайте спроектируем консольное приложение на C# (.NET 8), которое демонстрирует создание интерфейса, его реализацию в классе, а также полиморфный вызов метода через интерфейсную ссылку.

#### Условие задачи
Разработать интерфейс `ILoggable`, содержащий метод `Log(string message)` и логическое свойство `IsActive`. Реализовать этот интерфейс в классе `ConsoleLogger`, который выводит переданное сообщение в консоль, добавляя к нему текущую метку времени (например, `[14:32:05] Сообщение`). Если свойство `IsActive` установлено в значение `false`, метод `Log` не должен выполнять никаких действий. В методе `Main` создать объект класса через интерфейсную ссылку и продемонстрировать его работу.

#### Рисунок схемы связей (в текстовом виде)
```
+------------------------+
|   <<interface>>        |
|       ILoggable        |
+------------------------+
| + IsActive: bool       |
| + Log(string): void    |
+-----------^------------+
            | реализует
+-----------+------------+
|     ConsoleLogger      |
+------------------------+
| - isActive: bool       |
| + IsActive: bool       |
| + Log(string): void    |
+------------------------+
```

#### Ход рассуждений
1. Объявляем интерфейс `ILoggable`. В нем определяем свойство с доступными `get` и `set`, а также метод `Log`, принимающий строку и ничего не возвращающий (`void`).
2. Создаем класс `ConsoleLogger`. Поскольку интерфейс не хранит состояние, классу необходима закрытая переменная (поле) `isActive` для хранения значения свойства.
3. Реализуем свойство `IsActive`, которое транслирует чтение и запись в наше поле `isActive`.
4. В методе `Log(string message)` проверяем: если `IsActive` равен `true`, формируем строку с текущим временем (используя класс `DateTime.Now`) и выводим её на экран через `Console.WriteLine`. Если `false` — выходим из метода (ничего не делаем).
5. В исполняющем классе `Program` с методом `Main` объявляем переменную типа интерфейса `ILoggable logger = new ConsoleLogger();`. Вызываем свойство, затем метод `Log`. Меняем состояние свойства в `false` и снова вызываем метод, чтобы проверить защитную логику.

#### Полный исходный код программы

```csharp
using System;

namespace ConsoleAppInterfaceDemo
{
    // 1. Объявление интерфейса (контракта)
    public interface ILoggable
    {
        // Свойство для включения/выключения логирования
        bool IsActive { get; set; }

        // Метод записи лога
        void Log(string message);
    }

    // 2. Реализация интерфейса в классе ConsoleLogger
    public class ConsoleLogger : ILoggable
    {
        // Закрытое поле для хранения состояния свойства (так как интерфейс не имеет полей)
        private bool _isActive;

        // Конструктор по умолчанию: по умолчанию логгер активен
        public ConsoleLogger()
        {
            _isActive = true;
        }

        // Явная реализация свойства из интерфейса ILoggable
        public bool IsActive
        {
            get { return _isActive; }
            set { _isActive = value; }
        }

        // Реализация метода Log из интерфейса ILoggable
        public void Log(string message)
        {
            // Проверка контракта: если логирование выключено, ничего не делаем
            if (!_isActive)
            {
                return;
            }

            // Получаем текущее системное время в формате ЧЧ:ММ:СС
            string timeStamp = DateTime.Now.ToString("HH:mm:ss");

            // Вывод отформатированного сообщения в консоль
            Console.WriteLine($"[{timeStamp}] {message}");
        }
    }

    // 3. Главный класс программы
    class Program
    {
        static void Main(string[] args)
        {
            // Создание объекта класса ConsoleLogger, но сохранение ссылки в переменную интерфейсного типа ILoggable
            // Это демонстрирует полиморфизм: мы работаем с объектом исключительно через призму контракта.
            ILoggable logger = new ConsoleLogger();

            Console.WriteLine("Проверка 1: Логгер активен по умолчанию.");
            logger.Log("Система инициализирована успешно.");
            logger.Log("Загрузка пользовательских модулей завершена.");

            Console.WriteLine("\nПроверка 2: Отключаем логгер через свойство интерфейса.");
            logger.IsActive = false; // Меняем состояние
            
            // Это сообщение не должно вывестись на экран, так как IsActive == false
            logger.Log("Внимание: Попытка записи при выключенном логгере.");

            Console.WriteLine("\nПроверка 3: Включаем логгер обратно.");
            logger.IsActive = true;
            logger.Log("Работа приложения продолжена в штатном режиме.");

            // Задержка консоли для визуального контроля
            Console.WriteLine("\nНажмите любую клавишу для выхода...");
            Console.ReadKey();
        }
    }
}
```

#### Пояснение по строкам и блокам кода
- `public interface ILoggable` — объявляет публичный контракт, доступный для реализации любым классам проекта.
- `public bool IsActive { get; set; }` — определяет контракт свойства с операциями чтения и записи.
- `private bool _isActive;` в классе `ConsoleLogger` — компенсирует отсутствие полей в интерфейсах. Интерфейс задает *правило*, а класс обеспечивает его *физическое хранение*.
- `ILoggable logger = new ConsoleLogger();` — классический пример восходящего преобразования (Upcasting). Переменная имеет тип интерфейса, поэтому компилятор разрешает вызывать только те члены, которые описаны в `ILoggable`. Попытка вызвать метод, существующий только в `ConsoleLogger`, вызовет ошибку компиляции.

#### Пример ввода и вывода программы

**Ввод данных:**
Программа работает автономно без ввода с клавиатуры, однако состояние свойства `IsActive` изменяется программно.

**Вывод в консоли:**

#### Оценка сложности
- **Пространственная сложность (Memory Complexity):** $O(1)$ для создания экземпляра `ConsoleLogger`, так как он хранит ровно одно логическое поле `_isActive` и указатель на таблицу методов в куче.
- **Временная сложность (Time Complexity):** $O(1)$ для вызова метода `Log` и обращения к свойству `IsActive`, так как вызов интерфейсного метода в .NET оптимизирован и выполняется за константное время с минимальными накладными расходами на динамическое связывание.

## 2. Множественное наследование интерфейсов и явная реализация

### Проблема множественного наследования классов и роль интерфейсов

В языке программирования C#, как и в Java, реализована концепция **одиночного наследования классов**. Это означает, что каждый класс может иметь ровно одного непосредственного базового родителя (родительский класс указывается после двоеточия). Множественное наследование классов (когда у одного класса есть два и более прямых базовых класса) запрещено компилятором намеренно.

Чтобы понять, почему введено это ограничение, рассмотрим классическую проблему объектно-ориентированного проектирования, известную как **«Проблема ромба» (Diamond Problem)**. 

Представьте себе следующую схему классов:
- Существует базовый класс `A`, содержащий некоторый метод `Execute()`.
- Два производных класса, `B` и `C`, наследуются от `A` и переопределяют метод `Execute()` по-своему.
- Четвёртый класс, `D`, пытается наследоваться одновременно и от `B`, и от `C` (множественное наследование классов).

```
    [ A ] (базовый класс с методом Execute)
   /     \
  v       v
[ B ]     [ C ] (переопределяют Execute)
  \       /
   v     v
    [ D ]  <- КАКОЙ метод Execute() вызывать в D? (Проблема ромба)
```

Возникает критическая двусмысленность: если программист вызывает метод `Execute()` у объекта класса `D`, то какой именно метод должен быть вызван — унаследованный по пути от `B` или по пути от `C`? Компилятор не может принять это решение автоматически, что приводит к конфликтам в памяти, неопределенному поведению и усложнению архитектуры компилятора.

Однако на практике часто возникает необходимость объединить поведение нескольких независимых сущностей в одном классе. Например, класс `FileStream` должен уметь как читать данные, так и записывать их, а также закрывать соединение. Решением этой архитектурной задачи в C# являются **интерфейсы**. 

> **Определение.** Интерфейс в C# — это ссылочный тип данных, который задает чистый контракт поведения без реализации (за исключением современных возможностей реализации по умолчанию). Интерфейсы не содержат полей состояния, не имеют конструкторов и не хранят данные в памяти.

Поскольку интерфейсы определяют *что* должен делать объект, но не *как* именно он это делает (у них нет полей и логики в традиционных методах), **множественное наследование интерфейсов полностью разрешено и безопасно**. Один класс может реализовывать любое количество интерфейсов одновременно, избегая проблемы ромба, так как у интерфейсов нет собственного состояния и конфликтующего кода логики.

### Наследование интерфейсов: расширение контракта

Интерфейсы могут не только реализовываться классами, но и наследоваться друг от друга. Когда один интерфейс наследует другой, он расширяет существующий контракт, добавляя новые требования к будущим реализациям.

Синтаксис наследования интерфейсов аналогичен наследованию классов: после имени интерфейса ставится двоеточие и перечисляются базовые интерфейсы.

> **Правило.** Интерфейс может наследовать один или сразу несколько других интерфейсов через запятую.

Рассмотрим пример иерархии интерфейсов для работы с устройствами ввода-вывода. Пусть у нас есть базовый контракт для чтения `IReader` и контракт для записи `IWriter`. Мы можем создать объединенный интерфейс `IDevice`, который будет требовать выполнения обоих контрактов:

```csharp
// Базовый интерфейс для чтения
public interface IReader
{
    string Read();
}

// Базовый интерфейс для записи
public interface IWriter
{
    void Write(string data);
}

// Расширенный интерфейс, наследующий оба предыдущих контракта
public interface IDevice : IReader, IWriter
{
    void Reset();
}
```

Если некоторый класс решает реализовать интерфейс `IDevice`, он обязан предоставить конкретный код для *всех* методов цепочки наследования: и для `Read()`, и для `Write()`, и для `Reset()`. Компилятор проверит наличие каждого метода.

### Реализация нескольких интерфейсов одним классом

Когда класс реализует несколько интерфейсов, их имена перечисляются через запятую после двоеточия после имени класса. Если среди базовых интерфейсов присутствует базовый класс, то сначала всегда указывается класс (он может быть только один), а затем через запятую перечисляются все реализуемые интерфейсы.

> **Синтаксис.** `class ClassName : BaseClass, IInterface1, IInterface2, IInterface3`

Рассмотрим, как класс может неявно реализовать несколько интерфейсов, если их методы имеют уникальные имена.

```csharp
public interface I1
{
    void MethodA();
}

public interface I2
{
    void MethodB();
}

// Класс реализует сразу два интерфейса
public class Worker : I1, I2
{
    public void MethodA()
    {
        Console.WriteLine("Реализация MethodA из интерфейса I1");
    }

    public void MethodB()
    {
        Console.WriteLine("Реализация MethodB из интерфейса I2");
    }
}
```

При такой **неявной реализации** (Implicit Interface Implementation) методы автоматически становятся частью открытого (`public`) интерфейса самого класса `Worker`. Это значит, что мы можем вызвать метод `MethodA()` как через ссылку на сам класс `Worker`, так и через ссылку на интерфейс `I1`.

### Конфликт имён и явная реализация интерфейсов

Что происходит, если класс реализует два разных интерфейса, в которых объявлены члены с **абсолютно одинаковой сигнатурой** (одинаковое имя возвращаемого значения, имя метода и набор параметров)? 

Представьте ситуацию: интерфейс `IReader` содержит метод `void Process()`, и интерфейс `IWriter` также содержит метод `void Process()`. Если класс `SmartDevice` реализует оба этих интерфейса, то создание обычного публичного метода `public void Process()` приведёт к тому, что этот единственный метод попытается удовлетворить оба контракта одновременно. Но что делать, если логика обработки для чтения и для записи должна отличаться? Более того, сигнатуры могут совпадать полностью, а требования к поведению — нет.

Для решения этой проблемы в C# предусмотрена **явная реализация интерфейса** (Explicit Interface Implementation).

> **Определение.** Явная реализация интерфейса — это способ определения метода класса, при котором имя члена предваряется именем интерфейса с точкой (`InterfaceName.MemberName`). Такой член принадлежит строго этому интерфейсу и скрыт в самом классе.

Ключевые особенности явной реализации:
1. К явно реализованным членам **нельзя** применять модификаторы доступа (`public`, `private`, `protected`). По умолчанию они неявно являются приватными с точки зрения самого класса.
2. К явно реализованным членам **нельзя** обратиться напрямую через объект класса (например, `obj.Process()` вызовет ошибку компиляции).
3. Доступ к явно реализованному члену возможен **только** через приведение ссылки на объект к типу соответствующего интерфейса.

Рассмотрим синтаксис явной реализации на схематичном примере:

```csharp
public interface IReader
{
    void Execute();
}

public interface IWriter
{
    void Execute();
}

public class MultiProcessor : IReader, IWriter
{
    // Явная реализация для IReader
    void IReader.Execute()
    {
        Console.WriteLine("Выполнение чтения данных");
    }

    // Явная реализация для IWriter
    void IWriter.Execute()
    {
        Console.WriteLine("Выполнение записи данных");
    }
}
```

В коде выше метод `Execute()` реализован дважды. Класс `MultiProcessor` не имеет открытого метода `Execute` в своем публичном интерфейсе. Если мы напишем:
```csharp
MultiProcessor mp = new MultiProcessor();
// mp.Execute(); // Ошибка компиляции! Метод не найден на уровне класса.
```
То компилятор выдаст ошибку. Вызвать эти методы можно только через интерфейсные ссылки:
```csharp
IReader reader = mp;
reader.Execute(); // Выведет: "Выполнение чтения данных"

IWriter writer = mp;
writer.Execute(); // Выведет: "Выполнение записи данных"
```
Этот мощный механизм позволяет одному классу разрешать любые конфликты имен методов, пришедших из разных контрактов.

### Разобранный пример: Умное устройство с интерфейсами `IReader` и `IWriter`

Разработаем полностью компилируемую программу на C#. 

**Условие задачи:**
1. Создать интерфейс `IReader` с методом `string Read()`.
2. Создать интерфейс `IWriter` с методом `void Write(string data)`.
3. Создать класс `SmartDevice`, который моделирует работу универсального устройства. Класс должен реализовывать оба интерфейса. Поскольку в реальной системе чтение и запись могут использовать общую или раздельные шины данных, реализуем метод `Read()` неявно (как обычный публичный метод класса), а метод `Write()` реализуем как явно для интерфейса `IWriter` (например, чтобы запись требовала специального системного разрешения), либо реализуем оба метода в зависимости от архитектурных потребностей (сделаем один метод явным для демонстрации). Пусть класс хранит внутри себя строковое поле состояния `buffer`.
4. В методе `Main` создать экземпляр `SmartDevice`, записать в него строку через интерфейсную ссылку `IWriter`, прочитать строку через неявный метод класса или интерфейс `IReader`, и вывести результат в консоль.

#### Рисунок схемы связей (в виде текста и блоков):
```
[Интерфейс IReader]          [Интерфейс IWriter]
  - string Read()              - void Write(string data)
         ^                            ^
         | (неявная реализация)       | (явная реализация)
         +--------------+-------------+
                        |
               [Класс SmartDevice]
                 - string buffer
                 - Read() (публичный)
                 - IWriter.Write() (явный)
```

#### Ход рассуждений при проектировании:
1. Объявляем интерфейсы `IReader` и `IWriter` с точными сигнатурами из условия.
2. Проектируем класс `SmartDevice`. У него будет приватное поле `private string dataBuffer = "Пусто";`, которое будет хранить текущее состояние памяти устройства.
3. Метод `Read()` из интерфейса `IReader` сделаем обычным публичным методом класса `public string Read()`. Это позволит вызывать его как напрямую через объект `SmartDevice`, так и через переменную типа `IReader`. Он будет возвращать содержимое `dataBuffer`.
4. Метод `Write(string data)` из интерфейса `IWriter` реализуем явно (`void IWriter.Write(string data)`), чтобы продемонстрировать работу с явной реализацией интерфейсов при конфликтах или необходимости сокрытия метода от прямого вызова. Он будет записывать переданный аргумент в `dataBuffer`.
5. В функции `Main` создадим объект `SmartDevice device = new SmartDevice();`.
6. Вызовем метод записи, приведя ссылку к интерфейсу `IWriter writer = device; writer.Write("Тестовые данные 2024");`.
7. Вызовем метод чтения напрямую через объект `Console.WriteLine(device.Read());` или через интерфейсную ссылку `IReader reader = device; Console.WriteLine(reader.Read());`.

#### Полный листинг программы на C#:

```csharp
using System;

namespace InterfaceApp
{
    // 1. Объявление интерфейса IReader
    public interface IReader
    {
        string Read();
    }

    // 2. Объявление интерфейса IWriter
    public interface IWriter
    {
        void Write(string data);
    }

    // 3. Класс SmartDevice, реализующий оба интерфейса
    public class SmartDevice : IReader, IWriter
    {
        // Внутреннее состояние устройства (буфер данных)
        private string dataBuffer = "Инициализировано по умолчанию";

        // Неявная реализация метода Read из интерфейса IReader
        // Так как метод публичный, он удовлетворяет контракту IReader
        // и одновременно доступен напрямую у экземпляра класса SmartDevice.
        public string Read()
        {
            Console.WriteLine("[SmartDevice] Вызван метод чтения данных.");
            return dataBuffer;
        }

        // Явная реализация метода Write из интерфейса IWriter
        // Обратите внимание на синтаксис: имя интерфейса перед именем метода.
        // Модификаторы доступа здесь указывать запрещено.
        void IWriter.Write(string data)
        {
            Console.WriteLine("[SmartDevice] Вызван явно реализованный метод записи.");
            if (string.IsNullOrEmpty(data))
            {
                dataBuffer = "Ошибка: переданы пустые данные";
            }
            else
            {
                dataBuffer = data;
            }
        }
    }

    // Главный класс программы
    public class Program
    {
        public static void Main(string[] args)
        {
            // Создаем экземпляр класса SmartDevice
            SmartDevice myDevice = new SmartDevice();

            // Читаем начальное состояние напрямую через объект класса
            // (так как метод Read реализован неявно и является публичным)
            Console.WriteLine("Начальное чтение напрямую из объекта:");
            string initialValue = myDevice.Read();
            Console.WriteLine($"Результат: {initialValue}\n");

            // Пытаемся записать данные через интерфейсную ссылку IWriter,
            // так как метод Write реализован явно и недоступен через myDevice.Write(...)
            IWriter writerRef = myDevice;
            writerRef.Write("Системный пакет данных #404");

            // Проверяем изменение данных, используя интерфейсную ссылку IReader
            IReader readerRef = myDevice;
            Console.WriteLine("\nЧтение данных через интерфейсную ссылку IReader:");
            string updatedValue = readerRef.Read();
            Console.WriteLine($"Результат: {updatedValue}");

            // Демонстрация того, что явный метод недоступен напрямую
            // Следующая строка кода вызвала бы ошибку компиляции CS1061:
            // myDevice.Write("Прямой вызов"); 
            // Компилятор защищает скрытый интерфейсный метод от некорректного использования.
        }
    }
}
```

#### Проверка и анализ результатов:
- **Единицы измерения и типы:** В программе используются стандартные ссылочные типы C# (`string`), интерфейсы (`IReader`, `IWriter`) и классы. Ошибок несоответствия типов нет.
- **Правдоподобность логики:** Код компилируется без предупреждений в среде .NET 8. Явная реализация скрывает метод записи от случайного вызова на уровне класса, заставляя разработчика использовать интерфейсный контракт `IWriter`, что полностью соответствует архитектурной задумке защищенных устройств ввода-вывода.

#### Пример вывода программы в консоль:
```text

[SmartDevice] Вызван метод чтения данных.
Результат: Инициализировано по умолчанию

[SmartDevice] Вызван явно реализованный метод записи.
```

## 3. Перегрузка (Overloading) vs Переопределение (Overriding)

### Четкое разграничение терминов: перегрузка и переопределение

При проектировании объектно-ориентированных систем на языке C# разработчик часто сталкивается с необходимостью создания методов со схожими именами или изменения поведения унаследованных от базового класса методов. Для решения этих задач применяются два принципиально разных механизма: **перегрузка (overloading)** и **переопределение (overriding)**. Путать эти понятия нельзя, так как они работают на разных этапах жизненного цикла программы и решают совершенно разные архитектурные задачи.

> **Определение.** **Перегрузка методов (Method Overloading)** — это создание в рамках одной области видимости (например, внутри одного класса) нескольких методов с одинаковым именем, но с **разными сигнатурами**. 

> **Определение.** **Переопределение методов (Method Overriding)** — это процесс изменения реализации виртуального метода, унаследованного из базового класса, в производном классе с сохранением той же сигнатуры.

Главное концептуальное различие между ними заключается в моменте принятия решения о том, какой именно кусок кода будет выполнен:

1. **Перегрузка (статическое связывание / compile-time binding):** Компилятор во время сборки программы точно знает, версию какого метода нужно вызвать. Выбор основывается исключительно на типах переданных аргументов в момент вызова. Если типы аргументов не совпадают ни с одной сигнатурой, программа не скомпилируется.
2. **Переопределение (динамическое связывание / run-time binding):** Компилятор во время компиляции может не знать точный тип объекта. Если объект создается динамически (например, базовая ссылка указывает на экземпляр производного класса), то выбор вызываемого метода происходит **во время выполнения программы (runtime)** на основе реального типа объекта в памяти.

---

### Правила перегрузки методов в C#

Чтобы компилятор C# мог отличить один метод от другого при перегрузке, они должны иметь уникальную сигнатуру.

> **Определение.** **Сигнатура метода** — это совокупность имени метода, а также количества, типов и порядка следования его параметров. 

Важнейшее правило, которое необходимо запомнить раз и навсегда: **тип возвращаемого значения и модификаторы параметров `ref`/`out` (в определенных контекстах) не входят в сигнатуру метода для целей перегрузки**. Вы не можете перегрузить метод только за счет изменения типа возвращаемого значения.

Основные правила перегрузки:
- Имена методов должны быть абсолютно одинаковыми.
- Список параметров (сигнатура) должен отличаться: либо количеством параметров, либо типами параметров, либо их порядком (если типы различаются).

Рассмотрим пример правильной перегрузки:

```csharp
class MathOperations
{
    // Метод 1: два целочисленных параметра
    public int Add(int a, int b)
    {
        return a + b;
    }

    // Метод 2: три целочисленных параметра (отличается количеством)
    public int Add(int a, int b, int c)
    {
        return a + b + c;
    }

    // Метод 3: два параметра типа double (отличается типом данных)
    public double Add(double a, double b)
    {
        return a + b;
    }
}
```

Если попытаться добавить метод `public double Add(int a, int b)`, компилятор выдаст ошибку `Type 'MathOperations' already defines a member called 'Add' with the same parameter types`, так как возвращаемый тип (`double` вместо `int`) не учитывается компилятором при поиске нужного метода.

---

### Механизм виртуальных методов: `virtual` и `override`

Переопределение позволяет реализовать полиморфизм — свойство системы использовать единый интерфейс для работы с объектами разных типов. 

По умолчанию в C# все методы являются «статическими» с точки зрения вызова в иерархии: если вы вызываете метод через ссылку базового класса, будет вызван метод базового класса, даже если в памяти лежит объект производного. Чтобы разрешить дочернему классу изменять поведение метода, базовый класс должен явно разрешить это с помощью ключевого слова `virtual`.

- Ключевое слово **`virtual`** ставится перед сигнатурой метода в **базовом** классе. Оно сообщает компилятору: «Этот метод может быть изменен в классах-наследниках».
- Ключевое слово **`override`** ставится перед сигнатурой метода в **производном** классе. Оно явно указывает, что данный метод заменяет виртуальную реализацию из базового класса.

Если в производном классе забыть написать `override` и просто написать метод с тем же именем, то произойдет не переопределение, а *сокрытие* метода (компилятор выдаст предупреждение CS0108), и полиморфизм работать не будет.

---

### Запрет переопределения: ключевое слово `sealed`

Иногда при проектировании иерархий классов возникает необходимость зафиксировать поведение метода и запретить его дальнейшее переопределение в более глубоких наследниках. Для этого используется модификатор **`sealed`** (запечатанный) совместно с ключевым словом `override`.

Если класс B унаследован от A, а класс C унаследован от B:

```csharp
class BaseClass
{
    public virtual void DoWork() { /* ... */ }
}

class DerivedClass : BaseClass
{
    public sealed override void DoWork() { /* ... */ }
}

class FurtherDerivedClass : DerivedClass
{
    // ОШИБКА КОМПИЛЯЦИИ: нельзя переопределить запечатанный метод DoWork
    // public override void DoWork() { /* ... */ }
}
```
Модификатор `sealed` на методе повышает безопасность кода и помогает проектировщику гарантировать, что критически важная бизнес-логика не будет непреднамеренно изменена в будущих поколениях классов.

---

### Сокрытие членов класса (`new`)

Что происходит, если в производном классе объявляется метод с точно такой же сигнатурой, как в базовом классе, но при этом в базовом классе метод *не* был помечен как `virtual`, а в производном не используется `override`?

В таком случае компилятор C# выдает предупреждение о том, что метод скрывает унаследованный член. Чтобы явно указать компилятору, что это сделано намеренно, используется ключевое слово **`new`** перед сигнатурой метода в производном классе.

> **Внимание!** Сокрытие членов (`new`) **не имеет никакого отношения к полиморфизму**. Вызов скрытого метода жестко привязывается к типу ссылки, через которую происходит вызов.

Сравним поведение переопределения (`override`) и сокрытия (`new`):
- При `override` (динамическое связывание) важен **тип объекта в памяти** (реальный тип созданного экземпляра).
- При `new` (статическое связывание) важен **тип переменной** (тип ссылки), в которой этот объект сохранен.

Опытные разработчики настоятельно рекомендуют избегать использования сокрытия членов через `new` без крайней необходимости, так как это приводит к запутанному коду и нарушению логики полиморфизма.

### Концептуальный анализ таблицы виртуальных методов (vtable)

Чтобы понимать, как работает динамический полиморфизм «под капотом», рассмотрим концепцию **vtable (Virtual Method Table — таблица виртуальных методов)**.

Когда в классе появляется хотя бы один виртуальный метод (`virtual`), среда выполнения .NET во время создания класса выделяет в памяти специальную структуру данных — таблицу виртуальных методов. 
- Каждый класс в иерархии имеет свою vtable.
- Элементы vtable представляют собой указатели на конкретные исполняемые машинные инструкции методов, которые должны быть вызваны для данного класса.

Когда вы создаете объект класса с помощью оператора `new`, в памяти помимо полей самого объекта выделяется скрытый системный указатель (называемый часто `pointer-to-vtable` или `vptr`), который указывает на vtable соответствующего класса.

**Алгоритм работы динамического вызова:**
1. Вы вызываете виртуальный метод через ссылку базового типа: `BaseClass obj = new DerivedClass(); obj.VirtualMethod();`
2. Так как тип ссылки `BaseClass`, компилятор генерирует код, который смотрит не на фиксированный адрес функции, а обращается к объекту в памяти по указателю `vptr`.
3. Программа определяет реальный тип объекта (`DerivedClass`) и находит его vtable.
4. Из таблицы берётся актуальный адрес переопределенного метода (`override`) для `DerivedClass` и происходит переход на его выполнение.

Именно поэтому переопределение работает быстрее, чем рефлексия, но имеет минимальные накладные расходы на одно разыменование указателя в памяти по сравнению с обычным вызовом статического метода.

### Разобранный пример: Калькулятор, виртуальные методы и переопределение

Давайте решим комплексную практическую задачу, которая объединяет перегрузку методов, создание базового и производного классов, а также механизм виртуальных методов и переопределения (`override`).

#### Условие задачи
1. Создать класс `Calculator`, содержащий перегруженные методы `Sum`:
   - первый метод принимает два целых числа (`int`, `int`) и возвращает их сумму;
   - второй метод принимает три целых числа (`int`, `int`, `int`) и возвращает их сумму;
   - третий метод принимает два числа с плавающей точкой (`double`, `double`) и возвращает их сумму.
2. Создать базовый класс `Operation`, содержащий защищенное поле `string name` (название операции) и виртуальный метод `public virtual double Execute(double a, double b)`, который возвращает `0.0`.
3. Создать производный класс `AdvancedOperation`, наследующий `Operation`. В нем переопределить метод `Execute` (`override`), реализовав возведение первого числа в степень второго ($a^b$, используя класс `Math.Pow`).
4. Написать консольную программу (`Main`), в которой протестировать все созданные классы и методы, продемонстрировав как статическое связывание (перегрузка), так и динамическое связывание (полиморфизм через виртуальные методы).

#### Рисунок схемы связей классов (словами)
```
[ Calculator ] 
 (Содержит 3 перегруженных метода Sum для разных типов и количеств аргументов)

[ Operation ] (Базовый класс)
 ├── Поле: protected string name
 └── Метод: public virtual double Execute(double a, double b) -> возвращает 0.0
       ▲
       │ наследование
       │
[ AdvancedOperation ] (Производный класс)
 └── Метод: public override double Execute(double a, double b) -> возвращает Math.Pow(a, b)
```

#### Ход рассуждений (почему делаем именно так)
1. **Для класса `Calculator`:** Нам нужно три метода с именем `Sum`. Так как их имена совпадают, мы должны убедиться, что их сигнатуры различаются. Для этого варьируем количество параметров (2 и 3) и типы параметров (`int` и `double`). Тип возвращаемого значения для целочисленных методов сделаем `int`, для вещественных — `double`.
2. **Для класса `Operation`:** По условию требуется виртуальный метод. Указываем ключевое слово `virtual` перед методом `Execute`. Поле `name` делаем `protected`, чтобы производный класс имел к нему прямой доступ, а внешний код мог инкапсулировать его через конструктор.
3. **Для класса `AdvancedOperation`:** Наследуем его от `Operation` через двоеточие (`: Operation`). Внутри класса пишем метод с точно такой же сигнатурой, как в базовом классе, но добавляем ключевое слово `override`. Внутри метода вызываем стандартную библиотечную функцию `Math.Pow(a, b)`.
4. **В методе `Main`:** Создаем экземпляр `Calculator` и вызываем перегруженные методы. Затем создаем переменную базового типа `Operation`, в которую записываем объект производного класса `AdvancedOperation`, и вызываем метод `Execute` — это покажет работу полиморфизма (динамического связывания).

#### Полный листинг программы на C#

```csharp
using System;

namespace CourseApp
{
    // Класс для демонстрации перегрузки методов (Overloading)
    class Calculator
    {
        // Перегрузка 1: два целочисленных параметра
        public int Sum(int a, int b)
        {
            Console.WriteLine("[Calculator] Вызван метод Sum(int, int)");
            return a + b;
        }

        // Перегрузка 2: три целочисленных параметра
        public int Sum(int a, int b, int c)
        {
            Console.WriteLine("[Calculator] Вызван метод Sum(int, int, int)");
            return a + b + c;
        }

        // Перегрузка 3: два вещественных параметра
        public double Sum(double a, double b)
        {
            Console.WriteLine("[Calculator] Вызван метод Sum(double, double)");
            return a + b;
        }
    }

    // Базовый класс для демонстрации виртуальных методов
    class Operation
    {
        protected string operationName;

        public Operation(string name)
        {
            operationName = name;
        }

        // Виртуальный метод, разрешающий переопределение в наследниках
        public virtual double Execute(double a, double b)
        {
            Console.WriteLine($"[Operation] Базовая операция '{operationName}' не задана.");
            return 0.0;
        }

        public string GetName()
        {
            return operationName;
        }
    }

    // Производный класс, переопределяющий виртуальный метод (Overriding)
    class AdvancedOperation : Operation
    {
        public AdvancedOperation(string name) : base(name)
        {
        }

        // Переопределение метода базового класса
        public override double Execute(double a, double b)
        {
            Console.WriteLine($"[AdvancedOperation] Выполнение операции возведения в степень: {a}^{b}");
            return Math.Pow(a, b);
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Установка кодировки консоли для корректного отображения кириллицы
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            Console.WriteLine("--- ДЕМОНСТРАЦИЯ ПЕРЕГРУЗКИ МЕТОДОВ (OVERLOADING) ---");
            Calculator calc = new Calculator();

            int res1 = calc.Sum(10, 20);
            Console.WriteLine($"Результат Sum(10, 20) = {res1}\n");

            int res2 = calc.Sum(5, 15, 25);
            Console.WriteLine($"Результат Sum(5, 15, 25) = {res2}\n");

            double res3 = calc.Sum(4.5, 5.5);
            Console.WriteLine($"Результат Sum(4.5, 5.5) = {res3}\n");


            Console.WriteLine("--- ДЕМОНСТРАЦИЯ ПЕРЕОПРЕДЕЛЕНИЯ И ПОЛИМОРФИЗМА (OVERRIDING) ---");
            
            // Создаем объект производного класса, сохраняя его в переменную базового типа (полиморфизм)
            Operation op = new AdvancedOperation("Возведение в степень");

            Console.WriteLine($"Имя операции: {op.GetName()}");

            // Во время выполнения будет вызван метод из AdvancedOperation, а не из Operation
            double powResult = op.Execute(2.0, 3.0);
            
            Console.WriteLine($"Результат Execute(2.0, 3.0) = {powResult}");

            // Ожидание нажатия клавиши для завершения программы
            Console.WriteLine("\nНажмите любую клавишу для выхода...");
            Console.ReadKey();
        }
    }
}
```

#### Пояснения к коду по строкам и блокам
- Строки 7–29 (`Calculator`): Класс содержит три метода с одинаковым именем `Sum`. Компилятор выбирает нужный метод строго во время компиляции на основе переданных аргументов.
- Строки 32–49 (`Operation`): Базовый класс, содержащий защищенное поле `operationName` и виртуальный метод `Execute`, помеченный ключевым словом `virtual`.
- Строки 52–63 (`AdvancedOperation`): Производный класс. Конструктор вызывает базовый конструктор через ключевое слово `base(name)`. Метод `Execute` помечен как `override`, заменяя логику базового класса на расчет степени через `Math.Pow`.
- Строки 81–82 (`Main`): Демонстрация полиморфизма. Пересылка объекта `AdvancedOperation` в переменную типа `Operation` позволяет вызывать метод через единый интерфейс базового класса, но с фактическим выполнением кода из дочернего класса благодаря динамическому связыванию.

#### Пример ввода и вывода программы
Так как программа не запрашивает ввод с клавиатуры, примером «ввода» выступают жестко заданные аргументы методов.

**Вывод в консоли:**
```text
--- ДЕМОНСТРАЦИЯ ПЕРЕГРУЗКИ МЕТОДОВ (OVERLOADING) ---
[Calculator] Вызван метод Sum(int, int)
Результат Sum(10, 20) = 30

[Calculator] Вызван метод Sum(int, int, int)
Результат Sum(5, 15, 25) = 45

[Calculator] Вызван метод Sum(double, double)
Результат Sum(4.5, 5.5) = 10.0

--- ДЕМОНСТРАЦИЯ ПЕРЕОПРЕДЕЛЕНИЯ И ПОЛИМОРФИЗМА (OVERRIDING) ---
Имя операции: Возведение в степень
[AdvancedOperation] Выполнение операции возведения в степень: 2^3

```

#### Проверка и оценка сложности
- **Проверка единиц и правдоподобия:** $10 + 20 = 30$ (верно), $5 + 15 + 25 = 45$ (верно), $4{,}5 + 5{,}5 = 10{,}0$ (верно), $2^3 = 8$ (верно). Типы данных соблюдены, переполнение типов отсутствует.
- **Оценка временной сложности:** 
  - Вызов перегруженных методов `Sum` имеет сложность $O(1)$, так как выбор метода происходит на этапе компиляции, а само сложение выполняется за константное время.
  - Вызов виртуального метода `Execute` через полиморфную ссылку имеет сложность $O(1)$ с минимальной микрооптимизационной наценкой на разыменование таблицы vtable (что на практике пренебрежимо мало).
- **Оценка пространственной сложности:** $O(1)$, так как создается фиксированное число объектов в памяти (`Calculator` и `AdvancedOperation`), не зависящее от внешних входных данных.

## 4. Проектирование сложных иерархий: абстрактные классы + интерфейсы

### Архитектурное разделение ролей: абстрактный класс против интерфейса

При проектировании сложных программных систем на языке C# разработчик регулярно сталкивается с архитектурной дилеммой: задействовать ли для создания базовой сущности абстрактный класс (`abstract class`) или интерфейс (`interface`). Ошибочный выбор на этапе проектирования приводит к жесткой связанности кода, дублированию логики или невозможности расширения функционала в будущем. Чтобы принимать осознанные проектные решения, необходимо четко понимать фундаментальные различия между этими конструкциями.

> **Определение.** Абстрактный класс — это базовый класс, который не может быть инстанцирован напрямую (через оператор `new`) и предназначен для создания иерархий родственных типов, обладающих общей структурой состояния (полями) и частично реализованным поведением.

> **Определение.** Интерфейс — это ссылочный тип, представляющий собой чистый контракт поведения. Он задает набор сигнатур (методов, свойств, событий, индексаторов), которые реализующий класс обязан предоставить, но при этом не содержит переменных состояния (полей) и базовой реализации логики (за исключением возможностей .NET Core 8.0+ с методами по умолчанию, однако их назначение иное — безопасное эволюционирование контрактов).

Сравним абстрактные классы и интерфейсы по ключевым критериям:

| Критерий | Абстрактный класс (`abstract class`) | Интерфейс (`interface`) |
|---|---|---|
| **Наличие состояния (поля)** | Может содержать любые поля (private, protected и т.д.). | Не может содержать поля экземпляра (только константы и статические поля). |
| **Реализация методов** | Может содержать как абстрактные методы (без тела), так и полностью реализованные методы. | Содержит только сигнатуры (если не используются методы интерфейса по умолчанию). |
| **Множественное наследование** | Поддерживает только одинарное наследование (класс может наследоваться только от одного класса). | Поддерживает множественное реализацию (класс может реализовать сколько угодно интерфейсов). |
| **Конструкторы** | Имеет конструкторы, которые вызываются при создании экземпляра производного класса. | Не имеет конструкторов. |
| **Степень родства** | Описывает отношение «является» (`Is-A`) для тесно связанных объектов одной иерархии. | Описывает отношение «способен к / обладает свойством» (`Can-Do`) для любых независимых классов. |

Принцип проектирования заключается в следующем:
1. **Используйте абстрактный класс**, когда вы проектируете иерархию *родственных* объектов, которые разделяют общий код, единую структуру данных (поля) и защищенные (`protected`) вспомогательные методы. Например, классы `Dog` и `Cat` являются частными случаями абстрактного класса `Animal`.
2. **Используйте интерфейс**, когда вам необходимо навязать единый контракт поведения для *абсолютно разных* классов, не связанных жестким родством по иерархии наследования. Например, класс `Car` (автомобиль) и класс `Employee` (сотрудник) не имеют общего биологического предка, но оба могут реализовывать интерфейс `IComparable` для сортировки или `ILoggable` для логирования действий.

---

### Комбинирование абстрактного класса и интерфейсов в одной иерархии

На практике мощные архитектурные решения строятся на синергии абстрактных классов и интерфейсов. Абстрактный класс берет на себя рутину: инкапсулирует общие поля, реализует базовую логику, общую для всех наследников, и закрывает часть шаблонного кода. Интерфейсы же позволяют навешивать на эти ветви иерархии независимые кросс-функциональные возможности.

Рассмотрим синтаксическое правило объявления класса, который одновременно наследует абстрактный класс и реализует интерфейсы.

> **Правило порядка при наследовании.** В сигнатуре объявления производного класса **всегда сначала указывается базовый класс** (если он есть), и **через запятую перечисляются все реализуемые интерфейсы**. Нарушение этого порядка приводит к ошибке компиляции.

Общая схема объявления выглядит следующим образом:
```csharp
public class DerivedClass : BaseAbstractClass, IInterfaceOne, IInterfaceTwo
{
    // Обязательная реализация абстрактных членов базового класса
    // и членов всех указанных интерфейсов
}
```

---

### Наследование интерфейса абстрактным классом

Интерфейс может наследоваться абстрактным классом. Это мощный прием проектирования, который позволяет переложить обязанность реализации части контракта интерфейса на промежуточный абстрактный уровень.

Когда абстрактный класс реализует интерфейс, у разработчика есть три пути:
1. Не реализовывать методы интерфейса вовсе, объявив их абстрактными в самом классе (перекладывая их реализацию на конкретных наследников).
2. Реализовать методы интерфейса прямо в абстрактном классе (тогда конечные наследники получают готовую функциональность).
3. Реализовать часть методов, а остальные оставить абстрактными.

Это позволяет создавать гибкие архитектурные каркасы, где базовые абстрактные классы предоставляют каркас поведения, а конечные классы уточняют детали.

---

### Типичные архитектурные паттерны проектирования на основе интерфейсов

В промышленной разработке на C# интерфейсы являются основой для большинства архитектурных шаблонов (Design Patterns):
- **Dependency Injection (Инверсия зависимости / Внедрение зависимостей):** Классы зависят не от конкретных реализаций (например, `SqlDatabase`), а от абстрактных интерфейсов (`IDatabase`), что позволяет подменять реализации налету (например, для модульного тестирования подставлять `MockDatabase`).
- **Strategy (Стратегия):** Семейство алгоритмов инкапсулируется в отдельные классы, реализующие общий интерфейс, позволяя менять поведение объекта во время выполнения программы.
- **Repository (Репозиторий):** Абстракция слоя работы с данными через интерфейсы `IRepository<T>`, изолирующая бизнес-логику от деталей хранения в БД или файлах.

### Разобранный пример: Иерархия графических редакторов

#### Постановка задачи
Спроектировать иерархию классов и интерфейсов для графического редактора. 
1. Создать абстрактный класс `Shape`, содержащий общие поля координат центра фигуры (`X`, `Y`) и абстрактный метод `GetArea()` для вычисления площади.
2. Создать интерфейс `IDrawable` с методом `Draw()`.
3. Создать интерфейс `IResizable` с методом `Resize(double factor)`.
4. Спроектировать конкретный класс `Rectangle` (прямоугольник), который наследует абстрактный класс `Shape` и реализует оба интерфейса (`IDrawable` и `IResizable`).
5. Написать консольную программу на C#, демонстрирующую создание объекта `Rectangle`, вычисление площади, изменение размера и отрисовку полиморфным образом.

#### Рисунок схемы связей (ASCII)
```text
+-----------------------+
| <<interface>>         |
| IDrawable             |
| + Draw()              |
+-----------^-----------+
            | реализует
+-----------+-----------+       +------------------------+
| <<interface>>         |       | abstract class         |
| IResizable            |       | Shape                  |
| + Resize(factor)      |       | # double x             |
+-----------^-----------+       | # double y             |
            | реализует         | + abstract GetArea()   |
            |                   +-----------^------------+
            |                               | наследует
            |       +-----------------------+
            |       |
    +-------+-------+-------+
    | class Rectangle       |
    | - double width        |
    | - double height       |
    | + GetArea()           |
    | + Draw()              |
    | + Resize(factor)      |
    +-----------------------+
```

#### Ход рассуждений
1. Координаты `X` и `Y` присущи абсолютно любой геометрической фигуре в декартовой системе координат. Логично заложить их в базовый абстрактный класс `Shape`, чтобы не дублировать код в каждом конкретном классе.
2. Площадь вычисляется по-разному для круга, прямоугольника или треугольника. Поэтому метод `GetArea()` не имеет универсальной формулы на уровне абстрактного класса и объявляется как `abstract`.
3. Способность быть отрисованным (`IDrawable`) и изменяемым в размерах (`IResizable`) — это независимые поведения (контракты). Прямоугольник обязан их поддерживать, поэтому он реализует оба интерфейса.
4. Класс `Rectangle` обязан предоставить конкретную реализацию для метода `GetArea()` (из `Shape`), метода `Draw()` (из `IDrawable`) и метода `Resize()` (из `IResizable`).

#### Полный код программы

```csharp
using System;

namespace GraphicEditorSystem
{
    // 1. Определение первого интерфейса: контракт для объектов, которые можно рисовать
    public interface IDrawable
    {
        void Draw();
    }

    // 2. Определение второго интерфейса: контракт для объектов, размер которых можно изменять
    public interface IResizable
    {
        void Resize(double factor);
    }

    // 3. Абстрактный базовый класс для всех геометрических фигур
    public abstract class Shape
    {
        // Поля состояния, общие для всех фигур (инкапсуляция через protected)
        protected double x;
        protected double y;

        // Конструктор абстрактного класса для инициализации координат
        protected Shape(double x, double y)
        {
            this.x = x;
            this.y = y;
        }

        // Абстрактный метод: потомки обязаны предоставить собственную формулу площади
        public abstract double GetArea();

        // Обычный виртуальный метод с базовой реализацией, которую можно переопределить
        public virtual void DisplayInfo()
        {
            Console.WriteLine($"Фигура расположена в точке: ({x:F1}; {y:F1})");
        }
    }

    // 4. Конкретный класс Rectangle: наследует Shape, реализует IDrawable и IResizable
    // Внимание: Сначала базовый класс, затем интерфейсы через запятую!
    public class Rectangle : Shape, IDrawable, IResizable
    {
        private double width;
        private double height;

        // Конструктор прямоугольника, вызывающий конструктор базового класса через ключевое слово base
        public Rectangle(double x, double y, double width, double height) : base(x, y)
        {
            this.width = width;
            this.height = height;
        }

        // Реализация абстрактного метода GetArea из класса Shape
        public override double GetArea()
        {
            return width * height;
        }

        // Реализация метода Draw из интерфейса IDrawable
        public void Draw()
        {
            Console.WriteLine($"Отрисовка прямоугольника с размерами {width:F1}x{height:F1} в координатах ({x:F1}; {y:F1})");
        }

        // Реализация метода Resize из интерфейса IResizable
        public void Resize(double factor)
        {
            if (factor <= 0)
            {
                throw new ArgumentException("Коэффициент масштабирования должен быть больше нуля.");
            }
            width *= factor;
            height *= factor;
            Console.WriteLine($"Прямоугольник масштабирован в {factor:F1} раз. Новые размеры: {width:F1}x{height:F1}");
        }

        // Переопределение виртуального метода базового класса для вывода специфичной информации
        public override void DisplayInfo()
        {
            base.DisplayInfo();
            Console.WriteLine($"Тип: Прямоугольник | Площадь: {GetArea():F2}");
        }
    }

    // 5. Главный класс программы для запуска и тестирования
    public class Program
    {
        public static void Main(string[] args)
        {
            // Создание конкретного экземпляра прямоугольника
            Rectangle rect = new Rectangle(10.0, 20.0, 5.0, 4.0);

            Console.WriteLine("--- Информация о начальном объекте ---");
            rect.DisplayInfo();
            rect.Draw();

            Console.WriteLine("\n--- Выполнение операций через интерфейсы и полиморфизм ---");
            
            // Полиморфное использование через интерфейсные ссылки
            IDrawable drawableItem = rect;
            drawableItem.Draw(); // Вызов метода через интерфейс IDrawable

            IResizable resizableItem = rect;
            resizableItem.Resize(2.5); // Изменение размера через интерфейс IResizable

            Console.WriteLine("\n--- Состояние объекта после изменения размера ---");
            rect.DisplayInfo();

            // Проверка граничных условий (обработка исключения для некорректного коэффициента)
            try
            {
                resizableItem.Resize(-1.0);
            }
            catch (ArgumentException ex)
            {
                Console.WriteLine($"Перехвачено ожидаемое исключение: {ex.Message}");
            }
        }
    }
}
```

#### Пояснение по строкам кода
- Строки `7–16`: Объявление интерфейсов `IDrawable` и `IResizable`. Они задают чистые контракты поведения без реализации.
- Строки `19–38`: Абстрактный класс `Shape`. Содержит состояние (`x`, `y`), конструктор для их инициализации и абстрактный метод `GetArea()`. Прямое создание объекта `new Shape(...)` вызовет ошибку компиляции.
- Строки `41–80`: Класс `Rectangle`. Объявление `public class Rectangle : Shape, IDrawable, IResizable` строго соблюдает порядок: сначала базовый класс `Shape`, затем через запятую интерфейсы. Реализованы все контрактные методы (`GetArea`, `Draw`, `Resize`).
- Строки `94–96`: Демонстрация полиморфизма. Ссылка типа `IDrawable` указывает на объект `Rectangle`, что позволяет вызывать метод `Draw()`, скрывая остальные детали реализации объекта.

## 5. Полный проект: Система управления плагинами и обработкой документов

### Постановка комплексной задачи

Для закрепления полученных знаний по интерфейсам, иерархиям классов и полиморфизму мы разработаем консольное приложение на языке C# (.NET 8), моделирующее модульную систему обработки текстовых документов. 

В реальной разработке программное обеспечение часто строится по принципу плагинов (plug-and-play). Это означает, что ядро программы ничего не знает о конкретных деталях реализации отдельных модулей обработки, а взаимодействует с ними исключительно через строгие контракты — интерфейсы. Такой подход обеспечивает слабую связанность (loose coupling), высокую расширяемость и простоту тестирования.

Наша задача — спроектировать и реализовать систему, которая:
1. Представляет текстовый документ как объект, содержащий метаданные и тело текста.
2. Предоставляет набор независимых плагинов для модификации или анализа текста (например, проверка орфографии/цензуры, шифрование методом Цезаря, добавление водяных знаков).
3. Использует валидаторы для проверки соответствия документа определенным правилам перед обработкой.
4. Позволяет применять цепочку плагинов к документу динамически через полиморфные коллекции интерфейсных ссылок.

---

### Архитектура приложения

Проектирование начинается с определения контрактов взаимодействия. Выделим три ключевых интерфейса:

- `IDocument` — описывает сущность документа, доступ к его содержимому и состоянию (изменен / не изменен).
- `IValidator` — определяет контракт для проверки документа на соответствие заданным условиям.
- `IPlugin` — определяет контракт для модуля, выполняющего трансформацию или анализ документа.

Ниже приведена схема связей между компонентами системы, выраженная средствами UML-подобного описания в текстовом виде:

```text
[IDocument] <--- [TextDocument]
                         ^
                         | (обрабатывается)
[IPlugin] <----------------+
   ^
   |-- [EncryptionPlugin]
   |-- [WatermarkPlugin]
   
[IValidator] <--- [LengthValidator]
```

Каждый компонент выполняет свою зону ответственности, что полностью соответствует принципу единственной ответственности (Single Responsibility Principle) из SOLID.

### Реализация системы: полный листинг кода

Ниже представлен полный, самодостаточный и компилируемый код программы на C# (.NET 8). Код разбит на логические блоки с подробными комментариями к каждой строке и конструкции.

```csharp
using System;
using System.Collections.Generic;
using System.Text;

namespace DocumentProcessorSystem
{
    // Шаг 1. Определение контракта документа
    public interface IDocument
    {
        string Title { get; set; }
        string Content { get; set; }
        bool IsModified { get; set; }
        void Save();
    }

    // Шаг 2. Определение контракта валидатора
    public interface IValidator
    {
        bool Validate(IDocument document, out string errorMessage);
    }

    // Шаг 3. Определение контракта плагина обработки
    public interface IPlugin
    {
        string Name { get; }
        void Execute(IDocument document);
    }

    // Шаг 4. Конкретная реализация документа
    public class TextDocument : IDocument
    {
        public string Title { get; set; }
        public string Content { get; set; }
        public bool IsModified { get; set; }

        public TextDocument(string title, string content)
        {
            Title = title ?? throw new ArgumentNullException(nameof(title));
            Content = content ?? string.Empty;
            IsModified = false;
        }

        public void Save()
        {
            // Имитация сохранения документа в постоянную память
            Console.WriteLine($"[Система]: Документ '{Title}' успешно сохранен. Текущий текст: \"{Content}\"");
            IsModified = false;
        }
    }

    // Шаг 5. Реализация валидатора длины текста
    public class LengthValidator : IValidator
    {
        private readonly int _minLength;

        public LengthValidator(int minLength)
        {
            _minLength = minLength;
        }

        public bool Validate(IDocument document, out string errorMessage)
        {
            if (document == null)
            {
                errorMessage = "Документ не инициализирован.";
                return false;
            }

            if (document.Content.Length < _minLength)
            {
                errorMessage = $"Ошибка валидации: длина текста меньше минимальной ({document.Content.Length} < {_minLength}).";
                return false;
            }

            errorMessage = string.Empty;
            return true;
        }
    }

    // Шаг 6. Реализация плагина шифрования (простой шифр Цезаря со сдвигом 1)
    public class EncryptionPlugin : IPlugin
    {
        public string Name => "Модуль шифрования (Цезарь)";

        public void Execute(IDocument document)
        {
            if (document == null) return;

            char[] buffer = document.Content.ToCharArray();
            for (int i = 0; i < buffer.Length; i++)
            {
                // Сдвигаем каждый символ на единицу вперед по таблице ASCII
                buffer[i] = (char)(buffer[i] + 1);
            }

            document.Content = new string(buffer);
            document.IsModified = true;
            Console.WriteLine($"[{Name}]: Текст зашифрован.");
        }
    }

    // Шаг 7. Реализация плагина добавления водяного знака
    public class WatermarkPlugin : IPlugin
    {
        private readonly string _watermark;
        public string Name => "Модуль водяных знаков";

        public WatermarkPlugin(string watermark)
        {
            _watermark = watermark;
        }

        public Execute(IDocument document)
        {
            if (document == null) return;

            document.Content = $"{document.Content} [Конфиденциально: {_watermark}]";
            document.IsModified = true;
            Console.WriteLine($"[{Name}]: Добавлен водяной знак.");
        }
    }

    // Шаг 8. Главный класс программы с точкой входа
    public class Program
    {
        public static void Main(string[] args)
        {
            // Установка кодировки консоли для корректного отображения символов
            Console.OutputEncoding = Encoding.UTF8;

            Console.WriteLine("=== Инициализация системы обработки документов ===");

            // Создаем экземпляр документа через интерфейсную ссылку
            IDocument doc = new TextDocument("Отчет_01", "Hello world");
            Console.WriteLine($"Создан документ: '{doc.Title}' с текстом: \"{doc.Content}\"");

            // Создаем список валидаторов
            List<IValidator> validators = new List<IValidator>
            {
                new LengthValidator(5) // Минимальная длина текста — 5 символов
            };

            // Проверяем документ перед обработкой
            bool isValid = true;
            foreach (var validator in validators)
            {
                if (!validator.Validate(doc, out string error))
                {
                    Console.WriteLine(error);
                    isValid = false;
                    break;
                }
            }

            if (!isValid)
            {
                Console.WriteLine("Обработка отменена из-за ошибок валидации.");
                return;
            }

            Console.WriteLine("Валидация успешно пройдена.\n");

            // Создаем список плагинов, используя полиморфизм (все реализуют IPlugin)
            List<IPlugin> plugins = new List<IPlugin>
            {
                new EncryptionPlugin(),
                new WatermarkPlugin("Департамент ИБ")
            };

            // Последовательно применяем каждый плагин к документу
            foreach (var plugin in plugins)
            {
                Console.WriteLine($"Запуск плагина: {plugin.Name}...");
                plugin.Execute(doc);
            }

            Console.WriteLine("\n=== Обработка завершена ===");
            Console.WriteLine($"Итоговое состояние документа. Изменен: {doc.IsModified}");
            
            // Сохраняем документ
            doc.Save();
        }
    }
}
```

### Разбор работы программы и ход рассуждений

1. **Проектирование контрактов (`IDocument`, `IValidator`, `IPlugin`)**: Мы не пишем логику внутри интерфейсов (за исключением использования современных возможностей C# по умолчанию, но в архитектурном плане чистые контракты надежнее). Это позволяет создавать любые другие типы документов (например, `BinaryDocument` или `PdfDocument`), не меняя код плагинов и валидаторов.
2. **Полиморфизм в действии**: В методе `Main` списки `validators` и `plugins` объявлены как коллекции интерфейсных типов (`List<IValidator>` и `List<IPlugin>`). Цикл `foreach` вызывает методы `Validate` и `Execute`, не зная точного типа конкретного плагина. Благодаря механизму виртуальных вызовов в .NET, на этапе выполнения вызывается код именно того класса, экземпляр которого находится в текущей итерации.
3. **Выходные параметры (`out string errorMessage`)**: В методе `Validate` используется модификатор `out`, что позволяет вернуть не только булево значение успешности проверки (`true`/`false`), но и текстовое описание ошибки, избегая выброса исключений для штатных ситуаций проверки пользовательского ввода.

### Тестирование на граничных условиях

Для оценки надежности спроектированной системы рассмотрим поведение программы в граничных случаях:

1. **Пустой документ или текст короче минимальной длины**:
   Если инициализировать документ с текстом `"Hi"` (2 символа), валидатор `LengthValidator(5)` вернет `false`, выведет сообщение:
   `Ошибка валидации: длина текста меньше минимальной (2 < 5).`
   и выполнение цепочки плагинов будет заблокировано до их запуска. Это защищает систему от некорректных данных.

2. **Передача `null` в качестве документа**:
   Внутри плагинов и валидаторов предусмотрены защитные проверки (`if (document == null) return;`), предотвращающие возникновение исключения `NullReferenceException`.

### Анализ сложности алгоритмов

- **Временная сложность (Time Complexity)**:
  - Валидация документа: $O(1)$, так как выполняется проверка длины строки.
  - Шифрование текста: $O(N)$, где $N$ — длина строки содержимого документа, так как каждый символ обрабатывается ровно один раз в цикле `for`.

## 5. Полный проект: Система управления плагинами и обработкой документов

### Постановка комплексной задачи

В завершение темы разработаем масштабную модульную систему на языке C#, которая объединяет все изученные концепции: интерфейсы, множественное наследование интерфейсов, явную реализацию конфликтующих членов, абстрактные классы, перегрузку и переопределение методов, а также полиморфную обработку данных в коллекциях.

**Условие:**
Разработать консольное приложение для системы управления плагинами обработки текстовых документов.
1. Создать базовый интерфейс `IPlugin`, содержащий свойства `string Name { get; }` и `string Version { get; }`, а также метод `void Initialize()`.
2. Создать интерфейс `IDocumentProcessor`, содержащий метод `string ProcessDocument(string inputData)`.
3. Создать комплексный интерфейс `IAdvancedPlugin`, который наследует оба интерфейса (`IPlugin` и `IDocumentProcessor`) и добавляет метод `void ExportReport();`.

7. Продемонстрировать работу системы в методе `Main`: зарегистрировать плагин, выполнить полиморфную инициализацию, обработку текста и экспорт отчетов.

#### Полный исходный код проекта

```csharp
using System;
using System.Collections.Generic;

namespace DocumentPluginSystem
{
    // 1. Базовый интерфейс плагина
    public interface IPlugin
    {
        string Name { get; }
        string Version { get; }
        void Initialize();
    }

    // 2. Интерфейс обработки документов
    public interface IDocumentProcessor
    {
        string ProcessDocument(string inputData);
    }

    // 3. Расширенный интерфейс (множественное наследование интерфейсов)
    public interface IAdvancedPlugin : IPlugin, IDocumentProcessor
    {
        void ExportReport();
    }

    // 4. Абстрактный базовый класс плагина, реализующий IPlugin частично
    public abstract class BasePlugin : IPlugin
    {
        protected string pluginName;
        protected string pluginVersion;

        protected BasePlugin(string name, string version)
        {
            pluginName = name;
            pluginVersion = version;
        }

        public string Name
        {
            get { return pluginName; }
        }

        public string Version
        {
            get { return pluginVersion; }
        }

        // Абстрактный метод инициализации, который наследники обязаны переопределить
        public abstract void Initialize();
    }

    // 5. Конкретный плагин TextFormatterPlugin
    public class TextFormatterPlugin : BasePlugin, IAdvancedPlugin
    {
        private bool isInitialized;

        public TextFormatterPlugin(string name, string version) : base(name, version)
        {
            isInitialized = false;
        }

        // Переопределение абстрактного метода из BasePlugin
        public override void Initialize()
        {
            isInitialized = true;
            Console.WriteLine($"[Плагин '{pluginName}'] Инициализация успешна. Версия: {pluginVersion}");
        }

        // Реализация метода обработки документов (из IDocumentProcessor)
        public string ProcessDocument(string inputData)
        {
            if (!isInitialized)
            {
                throw new InvalidOperationException("Плагин не инициализирован перед запуском обработки!");
            }

            if (string.IsNullOrWhiteSpace(inputData))
            {
                return string.Empty;
            }

            Console.WriteLine($"[Плагин '{pluginName}'] Обработка текста...");
            
            // Бизнес-логика: удаление двойных пробелов и перевод текста в верхний регистр
            string cleaned = System.Text.RegularExpressions.Regex.Replace(inputData, @"\s+", " ");
            return cleaned.ToUpperInvariant();
        }

        // Реализация метода экспорта отчета (из IAdvancedPlugin)
        public void ExportReport()
        {
            Console.WriteLine($"[Плагин '{pluginName}'] Отчет об обработке успешно экспортирован в формат JSON.");
        }
    }

    // 6. Менеджер плагинов для пакетного управления
    public class PluginManager
    {
        private List<IAdvancedPlugin> plugins = new List<IAdvancedPlugin>();

        public void RegisterPlugin(IAdvancedPlugin plugin)
        {
            if (plugin != null)
            {
                plugins.Add(plugin);
                Console.WriteLine($"Менеджер: Зарегистрирован плагин -> {plugin.Name} (v{plugin.Version})");
            }
        }

        public void RunAll(string sampleText)
        {
            Console.WriteLine("\n--- Запуск пакетной обработки документов ---");
            foreach (var plugin in plugins)
            {
                plugin.Initialize();
                
                Console.WriteLine($"Входные данные : \"{sampleText}\"");
                string result = plugin.ProcessDocument(sampleText);
                Console.WriteLine($"Выходные данные: \"{result}\"");
                
                plugin.ExportReport();
                Console.WriteLine(new string('-', 40));
            }
        }
    }

    // 7. Главный класс приложения
    class Program
    {
        static void Main(string[] args)
        {
            // Настройка кодировки вывода
            Console.OutputEncoding = System.Text.Encoding.UTF8;

            Console.WriteLine("=== СИСТЕМА УПРАВЛЕНИЯ ПЛАГИНАМИ ДОКУМЕНТОВ ===\n");

            // Создаем менеджер плагинов
            PluginManager manager = new PluginManager();

            // Создаем экземпляр конкретного плагина
            IAdvancedPlugin formatter = new TextFormatterPlugin("TextCleaner & Formatter", "2.1.0");

            // Регистрируем плагин в менеджере
            manager.RegisterPlugin(formatter);

            // Исходный текст с лишними пробелами для обработки
            string rawText = "   отчет   по    лабораторной   работе   номер   28   ";

            // Запуск обработки через менеджер
            manager.RunAll(rawText);

            Console.WriteLine("\nРабота программы завершена. Нажмите любую клавишу для выхода...");
            Console.ReadKey();
        }
    }
}
```

- Строки `31–57`: Абстрактный класс `BasePlugin` берет на себя хранение неизменяемых полей названия и версии, избавляя дочерние классы от дублирования кода.

## Типичные ошибки

1. **Попытка создать экземпляр интерфейса через оператор `new`**
   * *Ошибка:* `IPlugin plugin = new IPlugin();`
   * *Почему возникает:* Студент забывает, что интерфейс — это абстрактный контракт без конструктора и памяти под поля.
   * *Как избежать:* Создавать экземпляр конкретного класса, реализующего этот интерфейс (`IPlugin plugin = new TextFormatterPlugin(...);`).

2. **Нарушение порядка наследования (сначала класс, потом интерфейсы)**
   * *Ошибка:* `class MyClass : IMyInterface, BaseClass { }`
   * *Почему возникает:* Незнание синтаксических правил языка C#. В C# разрешено наследовать только от одного базового класса, и он всегда должен стоять на первом месте после двоеточия.
   * *Как избежать:* Писать: `class MyClass : BaseClass, IMyInterface { }`.

3. **Забытая реализация хотя бы одного члена интерфейса**
   * *Ошибка:* Компилятор выдает ошибку CS0535 о том, что класс не реализует член интерфейса.
   * *Почему возникает:* В больших интерфейсах легко пропустить один из методов или свойств.
   * *Как избежать:* Использовать подсказки среды разработки (в Visual Studio / JetBrains Rider сочетание `Ctrl + .` -> *Implement interface*).

4. **Использование ключевого слова `override` без `virtual` в базовом классе**
   * *Ошибка:* Компилятор сообщает, что метод не может быть переопределен, так как он не виртуальный.
   * *Почему возникает:* Путаница между сокрытием членов (`new`) и полиморфным переопределением (`override`).
   * *Как избежать:* Убедиться, что в базовом классе метод помечен как `virtual` (или `abstract`), прежде чем переопределять его в потомке через `override`.

5. **Попытка изменить тип возвращаемого значения при перегрузке методов**
   * *Ошибка:* Два метода отличаются только тем, что один возвращает `int`, а другой `double`, при одинаковых параметрах.
   * *Почему возникает:* Непонимание определения сигнатуры метода (возвращаемый тип не входит в сигнатуру для перегрузки).
   * *Как избежать:* Изменять количество, типы или порядок параметров метода.

6. **Прямой вызов явно реализованного метода интерфейса через объект класса**
   * *Ошибка:* `myObj.Process();` выдает ошибку компиляции CS1061.
   * *Почему возникает:* Явно реализованные члены интерфейса скрыты на уровне класса и недоступны без приведения типов.
   * *Как избежать:* Приводить объект к типу интерфейса перед вызовом (`IProcessor pr = myObj; pr.Process();`).

7. **Изменение сигнатуры переопределенного метода (`override`)**
   * *Ошибка:* Попытка изменить типы параметров в дочернем методе при попытке переопределить родительский виртуальный метод.
   * *Почему возникает:* Студент путает перегрузку (overloading) и переопределение (overriding). `override` требует *абсолютно идентичной* сигнатуры.
   * *Как избежать:* Копировать сигнатуру метода из базового класса без изменений.

## Ответы к задачам

1. Для строки `"Pass1234"` метод возвращает `true`, для строки `"short"` — `false`.
2. Класс `FileDevice` корректно реализует интерфейс `IIoDevice`, обеспечивая вызов методов `Connect()`, `Read()` и `Write()`.
