## 1. Сущность полиморфизма и позднее связывание в C#

### Понятие полиморфизма и его роль в объектно-ориентированном программировании

Термин **полиморфизм** происходит от греческих слов *poly* (много) и *morphē* (форма). В объектно-ориентированном программировании (ООП) полиморфизм означает способность программы использовать единый интерфейс (одинаковый набор имен методов и свойств) для работы с объектами принципиально разных типов.

> **Определение.** Полиморфизм — это свойство системы, позволяющее вызывать методы с одинаковой сигнатурой для объектов разных классов, причем конкретная реализация метода выбирается во время выполнения программы на основе фактического типа объекта.

Чтобы понять ценность этого свойства, представим ситуацию без полиморфизма. Если у нас есть разные виды документов (текстовые файлы, таблицы, графические отчеты), и мы хотим вывести их на печать, нам пришлось бы писать отдельные методы для каждого типа данных: `PrintText(TextDocument doc)`, `PrintTable(TableDocument doc)` и так далее. Если в системе появится сотый тип документа, придется переписывать весь код, управляющий печатью. 

С полиморфизмом код выглядит иначе: мы обращаемся к любому объекту через общий базовый тип `Document` и вызываем метод `Print()`. Программа сама «знает», какой именно код выполнить для каждого конкретного объекта.

### Статический и динамический полиморфизм: раннее и позднее связывание

В C# полиморфизм реализуется в двух формах: статический и динамический.

1. **Статический полиморфизм (раннее связывание, compile-time polymorphism)**. Связывание вызова метода с его конкретной реализацией происходит во время компиляции. Примером статического полиморфизма являются перегрузка методов (`overloading`) и перегрузка операторов. Компилятор по сигнатуре метода (типам и количеству аргументов) точно знает, какую именно версию нужно вызвать.
2. **Динамический полиморфизм (позднее связывание, run-time polymorphism)**. Связывание вызова метода с его реализацией происходит в момент выполнения программы (в рантайме). Именно этот вид полиморфизма обеспечивается за счет наследования, виртуальных методов и ключевых слов `virtual` и `override`.

Для реализации динамического полиморфизма необходимы три условия:
- Иерархия классов, связанных отношениями наследования.
- Наличие в базовом классе виртуального метода (`virtual`).
- Переопределение этого метода в производном классе (`override`).

### Совместимость типов и полиморфные переменные

Прежде чем разбирать механизмы выбора методов, вспомним правило подстановки (принцип Барбары Лисков): объект производного класса может быть использован везде, где ожидается объект базового класса.

В C# ссылочная переменная базового класса способна хранить ссылку на объект любого производного класса. Рассмотрим это правило на примере:

```csharp
class BaseClass
{
    public void Show() => Console.WriteLine("Базовый класс");
}

class DerivedClass : BaseClass
{
    // Производный класс
}

// В коде программы:
BaseClass obj = new DerivedClass(); // Корректное присваивание
```

Здесь переменная `obj` объявлена как `BaseClass`, но ссылается на экземпляр `DerivedClass`. Однако тип самой переменной (`BaseClass`) определяет, какие члены класса будут доступны для вызова на этапе компиляции.

### Проблема сокрытия членов класса (`new`) вместо переопределения

Что произойдет, если и в базовом, и в производном классе объявить методы с одинаковым именем и сигнатурой, но без использования ключевых слов `virtual` и `override`? По умолчанию компилятор выдаст предупреждение, что метод скрывает член базового класса, и предложит использовать ключевое слово `new`.

Рассмотрим принципиальную разницу между сокрытием (`new`) и переопределением (`override`).

Пусть у нас есть базовый класс `Document` и производный от него класс `Report`.

```csharp
using System;

class Document
{
    public void Info()
    {
        Console.WriteLine("Это стандартный документ.");
    }
}

class Report : Document
{
    // Сокрытие метода базового класса с помощью ключевого слова new
    public new void Info()
    {
        Console.WriteLine("Это аналитический отчет.");
    }
}
```

Выполним следующий код:

```csharp
class Program
{
    static void Main()
    {
        Document doc1 = new Document();
        doc1.Info(); // Выведет: "Это стандартный документ."

        Report rep1 = new Report();
        rep1.Info(); // Выведет: "Это аналитический отчет."

        // Самый важный случай: полиморфная переменная
        Document doc2 = new Report();
        doc2.Info(); // Выведет: "Это стандартный документ." (!)
    }
}
```

Обратите внимание на последнюю строку. Несмотря на то, что в памяти создан объект `Report`, переменная `doc2` имеет тип `Document`. Поскольку метод `Info()` в базовом классе не был помечен как виртуальный (`virtual`), а в производном был скрыт через `new`, компилятор выполнил **раннее связывание**. Компилятор посмотрел исключительно на тип переменной (`Document`) и вызвал метод из базового класса. Позднее связывание в данном случае не сработало, и полиморфизм оказался «сломан».

### Механизм работы: Таблица виртуальных методов (`vtable`)

Чтобы понять, как C# добивается динамического полиморфизма, обратимся к внутреннему устройству среды .NET и CLR (Common Language Runtime).

Когда класс содержит хотя бы один виртуальный метод (`virtual`), компилятор и среда выполнения создают для этого класса скрытую структуру данных, называемую **таблицей виртуальных методов** (в англоязычной литературе — `vtable` или `virtual method table`).

1. Каждый класс имеет свою `vtable`, которая располагается в памяти в области метаданных типов.
2. Внутри `vtable` хранятся указатели на реальные инструкции методов, которые должен выполнять этот класс.
3. Каждый создаваемый объект в куче (heap) содержит скрытый системный указатель (так называемый `sync block index` и указатель на класс — `MethodTable pointer`), который ведет на `vtable` своего конкретного типа.

Когда в коде происходит вызов виртуального метода через переменную базового класса (например, `doc2.Info()`):
1. Компилятор видит, что метод виртуальный, и генерирует инструкцию позднего связывания (в IL-коде это инструкция `callvirt`).
2. Во время выполнения программы (в рантайме) CLR не смотрит на тип переменной (`Document`). Вместо этого среда заглядывает внутрь объекта, на который ссылается переменная (находит объект `Report` в памяти), переходит по его указателю на `vtable` класса `Report`.
3. В таблице `vtable` класса `Report` находится актуальный адрес переопределенного метода `Info()`, который и передается на выполнение процессору.

Этот механизм работает за доли наносекунд, обеспечивая гибкость объектно-ориентированных программ без существенных потерь производительности.

### Роль полиморфизма в уменьшении связности кода

Главное архитектурное назначение полиморфизма — **уменьшение связности кода** (coupling) и **повышение расширяемости** (extensibility). 

Связность определяет степень зависимости между различными модулями программы. Высокая связность означает, что изменение в одном классе повлечет каскад изменений в других классах. Полиморфизм разрывает эту жесткую связь. Модуль верхнего уровня (например, менеджер печати или графический редактор) работает с абстрактным типом (`Document` или `Shape`), ничего не зная о конкретных подклассах. 

Благодаря этому соблюдается принцип открытости/закрытости (Open/Closed Principle из SOLID): программные сущности должны быть открыты для расширения, но закрыты для модификации. Мы можем добавлять в систему новые типы документов, отчетов или фигур, вообще не изменяя уже написанный и протестированный управляющий код.

### Разобранный пример: Сравнение `new` и `virtual/override` на примере документов

Рассмотрим полную, компилируемую программу на C#, которая наглядно демонстрирует разницу между сокрытием членов (`new`) и правильным полиморфным переопределением (`virtual`/`override`).

#### Условие задачи
Требуется спроектировать иерархию документов. Базовый класс должен содержать метод `DisplayMetadata()`, выводящий общую информацию, и виртуальный метод `RenderContent()`, выводящий содержимое документа. Производный класс `FinancialReport` должен переопределить оба метода: один через сокрытие (`new`), второй — через полиморфное переопределение (`override`). Продемонстрировать вызов этих методов через коллекцию базового типа.

#### Рисунок схемы связей (в текстовом виде)
```
+-----------------------------------+
|          class Document           |
|-----------------------------------|
|  DisplayMetadata() [обычный]      |
|  RenderContent()   [virtual]      |
+-----------------------------------+
                  ^
                  | наследуется
+-----------------------------------+
|      class FinancialReport        |
|-----------------------------------|
|  DisplayMetadata() [new]          |
|  RenderContent()   [override]     |
+-----------------------------------+
```

#### Ход рассуждений
1. Создаем базовый класс `Document`. Метод `DisplayMetadata` объявляем обычным образом, а метод `RenderContent` снабжаем ключевым словом `virtual`, разрешая наследникам изменять его поведение полиморфно.
2. Создаем производный класс `FinancialReport`. Для метода `DisplayMetadata` используем модификатор `new`, демонстрируя статическое сокрытие. Для метода `RenderContent` используем модификатор `override`, реализуя динамическое позднее связывание.
3. В методе `Main` создаем массив (или список) типа `Document`, в который поместим как базовый документ, так и финансовый отчет, приведенный к типу `Document`.
4. В цикле вызываем оба метода для каждого элемента массива и наблюдаем разницу в поведении.

#### Полный исходный код программы

```csharp
using System;

// Базовый класс документов
class Document
{
    // Обычный метод базового класса
    public void DisplayMetadata()
    {
        Console.WriteLine("[Метаданные] Общий тип документа: Неизвестный документ.");
    }

    // Виртуальный метод, разрешающий полиморфное переопределение
    public virtual void RenderContent()
    {
        Console.WriteLine("[Содержимое] Отображение базового пустого листа.");
    }
}

// Производный класс финансового отчета
class FinancialReport : Document
{
    // Сокрытие метода базового класса с помощью ключевого слова new
    public new void DisplayMetadata()
    {
        Console.WriteLine("[Метаданные] Финансовый отчёт за текущий квартал (Строго конфиденциально).");
    }

    // Полиморфное переопределение метода с помощью ключевого слова override
    public override void RenderContent()
    {
        Console.WriteLine("[Содержимое] Рендеринг таблиц баланса, графиков прибыли и налоговых вычетов.");
    }
}

class Program
{
    static void Main(string[] args)
    {
        Console.WriteLine("--- Прямое создание объектов ---");
        Document baseDoc = new Document();
        baseDoc.DisplayMetadata();
        baseDoc.RenderContent();

        Console.WriteLine();

        FinancialReport report = new FinancialReport();
        report.DisplayMetadata();
        report.RenderContent();

        Console.WriteLine("\n--- Работа через полиморфные ссылки (тип Document) ---");
        
        // Массив базового типа содержит разные объекты иерархии
        Document[] documents = new Document[]
        {
            new Document(),
            new FinancialReport() // Восходящее преобразование (upcasting)
        };

        foreach (Document doc in documents)
        {
            Console.WriteLine($"\nТекущий объект в памяти: {doc.GetType().Name}");
            
            // Вызов обычного метода (срабатывает раннее связывание по типу переменной Document)
            doc.DisplayMetadata();
            
            // Вызов виртуального метода (срабатывает позднее связывание через vtable)
            doc.RenderContent();
        }
    }
}
```

#### Проверка и анализ результатов
1. **Проверка единиц и типов:** Код компилируется без ошибок и предупреждений (при условии корректного применения модификаторов `new` и `override`).
2. **Правдоподобие:** Для элемента массива со ссылкой на `FinancialReport` метод `DisplayMetadata()` вывел версию базового класса (`[Метаданные] Общий тип документа...`), потому что он был скрыт через `new`, и сработал статический тип переменной (`Document`). В то же время метод `RenderContent()` вывел специфическую версию подкласса (`[Содержимое] Рендеринг таблиц...`), потому что благодаря связке `virtual`/`override` сработал динамический полиморфизм и таблица виртуальных методов (`vtable`). Это доказывает разницу между сокрытием и переопределением.

Ответ: концепция динамического полиморфизма успешно продемонстрирована, различия между ранним и поздним связыванием подтверждены на практике.

## 2. Виртуальные и переопределенные методы: virtual и override

### Назначение модификатора `virtual` в базовом классе

Когда мы проектируем иерархию классов через наследование, производный класс автоматически получает все члены базового класса (поля, свойства, методы). По умолчанию в C# все методы ведут себя статически: если в базовом классе объявлен метод, а в производном создан метод с тем же именем, то выбор вызываемого метода зависит исключительно от *компилятора* и статического (объявленного) типа переменной, а не от того, какой именно объект находится в памяти в момент выполнения программы.

Чтобы разрешить производным классам изменять поведение метода и включить механизм динамического (позднего) связывания, в базовом классе используется модификатор `virtual` (виртуальный).

> **Определение.** Виртуальный метод — это метод базового класса, реализацию которого можно переопределить (изменить) в производных классах. Модификатор `virtual` явно говорит компилятору: «Этот метод может получить новую реализацию ниже по иерархии, поэтому при вызове через ссылку на базовый класс проверяй реальный тип объекта в памяти».

Рассмотрим синтаксис объявления виртуального метода:

```csharp
public class Document
{
    public string Title { get; set; }

    public virtual void Open()
    {
        Console.WriteLine("Открытие стандартного документа...");
    }
}
```

Модификатор `virtual` можно применять к методам, свойствам и индексаторам. Его нельзя применять к статическим (`static`) членам класса, так как статические члены принадлежат самому классу, а не конкретным экземплярам, и полиморфизм для них не применим.

### Использование ключевого слова `override` в производном классе

Если базовый класс предоставил виртуальный метод, производный класс может (но не обязан) предоставить его собственную версию. Для этого используется ключевое слово `override` (переопределение).

> **Определение.** Переопределение метода — это механизм создания новой реализации виртуального метода в производном классе с сохранением той же сигнатуры. Ключевое слово `override` сообщает компилятору, что мы осознанно заменяем поведение родительского метода.

Пример создания производного класса с переопределением:

```csharp
public class PdfDocument : Document
{
    public override void Open()
    {
        Console.WriteLine("Инициализация графического движка PDF...");
        Console.WriteLine("Открытие PDF-документа с поддержкой масштабирования.");
    }
}
```

Ключевое слово `override` требует наличия в базовом классе виртуального, абстрактного или уже переопределенного метода с точно такой же сигнатурой. Если попытаться применить `override` к обычному неуправляемому методу, компилятор выдаст ошибку.

---

### Правила сигнатур: почему переопределяемый метод должен иметь ту же сигнатуру

Сигнатура метода в C# включает в себя имя метода, а также количество, порядок и типы его параметров. Тип возвращаемого значения строго входит в сигнатуру переопределения (хотя в некоторых случаях допускается ковариантность возвращаемых типов — возвращение более узкого типа в производном классе, но на базовом уровне мы ориентируемся на полное совпадение).

Переопределенный метод в производном классе обязан полностью совпадать по сигнатуре с виртуальным методом в базовом классе:
1. Имя метода должно быть идентичным.
2. Набор параметров (типы и порядок) должен совпадать байт-в-байт.
3. Модификаторы доступа (`public`, `protected`) должны соответствовать базовому методу (нельзя сделать виртуальный `public` метод приватным при переопределении).

Если изменить тип параметра в производном классе (например, вместо `int` передать `double`), компилятор не сочтет это переопределением (`override`). Вместо этого он воспримет такой метод как **сокрытие** родительского метода (если явно не указано ключевое слово `new`), что приведет к разрыву полиморфной цепочки: при вызове метода через ссылку на базовый класс выполнится старая версия из родителя, а не новая из потомка.

---

### Запрет дальнейшего переопределения: модификатор `sealed` для методов

Иногда архитектура приложения требует, чтобы определенный метод больше не мог изменяться в классах, лежащих ниже по иерархии. Если класс `PdfDocument` является базовым для класса `EncryptedPdfDocument`, но мы хотим зафиксировать логику метода `Open()`, мы можем применить модификатор `sealed` (запечатанный) совместно с `override`.

> **Определение.** Запечатанный метод (`sealed override`) — это переопределенный метод, который запрещает всем последующим производным классам переопределять его заново.

Пример использования:

```csharp
public class EncryptedPdfDocument : PdfDocument
{
    public sealed override void Open()
    {
        Console.WriteLine("Ввод пароля дешифрования...");
        base.Open(); // Вызов логики родительского класса
    }
}
```

Если мы попытаемся создать класс-потомок от `EncryptedPdfDocument` и переопределить метод `Open()`, компилятор заблокирует сборку проекта. Это полезно для обеспечения безопасности и стабильности критически важных алгоритмов.

---

### Доступ к реализации родительского метода через ключевое слово `base`

Когда мы переопределяем метод в производном классе, новая версия полностью заменяет старую. Однако на практике часто возникает ситуация, когда дочерний метод должен не полностью переписать родительский алгоритм, а дополнить его. 

Для вызова оригинальной реализации метода из базового класса используется ключевое слово `base`.

```csharp
public class Employee
{
    public string FullName { get; set; }
    public decimal BaseSalary { get; set; }

    public virtual decimal CalculateBonus()
    {
        // Базовая премия: 10% от оклада
        return BaseSalary * 0{:}1m;
    }
}

public class Manager : Employee
{
    public int SubordinatesCount { get; set; }

    public override decimal CalculateBonus()
    {
        // Получаем базовую премию через ключевое слово base
        decimal baseBonus = base.CalculateBonus();
        
        // Добавляем бонус за каждого подчиненного: 1000 рублей за человека
        decimal managementBonus = SubordinatesCount * 1000{:}0m;

        return baseBonus + managementBonus;
    }
}
```

Здесь вызов `base.CalculateBonus()` выполняет расчет в классе `Employee`, возвращая числовое значение, к которому затем прибавляется надбавка менеджера. Это избавляет от дублирования кода.

---

### Особенности работы конструкторов при вызове виртуальных методов

Существует важное архитектурное правило в C# и других объектно-ориентированных языках: **никогда не вызывайте виртуальные методы из конструкторов**.

Когда создается экземпляр производного класса (например, `Manager`), порядок выполнения следующий:
1. Выделяется память под объект.
2. Вызывается конструктор базового класса (`Employee`).
3. Выполняется тело конструктора базового класса.
4. Вызывается конструктор производного класса (`Manager`).
5. Выполняется тело конструктора производного класса.

Если внутри конструктора базового класса (`Employee`) есть вызов виртуального метода (`CalculateBonus()`), то в момент выполнения этого вызова конструктор производного класса еще **не завершил** свою работу (поля производного класса еще не инициализированы). Тем не менее, механизм динамического связывания сработает, и вызов уйдет в переопределенный метод производного класса. Это приведет к тому, что метод дочернего класса будет оперировать еще не проинициализированными данными, что вызовет трудноуловимые ошибки и баги.

### Разобранный пример 1: Иерархия графических фигур `Shape`

#### Условие задачи
Требуется разработать иерархию классов для работы с графическими фигурами. Базовый класс `Shape` должен содержать виртуальный метод `Draw()`, выводящий информацию о рисовании общей фигуры, а также виртуальный метод `CalculateArea()` для расчета площади. Производные классы `Circle` (круг) и `Rectangle` (прямоугольник) должны переопределить оба метода с учетом специфики геометрических фигур. Написать исполняемую программу, которая демонстрирует полиморфный вызов методов через массив базового типа.

#### Рисунок (схема классов) словами
```
       +-----------------------+
       |     class Shape       |
       |-----------------------|
       | - Color: string       |
       | + Draw() [virtual]    |
       | + CalculateArea()     |
       +-----------------------+
            /             \
           /               \
          v                 v
+------------------+ +------------------+
|  class Circle    | | class Rectangle  |
|------------------| |------------------|
| - Radius: double | | - Width: double  |
|                  | | - Height: double |
| + Draw() [ovrd]  | | + Draw() [ovrd]  |
| + CalcArea() [o] | | + CalcArea() [o] |
+------------------+ +------------------+
```

#### Ход рассуждений
1. Создаем базовый класс `Shape` со свойством цвета фигуры и общим виртуальным методом `Draw()`.
2. В классе `Shape` метод `CalculateArea()` также объявим как `virtual`, возвращающий `0`.
3. Создаем класс `Circle`, наследующий `Shape`. Добавляем поле `Radius`. Переопределяем метод `CalculateArea()` по формуле площади круга: $S = \pi r^2$, и метод `Draw()`, выводящий параметры круга.
4. Создаем класс `Rectangle`, наследующий `Shape`. Добавляем поля `Width` и `Height`. Переопределяем метод `CalculateArea()` по формуле площади прямоугольника: $S = w \cdot h$, и метод `Draw()`.
5. В методе `Main` создадим массив типа `Shape[]`, заполним его объектами `Circle` и `Rectangle`, после чего запустим цикл вызова методов `Draw()` и `CalculateArea()` полиморфно.

#### Решение на C#

```csharp
using System;

namespace PolymorphismDemo
{
    // Базовый класс фигуры
    public class Shape
    {
        public string Color { get; set; }

        public Shape(string color)
        {
            Color = color;
        }

        // Виртуальный метод отрисовки
        public virtual void Draw()
        {
            Console.WriteLine($"Рисование абстрактной фигуры цвета: {Color}");
        }

        // Виртуальный метод расчета площади
        public virtual double CalculateArea()
        {
            return 0.0;
        }
    }

    // Производный класс: Круг
    public class Circle : Shape
    {
        public double Radius { get; set; }

        public Circle(string color, double radius) : base(color)
        {
            Radius = radius;
        }

        public override void Draw()
        {
            Console.WriteLine($"Окружность [Цвет: {Color}, Радиус: {Radius:F2} см]");
        }

        public override double CalculateArea()
        {
            // Площадь круга: S = pi * r^2
            return Math.PI * Radius * Radius;
        }
    }

    // Производный класс: Прямоугольник
    public class Rectangle : Shape
    {
        public double Width { get; set; }
        public double Height { get; set; }

        public Rectangle(string color, double width, double height) : base(color)
        {
            Width = width;
            Height = height;
        }

        public override void Draw()
        {
            Console.WriteLine($"Прямоугольник [Цвет: {Color}, Ширина: {Width:F2} см, Высота: {Height:F2} см]");
        }

        public override double CalculateArea()
        {
            // Площадь прямоугольника: S = width * height
            return Width * Height;
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Создаем полиморфный массив базового типа Shape
            Shape[] shapes = new Shape[]
            {
                new Circle("Красный", 5.0),
                new Rectangle("Синий", 4.0, 6.0),
                new Circle("Зеленый", 2.5)
            };

            // Обрабатываем коллекцию в цикле
            foreach (Shape shape in shapes)
            {
                shape.Draw();
                double area = shape.CalculateArea();
                Console.WriteLine($"Вычисленная площадь: {area:F2} кв. см\n");
            }
        }
    }
}
```

#### Пример ввода и вывода
*Ввод:* Данные заданы жестко в коде (массив объектов `Circle` и `Rectangle`).

*Вывод программы:*
```text
Окружность [Цвет: Красный, Радиус: 5,00 см]
Вычисленная площадь: 78,54 кв. см

Прямоугольник [Цвет: Синий, Ширина: 4,00 см, Высота: 6,00 см]
Вычисленная площадь: 24,00 кв. см

Окружность [Цвет: Зеленый, Радиус: 2,50 см]
Вычисленная площадь: 19,63 кв. см
```

#### Проверка и оценка сложности
- **Проверка единиц:** линейные размеры в сантиметрах, площади в квадратных сантиметрах. Значения рассчитаны верно ($\pi \cdot 5^2 \approx 78{,}5398$, $4 \cdot 6 = 24$, $\pi \cdot 2{,}5^2 \approx 19{,}6349$).
- **Оценка сложности:** Временная сложность обхода массива из $N$ элементов составляет $O(N)$. Пространственная сложность для хранения массива ссылок — $O(N)$.

### Разобранный пример 2: Расчет премии сотрудников с использованием `base`

#### Условие задачи
Разработать иерархию классов для учета сотрудников компании. Базовый класс `Employee` содержит ФИО, базовый оклад и виртуальный метод расчета общей компенсации `CalculateTotalCompensation()`. Производный класс `SalesPerson` (продавец) добавляет объем продаж и процент комиссионных. Метод расчета компенсации в классе `SalesPerson` должен вызывать базовую логику через `base`, добавляя к базовой зарплате комиссионные с продаж.

#### Ход рассуждений
1. Создаем класс `Employee` с полями `FullName` (строка) и `BaseSalary` (децимал). Описываем виртуальный метод `CalculateTotalCompensation()`, возвращающий `BaseSalary`.
2. Создаем класс `SalesPerson`, наследующий `Employee`. Добавляем уникальные поля: `SalesVolume` (объем продаж в рублях) и `CommissionRate` (процент комиссии, например, 0,05 для 5%).
3. Переопределяем метод `CalculateTotalCompensation()`. Внутри метода вызываем `base.CalculateTotalCompensation()`, чтобы получить базовый оклад, и прибавляем к нему произведение объема продаж на процент комиссии: $\text{Total} = \text{BaseSalary} + (\text{SalesVolume} \cdot \text{CommissionRate})$.

#### Решение на C#

```csharp
using System;

namespace EmployeeBonusDemo
{
    public class Employee
    {
        public string FullName { get; set; }
        public decimal BaseSalary { get; set; }

        public Employee(string fullName, decimal baseSalary)
        {
            FullName = fullName;
            BaseSalary = baseSalary;
        }

        // Виртуальный метод расчета компенсации
        public virtual decimal CalculateTotalCompensation()
        {
            return BaseSalary;
        }
    }

    public class SalesPerson : Employee
    {
        public decimal SalesVolume { get; set; }
        public decimal CommissionRate { get; set; }

        public SalesPerson(string fullName, decimal baseSalary, decimal salesVolume, decimal commissionRate)
            : base(fullName, baseSalary)
        {
            SalesVolume = salesVolume;
            CommissionRate = commissionRate;
        }

        // Переопределение метода с вызовом базовой логики
        public override decimal CalculateTotalCompensation()
        {
            decimal baseComp = base.CalculateTotalCompensation();
            decimal commission = SalesVolume * CommissionRate;
            
            return baseComp + commission;
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            Employee[] staff = new Employee[]
            {
                new Employee("Иванов И.И.", 50000.0m),
                new SalesPerson("Петров П.П.", 40000.0m, 500000.0m, 0.07m),
                new SalesPerson("Сидорова С.С.", 45000.0m, 800000.0m, 0.06m)
            };

            foreach (Employee emp in staff)
            {
                decimal total = emp.CalculateTotalCompensation();
                Console.WriteLine($"Сотрудник: {emp.FullName}, Итоговая выплата: {total:N2} руб.");
            }
        }
    }
}
```

#### Пример ввода и вывода
*Ввод:* Данные жестко закодированы в массиве сотрудников.

*Вывод программы:*
```text
Сотрудник: Иванов И.И., Итоговая выплата: 50 000,00 руб.
Сотрудник: Петров П.П., Итоговая выплата: 75 000,00 руб.
Сотрудник: Сидорова С.С., Итоговая выплата: 93 000,00 руб.
```
*(Проверка расчетов для Петрова: $40000 + (500000 \cdot 0{,}07) = 40000 + 35000 = 75000$. Для Сидоровой: $45000 + (800000 \cdot 0{,}06) = 45000 + 48000 = 93000$. Все вычисления верны).*

Ответ: Рассмотренные механизмы `virtual`, `override`, `sealed` и `base` составляют фундамент динамического полиморфизма в C#, позволяя строить расширяемые программные системы без изменения существующего кода базовых модулей.

## 3. Абстрактные классы и абстрактные методы

### Сущность и назначение абстрактных классов

В процессе проектирования сложных иерархий классов часто возникает ситуация, когда базовый класс создается исключительно для того, чтобы объединить общую логику и задать единый интерфейс (набор правил) для всех производных классов. При этом сам по себе базовый класс является слишком общим понятием, и создавать его конкретные экземпляры не имеет никакого смысла.

> **Определение.** Абстрактный класс — это специальный класс, помеченный ключевым словом `abstract`, который служит неполным шаблоном для производных классов и не позволяет создавать свои экземпляры с помощью операции `new`.

Рассмотрим это на концептуальном уровне. Если у нас есть иерархия «Животное», то понятия «Просто Животное» в природе не существует — всегда есть конкретный представитель: собака, кошка или птица. Попытка создать объект базового типа `Animal animal = new Animal();` не имеет практического смысла и должна быть запрещена на уровне компилятора. Абстрактный класс как раз и реализует этот запрет.

Для объявления абстрактного класса используется ключевое слово `abstract` перед ключевым словом `class`:

```csharp
public abstract class Animal
{
    // Члены класса
}
```

Если вы попытаетесь написать в коде программы инструкцию:

```csharp
Animal myAnimal = new Animal(); // Ошибка компиляции!
```

Компилятор выдаст ошибку: *«Не удается создать экземпляр абстрактного типа или интерфейса»*. Абстрактные классы предназначены исключительно для наследования.

---

### Абстрактные методы и правила их переопределения

Абстрактный класс может содержать не только обычные поля, свойства, конструкторы и методы с готовой реализацией, но и специальные — **абстрактные методы**.

> **Определение.** Абстрактный метод — это метод, объявленный с ключевым словом `abstract` внутри абстрактного класса, который **не имеет тела** (реализации) и обязательно должен быть переопределен в неабстрактных производных классах.

Синтаксис объявления абстрактного метода:

```csharp
public abstract void MakeSound();
```

Обратите внимание на следующие жесткие правила компилятора C#:
1. Абстрактный метод **не может** иметь тела (фигурные скобки `{}` заменяются точкой с запятой `;`).
2. Абстрактный метод **можно объявить только внутри абстрактного класса**. Если обычный класс попытается содержать абстрактный метод, компилятор выдаст ошибку.
3. Любой неабстрактный класс, который наследуется от абстрактного класса, **обязан** предоставить реализацию (переопределить через `override`) для всех унаследованных абстрактных методов. Если программист забудет это сделать, программа не скомпилируется.

Зачем это нужно? Абстрактный метод задает жесткий контракт: базовый класс говорит: *«Я не знаю, как именно должен выполняться этот расчет или действие, но я требую, чтобы каждый мой потомок обязательно написал собственную версию этого метода»*.

---

### Устройство абстрактного класса: поля, свойства, конструкторы

Многие начинающие разработчики ошибочно полагают, что абстрактный класс похож на пустой интерфейс и может содержать только сигнатуры методов. Это не так. Абстрактный класс является полноценным классом и может содержать:
- Обычные поля (переменные состояния).
- Свойства с логикой или автосвойства.
- Конструкторы (которые вызываются через ключевое слово `base` из конструкторов производных классов).
- Обычные методы с готовым телом, которые наследуются и используются потомками без изменений.

Конструктор абстрактного класса не может быть вызван напрямую через `new`, однако он выполняется при создании объекта производного класса для инициализации общих полей.

Сравним абстрактный класс и виртуальный метод с реализацией по умолчанию:
- **Виртуальный метод (`virtual`)** в базовом классе имеет стандартную реализацию. Потомок *может* её переопределить, но *не обязан*.
- **Абстрактный метод (`abstract`)** в базовом классе *не имеет* реализации. Потомок *обязан* предоставить свою реализацию.

### Полный разобранный пример 1: Банковские счета

Рассмотрим проектирование иерархии банковских счетов. У нас есть общий концепт «Банковский счет», но специфика начисления процентов различается для сберегательных и кредитных счетов.

#### Условие задачи
Требуется спроектировать иерархию классов для работы с банковскими счетами:
1. Создать абстрактный базовый класс `Account`. Он должен содержать:
   - защищенное поле `owner` (владелец, строка);
   - защищенное поле `balance` (баланс, число с плавающей точкой `decimal`);
   - конструктор для инициализации владельца и начального баланса;
   - виртуальный метод `Deposit(decimal amount)` для пополнения счета;
   - абстрактный метод `CalculateInterest()` для расчета и начисления процентов (возвращает `decimal`).
2. Создать производный класс `SavingsAccount` (сберегательный счет):
   - проценты начисляются в размере $5\%$ от текущего положительного баланса.
3. Создать производный класс `CreditAccount` (кредитный счет):
   - если баланс отрицательный (долг), начисляется штраф в размере $10\%$ от суммы долга (возвращаемое значение будет отрицательным или уменьшающим баланс числом, либо фиксированный расчет процентов на задолженность). Для простоты примем, что штраф за задолженность рассчитывается как $-0{,}10 \times \text{баланс}$, если баланс $< 0$, иначе $0$.
4. Написать консольную программу на C#, которая создает массив счетов обоих типов, выполняет полиморфный расчет процентов и выводит результат в консоль.

#### Рисунок схемы классов (в виде ASCII-диаграммы)

```
+---------------------------------------------------+
|                   abstract Account                |
+---------------------------------------------------+
| # owner: string                                   |
| # balance: decimal                                |
+---------------------------------------------------+
| + Account(string owner, decimal initialBalance)   |
| + virtual void Deposit(decimal amount)            |
| + abstract decimal CalculateInterest()            |
+---------------------------------------------------+
                         ▲
                         │ (наследование)
         ┌───────────────┴───────────────┐
         │                               │
+------------------------+      +------------------------+
|     SavingsAccount     |      |     CreditAccount      |
+------------------------+      +------------------------+
| + SavingsAccount(...)  |      | + CreditAccount(...)   |
| + override decimal     |      | + override decimal     |
|   CalculateInterest()  |      |   CalculateInterest()  |
+------------------------+      +------------------------+
```

#### Ход рассуждений
1. Класс `Account` объявляется как `public abstract class Account`, так как самостоятельного счета без конкретного типа не существует.
2. Поля `owner` и `balance` объявляются с модификатором `protected`, чтобы производные классы имели к ним прямой доступ, а внешний код взаимодействовал через методы и свойства (инкапсуляция).
3. Метод `Deposit` делает стандартное действие (увеличивает `balance`), поэтому он реализован прямо в базовом классе и помечен как `virtual` на случай, если какой-то счет захочет изменить логику пополнения (например, брать комиссию).
4. Метод `CalculateInterest()` не может быть реализован в общем виде, так как формула для сберегательного и кредитного счета кардинально отличается. Мы делаем его `public abstract decimal CalculateInterest()`.
5. Класс `SavingsAccount` наследуется от `Account` (`public class SavingsAccount : Account`). Он обязан реализовать `CalculateInterest()`. Формула: $\text{balance} \times 0{,}05$.
6. Класс `CreditAccount` также наследуется от `Account` и реализует свой расчет: если $\text{balance} < 0$, то $\text{balance} \times 0{,}10$ (проценты по кредиту), иначе $0$.

#### Решение на языке C# (полный компилируемый код)

```csharp
using System;

namespace AbstractClassesDemo
{
    // Абстрактный базовый класс
    public abstract class Account
    {
        protected string owner;
        protected decimal balance;

        // Конструктор базового класса
        public Account(string owner, decimal initialBalance)
        {
            this.owner = owner;
            this.balance = initialBalance;
        }

        // Свойство для получения баланса (только чтение снаружи)
        public decimal Balance
        {
            get { return balance; }
        }

        // Свойство для владельца
        public string Owner
        {
            get { return owner; }
        }

        // Виртуальный метод пополнения счета
        public virtual void Deposit(decimal amount)
        {
            if (amount > 0)
            {
                balance += amount;
                Console.WriteLine($"Счет пользователя {owner} пополнен на {amount:C}. Баланс: {balance:C}");
            }
        }

        // Абстрактный метод расчета процентов (реализуется в потомках)
        public abstract decimal CalculateInterest();
    }

    // Сберегательный счет
    public class SavingsAccount : Account
    {
        public SavingsAccount(string owner, decimal initialBalance) 
            : base(owner, initialBalance)
        {
        }

        // Обязательная реализация абстрактного метода
        public override decimal CalculateInterest()
        {
            // Начисление 5% годовых на положительный баланс
            if (balance > 0)
            {
                return balance * 0.05m;
            }
            return 0m;
        }
    }

    // Кредитный счет
    public class CreditAccount : Account
    {
        public CreditAccount(string owner, decimal initialBalance) 
            : base(owner, initialBalance)
        {
        }

        // Обязательная реализация абстрактного метода
        public override decimal CalculateInterest()
        {
            // Если баланс отрицательный, начисляем 10% комиссии за задолженность
            if (balance < 0)
            {
                return balance * 0.10m; // результат будет отрицательным
            }
            return 0m;
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Создание массива полиморфных ссылок базового класса
            Account[] accounts = new Account[]
            {
                new SavingsAccount("Иван Петров", 10000.00m),
                new CreditAccount("Анна Смирнова", -2500.00m),
                new SavingsAccount("Пётр Васильев", 50000.00m)
            };

            Console.WriteLine("=== Расчет процентов по счетам ===");
            
            foreach (Account acc in accounts)
            {
                // Позднее связывание: вызывается метод конкретного класса в зависимости от типа объекта
                decimal interest = acc.CalculateInterest();
                
                Console.WriteLine($"Владелец: {acc.Owner}, Баланс: {acc.Balance:C}, Расчет процентов/комиссии: {interest:C}");
            }

            Console.ReadKey();
        }
    }
}
```

#### Проверка и анализ результатов
- **Единицы измерения:** В расчетах используется денежный тип данных `decimal` (суффикс `m`), что исключает погрешности округления, свойственные типу `double`. Проценты выражены в долях единицы ($0{,}05$ для $5\%$, $0{,}10$ для $10\%$).
- **Правдоподобность:** Для Ивана Петрова с балансом $10\,000{,}00$ руб. метод вернет $500{,}00$ руб. Для Анны Смирновой с долгом $-2\,500{,}00$ руб. метод вернет $-250{,}00$ руб. Код успешно компилируется и выполняется благодаря обязательному переопределению метода `CalculateInterest()`.

### Полный разобранный пример 2: Игровые юниты

Для закрепления материала рассмотрим вторую задачу из области разработки игр, где полиморфизм и абстрактные классы применяются наиболее часто.

#### Условие задачи
Требуется спроектировать иерархию игровых персонажей (юнитов) для пошаговой стратегии:
1. Создать абстрактный класс `GameUnit`:
   - поле `name` (имя юнита, строка);
   - поле `health` (текущее здоровье, целое число `int`);
   - поле `attackPower` (базовая сила атаки, целое число `int`);
   - конструктор для инициализации полей;
   - абстрактный метод `Attack(GameUnit target)` для нанесения урона другому юниту;
   - виртуальный метод `TakeDamage(int damage)` для получения урона (здоровье уменьшается, но не падает ниже 0);
   - виртуальный метод `IsAlive()` (возвращает `bool`, если здоровье $> 0$).
2. Создать производный класс `Warrior` (Воин):
   - наносит полный урон $\text{attackPower}$, но при атаке расходует выносливость или имеет простой удар.
3. Создать производный класс `Mage` (Маг):
   - наносит усиленный магический урон, равный $\text{attackPower} \times 1{,}5$ (с округлением до целого), но имеет уменьшенный запас здоровья.
4. Написать демонстрационную программу, в которой воин атакует мага, а маг отвечает воину, используя полиморфные вызовы.

#### Ход рассуждений
1. Базовый класс `GameUnit` описывает общее состояние любого персонажа игры (имя, здоровье, сила). Создать объект `new GameUnit(...)` нельзя, так как поведение атаки у всех разное.
2. Метод `TakeDamage` реализован в базовом классе одинаково для всех: $\text{health} = \max(0, \text{health} - \text{damage})$. Это избавляет от дублирования кода в потомках.
3. Метод `Attack(GameUnit target)` объявлен как `abstract`, потому что воин бьет мечом в ближнем бою, а маг кастует заклинание на расстоянии и по-разному рассчитывает урон.
4. Внутри метода `Attack` мы вызываем у цели метод `target.TakeDamage(damage)`, демонстрируя взаимодействие объектов в иерархии.

#### Решение на языке C# (полный компилируемый код)

```csharp
using System;

namespace GameUnitsDemo
{
    // Абстрактный класс игрового юнита
    public abstract class GameUnit
    {
        protected string name;
        protected int health;
        protected int attackPower;

        public GameUnit(string name, int health, int attackPower)
        {
            this.name = name;
            this.health = health;
            this.attackPower = attackPower;
        }

        public string Name
        {
            get { return name; }
        }

        public int Health
        {
            get { return health; }
        }

        // Виртуальный метод получения урона
        public virtual void TakeDamage(int damage)
        {
            health -= damage;
            if (health < 0)
            {
                health = 0;
            }
            Console.WriteLine($"{name} получает {damage} урона. Остаток здоровья: {health}");
        }

        // Виртуальный метод проверки живой ли юнит
        public virtual bool IsAlive()
        {
            return health > 0;
        }

        // Абстрактный метод атаки (реализуется в классах воина и мага)
        public abstract void Attack(GameUnit target);
    }

    // Класс Воин
    public class Warrior : GameUnit
    {
        public Warrior(string name, int health, int attackPower) 
            : base(name, health, attackPower)
        {
        }

        public override void Attack(GameUnit target)
        {
            Console.WriteLine($"Воин {name} совершает мощный удар мечом по {target.Name}!");
            // Воин наносит стандартный физический урон
            target.TakeDamage(attackPower);
        }
    }

    // Класс Маг
    public class Mage : GameUnit
    {
        private int mana;

        public Mage(string name, int health, int attackPower, int mana) 
            : base(name, health, attackPower)
        {
            this.mana = mana;
        }

        public override void Attack(GameUnit target)
        {
            int magicDamage = (int)(attackPower * 1.5);
            Console.WriteLine($"Маг {name} выпускает огненный шар в {target.Name} (Мана: {mana})!");
            // Маг наносит усиленный магический урон
            target.TakeDamage(magicDamage);
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            // Создание конкретных объектов через полиморфные переменные базового класса
            GameUnit warrior = new Warrior("Арагорн", 120, 25);
            GameUnit mage = new Mage("Гэндальф", 80, 20, 100);

            Console.WriteLine($"Начало боя: {warrior.Name} (HP: {warrior.Health}) против {mage.Name} (HP: {mage.Health})");
            Console.WriteLine(new string('-', 50));

            // Раунд 1: Воин атакует мага
            warrior.Attack(mage);
            
            Console.WriteLine();

            // Раунд 2: Маг атакует воина
            mage.Attack(warrior);

            Console.WriteLine(new string('-', 50));
            Console.WriteLine("Итог боя:");
            Console.WriteLine($"{warrior.Name} здоровья: {warrior.Health}, жив: {warrior.IsAlive()}");
            Console.WriteLine($"{mage.Name} здоровья: {mage.Health}, жив: {mage.IsAlive()}");

            Console.ReadKey();
        }
    }
}
```

#### Проверка и анализ результатов
- **Сложность алгоритмов:** Создание и вызов методов имеют сложность $O(1)$, так как выбор метода происходит через таблицу виртуальных методов (vtable) за постоянное время.
- **Правдоподобность:** Воин с силой атаки $25$ наносит магу ровно $25$ урона (здоровье мага падает с $80$ до $55$). Маг с базовой силой $20$ наносит $20 \times 1{,}5 = 30$ урона (здоровье воина падает с $120$ до $90$). Программа полностью отражает принципы полиморфизма: один и тот же метод `Attack()` ведет себя совершенно по-разному в зависимости от того, к какому именно объекту (`Warrior` или `Mage`) он применяется.

## 4. Полиморфные коллекции и операторы is / as

### Хранение объектов разных подклассов в едином коллекционном типе

До сих пор мы рассматривали создание отдельных объектов или массивов однородных элементов. Однако на практике часто возникает задача управления группой объектов, которые имеют общую концептуальную основу (базовый класс или интерфейс), но различаются по своему внутреннему устройству и поведению. В C# ссылочная совместимость типов позволяет помещать экземпляры производных классов в коллекцию, объявленную с типом родительского класса.

> **Определение.** Полиморфная коллекция — это коллекция (массив, список `List<T>`, очередь или другой контейнер), объявленная с типом базового класса или интерфейса, которая во время выполнения программы (runtime) содержит ссылки на объекты различных производных классов.

Рассмотрим этот механизм подробно. Пусть у нас есть базовый класс (или абстрактный класс) `Base`. Если мы создадим список:

```csharp
List<Base> items = new List<Base>();
```

то в этот список мы можем беспрепятственно добавлять объекты типа `DerivedA`, `DerivedB` и `DerivedC`, при условии, что все они наследуют от `Base`. 

Почему это работает? С точки зрения системы типов C#, любая переменная или элемент списка типа `Base` может хранить ссылку на любой объект, который является производным от `Base` (согласно принциму подстановки Лисков). Когда мы обращаемся к элементу списка, компилятор видит его тип как `Base`. Однако благодаря механизму динамического связывания (virtual / override / abstract), вызов виртуальных методов приводит к выполнению кода именно того класса, экземпляр которого фактически находится в памяти в данный момент.

---

### Автоматический выбор реализации метода при обходе коллекции

Главная сила полиморфных коллекций проявляется при их обработке в цикле. Нам не нужно писать громоздкие разветвления вида «если это объект типа А, вызови такой метод, а если типа Б — другой». Мы можем применить единый интерфейс взаимодействия для всех элементов.

Рассмотрим полный разобранный пример.

#### Пример 1. Обработка разнородных документов

**Условие:** Необходимо разработать систему управления документами. Есть абстрактный класс `Document` с виртуальным методом `Print()` и абстрактным свойством `Title`. Требуется создать список документов разного типа (`TextDocument`, `SpreadSheet`, `ImageDocument`), заполнить его тестовыми данными и вывести информацию о каждом документе на экран с помощью единого цикла `foreach`, не зная заранее точный тип конкретного элемента.

**Рисунок словами:**
В памяти компьютера создается динамический массив (список `List<Document>`), содержащий ссылки на три разных объекта в куче (heap):
1. Объект `TextDocument` с заголовком "Отчет" и количеством слов 1500.
2. Объект `SpreadSheet` с заголовком "Бюджет" и размером таблицы 10x12.
3. Объект `ImageDocument` с заголовком "Схема" и разрешением 1920x1080.
Цикл `foreach` последовательно берет ссылки из списка и вызывает метод `Print()`. Для каждого элемента срабатывает своя переопределенная версия метода.

**Ход рассуждений:**
1. Объявляем абстрактный класс `Document`, который задает общую структуру: свойство `Title` и виртуальный (или абстрактный) метод `Print()`.
2. Создаем три производных класса, каждый из которых переопределяет метод `Print()` для вывода специфической информации.
3. В методе `Main` создаем `List<Document>` и добавляем в него экземпляры подклассов. Поскольку все они наследуют от `Document`, компилятор разрешает такое добавление.
4. Запускаем цикл `foreach (Document doc in documents)`. На каждой итерации переменная `doc` ссылается на очередной документ. Вызов `doc.Print()` перенаправляется механизмом виртуальных вызовов (vtable) на реализацию конкретного класса.

**Код программы:**

```csharp
using System;
using System.Collections.Generic;

// Абстрактный базовый класс
public abstract class Document
{
    public string Title { get; set; }

    protected Document(string title)
    {
        Title = title;
    }

    // Виртуальный метод печати информации о документе
    public virtual void Print()
    {
        Console.WriteLine($"Документ: {Title}");
    }
}

// Производный класс: Текстовый документ
public class TextDocument : Document
{
    public int WordCount { get; set; }

    public TextDocument(string title, int wordCount) : base(title)
    {
        WordCount = wordCount;
    }

    public override void Print()
    {
        Console.WriteLine($"[Текстовый документ] Название: \"{Title}\", Слов: {WordCount}");
    }
}

// Производный класс: Электронная таблица
public class SpreadSheet : Document
{
    public int Rows { get; set; }
    public int Columns { get; set; }

    public SpreadSheet(string title, int rows, int columns) : base(title)
    {
        Rows = rows;
        Columns = columns;
    }

    public override void Print()
    {
        Console.WriteLine($"[Таблица] Название: \"{Title}\", Размер: {Rows}x{Columns}");
    }
}

// Производный класс: Графический документ
public class ImageDocument : Document
{
    public string Resolution { get; set; }

    public ImageDocument(string title, string resolution) : base(title)
    {
        Resolution = resolution;
    }

    public override void Print()
    {
        Console.WriteLine($"[Изображение] Название: \"{Title}\", Разрешение: {Resolution}");
    }
}

class Program
{
    static void Main()
    {
        // Создание полиморфной коллекции
        List<Document> docs = new List<Document>
        {
            new TextDocument("Годовой отчет", 2400),
            new SpreadSheet("Финансовый план 2025", 50, 12),
            new ImageDocument("Архитектурная схема", "1920x1080"),
            new TextDocument("Служебная записка", 350)
        };

        Console.WriteLine("Печать содержимого полиморфной коллекции документов:\n");

        // Полиморфный обход коллекции
        foreach (Document doc in docs)
        {
            doc.Print(); // Автоматически вызывается нужная версия метода Print()
        }
    }
}
```

**Пример вывода:**
```text
Печать содержимого полиморфной коллекции документов:

[Текстовый документ] Название: "Годовой отчет", Слов: 2400
[Таблица] Название: "Финансовый план 2025", Размер: 50x12
[Изображение] Название: "Архитектурная схема", Разрешение: 1920x1080
[Текстовый документ] Название: "Служебная записка", Слов: 350
```

**Проверка и анализ:** Код компилируется успешно. Типы строго соблюдены. Вывод соответствует содержимому объектов в памяти. Никаких ручных проверок типов через `if` на данном этапе не потребовалось, что подтверждает элегантность полиморфизма.

### Проверка типов в рантайме: оператор `is`

Хотя полиморфизм позволяет вызывать переопределенные методы без знания точного типа объекта, иногда возникает необходимость выполнить специфическое действие, которое присуще только конкретному производному классу и отсутствует в базовом классе. 

Для определения фактического типа объекта во время выполнения программы (runtime) используется бинарный оператор `is`.

> **Определение.** Оператор `is` проверяет, совместим ли результат вычисления выражения с заданным типом, и возвращает логическое значение `true`, если объект принадлежит этому типу или производному от него, и `false` в противном случае.

Синтаксис проверки:
```csharp
bool result = expression is TargetType;
```

Если переменная хранит `null`, оператор `is` всегда возвращает `false`.

### Безопасное приведение типов: оператор `as`

Когда мы убедились с помощью проверки или логики программы, что объект в базовой переменной имеет конкретный производный тип, нам нужно получить к нему доступ как к этому типу, чтобы вызвать уникальные методы или обратиться к уникальным полям.

Обычное явное приведение типов (кастинг) в стиле C-style:
```csharp
DerivedClass d = (DerivedClass)baseReference;
```
опасно тем, что если реальный объект в памяти не совместим с `DerivedClass`, среда выполнения выбросит исключение `InvalidCastException`, что приведет к аварийному завершению программы.

Для предотвращения этого используется безопасное приведение типов с помощью оператора `as`.

> **Определение.** Оператор `as` пытается выполнить преобразование ссылочного типа к указанному типу. Если преобразование невозможно, оператор не генерирует исключение, а возвращает значение `null`.

Синтаксис безопасного приведения:
```csharp
TargetType variable = expression as TargetType;
if (variable != null)
{
    // Работа с переменной
}
```

### Современный Pattern Matching (сопоставление с образцом) в C#

Начиная с версии C# 7.0 и активно развиваясь в современных версиях .NET (.NET 8), язык предоставляет мощный инструмент — сопоставление с образцом (pattern matching), который объединяет проверку типа (`is`) и присваивание в переменную в единую компактную конструкцию.

Вместо раздельного написания:
```csharp
if (doc is TextDocument)
{
    TextDocument textDoc = (TextDocument)doc;
    Console.WriteLine(textDoc.WordCount);
}
```
современный C# позволяет написать:
```csharp
if (doc is TextDocument textDoc)
{
    // Переменная textDoc уже объявлена, имеет тип TextDocument и доступна внутри блока if
    Console.WriteLine(textDoc.WordCount);
}
```
Это не только сокращает объем кода, но и исключает потенциальные ошибки при ручном приведении.

### Разобранный пример 2: Фильтрация транспорта и вызов специфических методов

**Условие:** Разработать систему учета транспортных средств. Есть базовый класс `Vehicle` со свойствами модели и скорости. От него наследуются три класса: `Car` (с уникальным методом `OpenTrunk()`), `Bicycle` (с уникальным методом `RingBell()`) и `Truck` (с уникальным методом `UnloadCargo()`). Необходимо создать список транспортных средств разного типа, обойти его в цикле, для каждого объекта вывести общие характеристики, а также с помощью оператора `is`, оператора `as` и современного pattern matching вызвать специфические методы каждого подкласса.

**Рисунок словами:**
В памяти находится список `List<Vehicle>`, содержащий четыре объекта: легковой автомобиль, велосипед, грузовик и еще один легковой автомобиль. При обходе списка программа анализирует каждый элемент:
- Если это `Car`, программа вызывает метод открытия багажника.
- Если это `Bicycle`, программа заставляет его звонить в звонок.
- Если это `Truck`, программа разгружает кузов.

**Ход рассуждений:**
1. Проектируем иерархию классов `Vehicle` -> `Car`, `Bicycle`, `Truck`.
2. Заполняем список разнородными объектами.
3. В цикле `foreach` для каждого элемента выводим общую информацию (полиморфно).
4. Применяем три разных подхода для демонстрации работы с типами:
   - Оператор `is` со старым синтаксисом проверки и приведением.
   - Оператор `as` с проверкой на `null`.
   - Современный pattern matching с объявлением переменной прямо в условии `if` и в конструкции `switch`.

### Анализ производительности и типичные ошибки

При активном использовании полиморфных коллекций, операторов `is`, `as` и сопоставления с образцом важно понимать внутренние механизмы .NET и избегать типичных архитектурных ловушек.

#### 1. Накладные расходы на виртуальные вызовы и упаковку
* **Виртуальные вызовы (vtable):** Вызов метода через таблицу виртуальных методов требует одного дополнительного обращения по указателю в памяти (переход по адресу метода в vtable). В 99,9% приложений эти микросекундные задержки абсолютно незаметны. Однако в критическом высокопроизводительном коде (например, в игровых циклах с миллионами итераций в секунду) избыточный полиморфизм может вызывать падение производительности из-за промахов мимо кэша процессора (cache misses) и невозможности инлайнинга (inlining) методов компилятором JIT.
* **Типы значений и упаковка (Boxing):** Коллекции вроде `List<object>` заставляют упаковывать типы значений (`int`, `struct`) в кучу, что приводит к нагрузке на сборщик мусора (GC). Полиморфные коллекции ссылочных типов (`List<BaseClass>`) хранят указатели и не вызывают упаковки, поэтому они полностью безопасны в этом отношении.

#### 2. Типичные ошибки разработчиков

* **З злоупотребление проверками типов (`is` / `сas`) в циклах:**
  Если в коде постоянно пишется что-то вроде:
  ```csharp
  foreach(var item in collection)
  {
      if (item is TypeA) { ... }
      else if (item is TypeB) { ... }
  }
  ```
  Это явный признак нарушения принципов ООП (в частности, принципа открытости-закрытости OCP). Вместо разветвления логики по типам снаружи, эту логику следует инкапсулировать внутрь виртуального метода базового класса. Полиморфизм создан именно для того, чтобы избавиться от проверок типов в коде. Операторы `is` и `as` следует применять только в крайних случаях (например, при сериализации, написании универсальных библиотек или логировании специфических свойств).

* **Игнорирование проверки результата `as`:**
  ```csharp
  Car c = v as Car;
  c.OpenTrunk(); // Ошибка! Если v — это велосипед, то c будет равен null,
                 // и произойдет NullReferenceException.
  ```
  Всегда проверяйте результат оператора `as` на неравенство `null` перед использованием или используйте pattern matching (`if (v is Car c)`).

* **Потеря специфических данных при восходящем преобразовании (Upcasting):**
  Когда объект производного класса помещается в список базового типа `List<Base>`, компилятор «забывает» о существовании уникальных полей подкласса. Обратиться к ним напрямую через переменную базового типа нельзя без приведения типов. Это не баг, а защитный механизм статической типизации, но начинающие программисты часто путаются, почему метод базового класса доступен, а поле дочернего класса — нет.

```csharp

    }
}
```

## Типичные ошибки

1. **Забыли ключевое слово `virtual` в базовом классе.**
   - *Почему возникает:* Разработчик объявляет метод в базовом классе обычным образом, а в потомке пишет `override`.
   - *Как избежать:* Компилятор выдаст ошибку сборки, сообщая, что метод не имеет подходящего базового метода для переопределения. Всегда явно помечайте метод родителя как `virtual`.
   - *Пример:* `public void Run() {}` в базе и `public override void Run() {}` в потомке вызовут ошибку компиляции.

2. **Использование ключевого слова `new` вместо `override` в надежде на полиморфизм.**
   - *Почему возникает:* Метод скрывается через `new`, и программист ожидает динамического связывания.
   - *Как избежать:* Помнить правило: `new` реализует *статическое сокрытие* (вызывается метод по типу переменной), а `override` — *динамический полиморфизм* (вызывается метод по типу объекта в памяти).
   - *Пример:* `Document doc = new Report(); doc.Info();` выведет метод базового класса, если был использован `new`.

3. **Создание экземпляра абстрактного класса через оператор `new`.**
   - *Почему возникает:* Попытка инициализировать базовый класс напрямую.
   - *Как избежать:* Помнить, что абстрактные классы — это неполные шаблоны контрактов. Создавать можно только объекты неабстрактных производных классов.
   - *Пример:* `Shape s = new Shape("Red");` приведет к ошибке компиляции.

4. **Забыли реализовать абстрактный метод в производном классе.**
   - *Почему возникает:* Наследование от абстрактного класса без переопределения всех его `abstract` членов.
   - *Как избежать:* Компилятор не позволит собрать проект, пока каждый абстрактный метод не будет снабжен ключевым словом `override` и телом в потомке.
   - *Пример:* Наследник абстрактного класса `Account` обязан реализовать метод `CalculateInterest()`.

5. **Вызов виртуальных методов из конструктора базового класса.**
   - *Почему возникает:* Желание инициализировать поля через виртуальный метод в момент создания родителя.
   - *Как избежать:* Не вызывать `virtual` методы из конструкторов, так как объект-потомок еще не закончил инициализацию своих полей.
   - *Пример:* Вызов `CalculateBonus()` из конструктора `Employee` приведет к обращению к неинициализированным данным `Manager`.

6. **Ошибки при явном приведении типов (кастинге) без предварительной проверки.**
   - *Почему возникает:* Приведение объекта через статический синтаксис `(TargetType)obj` без гарантии совпадения типов.
   - *Как избежать:* Использовать безопасное приведение `as` с проверкой на `null` или современный `pattern matching` (`is TargetType variable`).
   - *Пример:* `Car c = (Car)vehicle;` выбросит исключение `InvalidCastException`, если в переменной хранился `Bicycle`.

7. **Несовпадение сигнатур при попытке переопределения метода.**
   - *Почему возникает:* Изменение типов параметров или возвращаемого значения в производном классе.
   - *Как избежать:* Сигнатура переопределенного метода (`override`) должна байт-в-байт совпадать с виртуальным методом (`virtual`) базового класса.
   - *Пример:* `public override void SetSpeed(double s)` вместо `public override void SetSpeed(int s)` приведет к сокрытию, а не переопределению.

8. **Нарушение принципа подстановки Лисков (LSP) при переопределении логики.**
   - *Почему возникает:* Переопределенный метод в потомке делает нечто противоположное контракту родителя (например, метод `Fly()` в классе пингвина выбрасывает исключение).
   - *Как избежать:* Проектировать иерархию так, чтобы производный класс полностью соответствовал ожиданиям базового типа.
